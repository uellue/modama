## H. Data and availability

### H1. `restart: on-failure` makes `up --wait` hang on any failure of `crawler-migrate`

- **What.** D8 gives `crawler-migrate` `restart: on-failure`, and `crawler` and `crawl-timer` wait for it with `service_completed_successfully`. When the one-shot exits non-zero, Docker restarts it with growing back-off, and Compose waits for a successful completion that never comes. `--wait-timeout` does not bound that wait: it applies only to the final health wait, not to the dependency wait before the dependents start. The dependents stay `Created`, so the OAI endpoint is down. The operator sees only `Waiting` in `upstaging.sh`'s output. The design's mitigation, "the log shows the error each time; the operator acts" (`design.md:56`), assumes that the operator looks at `crawler-migrate`'s log, but nothing in the output points there.
- **Where.** `design.md:43` (D8), `:56` (Risks); `prototypes/search-stack/upstaging.sh:9-10` (`up -d --wait --wait-timeout 900`); the existing pattern `docker-compose.yml:212` (`warehouse-init`), `:326`, `:342`.
- **Scenario.** An image is rolled back without the downgrade first (spec "An image rolled back"): `migrate` exits 2 as designed. Or a migration's `ALTER` meets a transaction that holds `crawl_runs` for more than 10 s: exit 1. In both cases `./upstaging.sh --build` never returns, `crawler` and `crawl-timer` are not started, and harvests fail until someone runs `docker compose ps -a` and finds `crawler-migrate` restarting.
- **Verdict.** CONFIRMED (ran): a one-shot that exits 2 with `restart: on-failure`, and two dependents with `service_completed_successfully` / `service_healthy`. `up -d --wait --wait-timeout 30` was still waiting after 100 s, the one-shot had restarted 10 times, and the dependents were `Created`. With `restart: "no"`, the same `up` failed after 1 s with exit 1 and `service "mig" didn't complete successfully: exit 2`. A slow one-shot (25 s) with `--wait-timeout 4` also ran to completion and returned 0: the timeout does not cover it.
- **Fix.** `restart: "no"` for `crawler-migrate` (the default; drop the line). `up` then fails at once and names the service; the README's upgrade step says `docker compose logs crawler-migrate` for the reason. A lock timeout is then a failed `up` that the operator repeats, which is visible and under the operator's control (2.4). Add a failure path to task 3.1: a database written ahead of the code makes `./uptest.sh` exit non-zero within seconds, naming `crawler-migrate`. `warehouse-init` and `airflow-init` have the same pattern (`docker-compose.yml:212`, `:326`); that is a backlog note, not part of this change.

### H2. The check for pending migrations migrates before the dump

- **What.** D7: "Whether migrations are pending is shown by `modama-crawler runs` in the new image (D4) before `up`", and the operator takes the dump "before an upgrade that has migrations". The natural way to run `runs` in the new image is `docker compose run --rm crawler modama-crawler runs`. `docker compose run` starts the service's dependencies first, and after D8 `crawler` depends on `crawler-migrate`. So the check runs the migration, with the new image, before the operator has decided to take the dump. For a migration with a `downgrade()` that costs little; for one without, the dump taken afterwards is already migrated, and restoring it is no way back.
- **Where.** `design.md:41` (D7), `:43` (D8); `proposal.md:44` ("Not now": no `migrate --check`, because `runs` already says it); `tasks.md:23` (3.2: "`runs` as the check for pending migrations").
- **Scenario.** Production, a future 0005 that rewrites a column without a `downgrade()`. The operator builds the new image, runs `docker compose run --rm crawler modama-crawler runs` to see whether a dump is needed, and sees runs listed, with no error: the database was migrated a second earlier by `crawler-migrate`. The operator concludes that nothing is pending and skips the dump. A problem found the next day has no way back short of a re-crawl.
- **Verdict.** CONFIRMED (ran): in the probe project, `docker compose run --rm app echo ran` (`app` depending on the one-shot `mig` with `service_completed_successfully`) created and started `mig` before `app` (events: `start mig`, `die mig`, `start app`).
- **Fix.** Make the dump the first step of every upgrade whose image has new files in `migrations/versions/`, without a check before it, so that the order cannot go wrong. Where a check is still wanted, the README gives `docker compose run --rm --no-deps crawler modama-crawler runs`, and task 3.2 runs exactly that command and shows that `alembic_version` is unchanged afterwards. Name the trap in the README.

## M. Contradictions, gaps and reachable defects

### M1. 0002's downgrade turns subtree runs into full crawls

- **What.** D6 gives 0002 a `downgrade()` of `ALTER TABLE crawl_runs DROP COLUMN scope`, "one obvious statement" (D7). After it, a subtree run is a row like any full crawl: `last_finished()` (`store.py:271-275`, `outcome = 'finished'`) and `modama-chain`'s T count it. `subtree-crawl` itself says that this makes T a false claim, and that before a rollback "the operator deletes the subtree runs' rows (`DELETE FROM crawl_runs WHERE scope IS NOT NULL`)" (its `design.md:75`, review L4). D7's "Rolling back past this change needs nothing: the code before it [...] ignores `scope` as well" contradicts that.
- **Where.** `design.md:36` (D6), `:41` (D7, last sentence); `subtree-crawl/design.md:58` (D5), `:75` (Migration Plan).
- **Scenario.** Staging rolls back with `alembic downgrade 0001_baseline` after a few subtree crawls of `adhoc/libertem/...`. The old timer sees a finished run from an hour ago and does not catch up; `modama-chain status` states a T at the subtree crawl's start, claiming that every file older than that is in the search, which holds only for the subtree.
- **Verdict.** CONFIRMED by reading both changes. It applies only once `subtree-crawl` writes the column, which is the reason 0002 exists.
- **Fix.** Either 0002's `downgrade()` runs `DELETE FROM crawl_runs WHERE scope IS NOT NULL` before the `DROP COLUMN`, with a test that a subtree run is gone after the downgrade, or 0002 has no downgrade and the dump is the way back (forward-only, A4's alternative). In both cases D7's last sentence points at `subtree-crawl`'s rollback step instead of "needs nothing". For the pending A4 question: "trivial" should mean "loses nothing that the older code would misread", not "one statement".

### M2. The lock is taken before looking; on an upgrade, compose stops the crawl first anyway

- **What.** D3 takes the crawl lock in `env.py`, waiting for a running crawl, before anything else, so that every way into Alembic takes it. Three consequences follow, and one assumption does not hold:
  1. `crawler-migrate` runs on every `up`, also when nothing changed (Compose starts an exited one-shot again). On staging, `./upstaging.sh` for an unrelated service during the nightly crawl starts `migrate`, which has nothing to do but waits for the crawl lock for the rest of the crawl, and `up` blocks that long (H1: `--wait-timeout` does not bound it).
  2. `alembic current`, which a developer or operator uses to read the version, waits for the crawl too, and so does `alembic upgrade --sql` (`proposal.md:44` offers it as the dry run), because `env.py` connects and locks in offline mode as well. Upstream's `env.py` has an offline branch that does not connect (`metadata-warehouse/alembic/env.py:54-75`, `:97-100`).
  3. On an upgrade (`up --build`, new image ID), Compose stops and recreates `crawler` and `crawl-timer` *before* it starts `crawler-migrate`. A running crawl gets SIGTERM and is recorded as failed (as with any rebuild today); `migrate` never waits for it. So the question "`crawler` stays down while `crawler-migrate` waits [for a crawl of an hour]" (`proposal.md:52`, `design.md:53`) does not arise in the compose path; the real cost of an upgrade during a crawl is the crawl. Task 4.2's planned observation ("what compose does with the old `crawler` and `crawl-timer` while `crawler-migrate` waits") will show no wait.
- **Where.** `design.md:26-30` (D3), `:53` (Risks); `proposal.md:34` (A2), `:44`, `:52`; `tasks.md:28` (4.2).
- **Verdict.** CONFIRMED (ran). Events of an upgrade in the probe project (all three services with a changed environment): `kill app`, `destroy app`, `kill timer`, `destroy timer`, then `start mig`, `die mig` 8 s later, then `start app`, `start timer`. A second `up` with unchanged configuration started only `mig` again, with `app` and `timer` left running, and returned after the one-shot's 8 s. With the prototype `env.py` and another session holding `pg_advisory_lock(0x6D6F, 1)`, `alembic current` printed `INFO waiting for the running crawl to end` and was still waiting after 5 s; `alembic upgrade 0001_baseline:head --sql` printed the SQL only after taking the lock.
- **Fix.** In `migrate`: read the version first, without the lock; at the head, log "up to date" and exit 0 at once. Only when revisions are pending, take the lock (logging the wait), read the version again under it, and upgrade. In `env.py`: take the lock only in online mode, and keep upstream's offline branch so that `--sql` needs no database. Rewrite the proposal's question with the facts: an upgrade during a crawl costs the crawl (as today); waiting or refusing at once matters only for a `migrate` run by hand (`docker compose run --rm crawler-migrate`) while the timer is crawling. My lean: keep the wait there, since that is the case where the operator is watching.

### M3. A relative `script_location` breaks D7's downgrade command

- **What.** D2's `alembic.ini` in `python/crawler/` "points at the same directory", and D7 runs `docker compose run --rm crawler-migrate alembic -c /src/alembic.ini downgrade 0001_baseline`. Alembic resolves a relative `script_location` against the current directory, not the ini file's. The image sets no `WORKDIR` (`crawler.Dockerfile`), so the command runs in `/` and fails. Upstream writes `script_location = %(here)s/alembic` (`metadata-warehouse/alembic.ini`).
- **Where.** `design.md:24` (D2), `:41` (D7); `tasks.md:12` (2.1 tests `alembic revision` only from `python/crawler/`).
- **Scenario.** The way back after a bad upgrade, on staging, under pressure: `FAILED: Path doesn't exist: migrations. Please use the 'init' command to create a new scripts folder.` The suggestion in the message, `init`, would write a new scripts folder.
- **Verdict.** CONFIRMED (ran): `alembic -c <dir>/alembic.ini heads` with `script_location = migrations` failed from `/` with that message and worked from `<dir>`.
- **Fix.** `script_location = %(here)s/src/modama_crawler/migrations` (and `path_separator = os`, as upstream), and add to task 2.1's verification `alembic -c python/crawler/alembic.ini heads` run from `/`. Task 3.2 runs D7's command as written in the test deployment.

### M4. A revision without `downgrade()` crashes instead of refusing

- **What.** D7: "otherwise there is none, and Alembic refuses the downgrade." It does not refuse. It imports the revision and calls the missing function. The transaction rolls back, so nothing is lost, but the operator gets a traceback at the moment they most need the next step. D5 gives 0001 no `downgrade()`. Upstream's 0001 has `downgrade(): pass`, which is correct for its empty baseline but would be a lie for ours (Alembic would record "base" with all tables still there).
- **Where.** `design.md:34` (D5), `:41` (D7); `tasks.md:12` (2.1: "no `downgrade()`").
- **Verdict.** CONFIRMED (ran): `alembic downgrade base` on a database at 0002 ended with `AttributeError: module '0001_baseline_py' has no attribute 'downgrade'`, exit 1, and the database was still at `0002_crawl_runs_scope` with the column.
- **Fix.** Every revision without a way back gets `def downgrade(): raise NotImplementedError("no downgrade from <rev>: restore the dump taken before the upgrade (README, Upgrade)")`. That is also upstream's practice of a `downgrade()` per revision (pending A4), in the form that fits a non-empty baseline. The template `script.py.mako` can carry it as the default body. Add a test that downgrading below such a revision exits 1 with that message and leaves the version unchanged.

## L. Small risks and cleanliness

### L1. `SET lock_timeout` before `begin_transaction()` makes `migrate` a silent no-op

D3 sets `lock_timeout` "on the migration's connection" and then runs the revisions in one transaction. Done in the obvious way, `connection.exec_driver_sql("SET lock_timeout = '10s'")` on the SQLAlchemy connection begins a transaction (SQLAlchemy 2's autobegin). Alembic's `begin_transaction()` then sees a transaction it did not start and leaves it alone, and leaving `engine.connect()` rolls everything back. CONFIRMED (ran): `alembic upgrade head` on an empty database exited 0, printed nothing, and left no tables and no `alembic_version`. A `connection.commit()` after the `SET` fixed it. The test of "A fresh database" would catch it, but D3 should name the form: `SET LOCAL lock_timeout = '10s'` as the first statement inside `begin_transaction()`, or `options='-c lock_timeout=10s'` in the connection that the `creator` opens.

### L2. The version "before" is read outside the lock

D3: "The command around it reads the version before and after and logs one line", while the lock is taken inside `env.py`. A second `migrate` that starts while the first is migrating reads the old version (the first transaction is not committed), then waits, finds nothing to do, reads the new version, and logs "schema migrated from 0001_baseline to 0002_crawl_runs_scope" too. The spec scenario "Two migrations start at once" requires that one of them logs "up to date" (`specs/database-schema/spec.md:52-54`). PLAUSIBLE: it follows from MVCC and the design's wording; the prototype's two concurrent runs applied the revision once and both exited 0 (ran), but it did not have the command's log line. Fix: read "before" under the lock (in `env.py`, `context.get_context().get_current_revision()` before `run_migrations()`, passed back through `config.attributes`); this goes with M2's fix.

### L3. The schema check imports Alembic into every command

D4's `schema.check` gets the head from Alembic's `ScriptDirectory`. Reading the directory takes 1 ms; importing `alembic.script` takes 226-238 ms and pulls in SQLAlchemy and Mako (ran, three times). Importing `modama_crawler.cli` takes 239-274 ms today, so every `runs`, every crawl subprocess of the timer and every CLI test subprocess roughly doubles its start time. The design's risk "it reads one directory of small files; measured in task 2.3" (`design.md:58`) measures the wrong part. Cheaper: a constant `HEAD = "0001_baseline"` in `schema.py`, checked against `ScriptDirectory` by the single-head test, so that only `migrate` imports Alembic. Either way, task 2.3 should measure the import, not the read.

### L4. `crawler-migrate` needs `pull_policy: never`

D8 gives the service the image `search-stack-crawler`, which only `crawler` builds. Without `pull_policy: never`, `up` on a host without the image first tries Docker Hub. CONFIRMED (ran): `mig Error pull access denied for revmig-probe-img`, after which the build supplied the image and `up` ended with 0. `crawl-timer` and `warehouse-init` already carry the line for that reason (`docker-compose.yml:111`, `:210`). Add it, with the same comment.

### L5. `before_migrations.sql` as a copy of 0001 compares a schema with itself

D9's previous-schema test loads `before_migrations.sql`, which "holds `ensure_tables`' statements as plain SQL", and 0001 executes the same statements. When this change ships first, the test cannot find a difference between the two schemas, only that the rows survive and that the database is adopted. That is useful, but it is not R42's "a database made by the code before this change" (`proposal.md:14`). The real evidence is task 4.1, which runs the crawler at e35e4b4. Fix: take the file from e35e4b4's `store.py` (`git show e35e4b4:python/crawler/src/modama_crawler/store.py`), with that commit in a header comment, and say in D9 what the test proves. With `subtree-crawl` first, the file differs from 0001 and the comparison does find differences, as D6 says.

### L6. Small points

- **Task 1.2's verification does not run.** `~/.venv` is made by `uv venv` (README) and has no pip: `~/.venv/bin/python -m pip show` gives `No module named pip` (ran). Use `uv pip show --python ~/.venv/bin/python alembic SQLAlchemy Mako` and `uv pip list`. The versions, the MIT licences (`License-Expression`) and the requirements (alembic: SQLAlchemy ≥ 2.0, Mako, typing-extensions ≥ 4.12; SQLAlchemy 2.1.8: typing-extensions only; Mako: MarkupSafe) are as the proposal says, and `typing-extensions` 4.16.0 and MarkupSafe 3.0.4 are installed already (ran).
- **D1 and "What Changes" were not updated for A1.** A1 now follows the warehouse: `op.add_column`/`op.alter_column` with `sa` types or `op.execute`, "whichever fits" (`proposal.md:33`). D1 still says "Alembic with plain SQL [...] with `op.execute`" (`design.md:22`), "What Changes" says "plain SQL through `op.execute`" (`proposal.md:21`), and task 2.6 has the README say "plain DDL from 0003 on". Align them.
- **Alembic's own log lines.** Under `main()`'s `logging.basicConfig(level=INFO)`, an upgrade also logs seven `INFO setup plugin alembic.autogenerate...` lines, `Context impl PostgresqlImpl.`, `Will assume transactional DDL.` and one `Running upgrade A -> B` per revision (ran). D3 promises one line. The `Running upgrade` lines are worth keeping: they name the failing revision, which the spec requires for "A failed migration changes nothing". Set the `alembic` logger to WARNING and `alembic.runtime.migration` to INFO. Conversely, the "small `alembic.ini`" without `[loggers]` makes Alembic's own command line print nothing at all on an upgrade (ran); copy upstream's logging sections.
- **"waiting for the running crawl to end"** is also what the second of two `migrate`s logs; "waiting for the crawl lock (a crawl or another migration holds it)" is true in both cases.
- **The endpoint is down during an upgrade,** not answering 503: Compose stops `crawler` before `crawler-migrate` runs (M2). That is today's behaviour on any rebuild; the Non-Goals' "harvesters retry on 503" (`design.md:18`) should say "the endpoint is down for the length of the migration".
- **A downgrade runs before the rebuild.** There is one image tag, `search-stack-crawler`; the downgrade needs the newer code, so the README's rollback is: downgrade with the image that is still there, then check out and `--build` the older version. Task 3.2 should keep that order.
- **No CI.** `.github/workflows/ci.yml` runs no crawler tests, so the single-head, previous-schema and lock tests run only where a developer runs `pytest` (as noted in `design/review.md`, C5). Not this change's to fix, but "`pytest` runs the new one" (`proposal.md:26`) holds only locally.

## For the pending questions on A3 and A4

Facts only, for @weber's answer on whether "follow the warehouse's practice" covers them.
- **A3, baseline.** Upstream's create script is frozen at the baseline: `scripts/postgres_data/create_sql` does not have 0002's `raw_subjects` (grep), and its README says the script "defines the initial state of the database and should be stamped as the migration baseline". Upstream's form, applied here, would keep `ensure_tables` frozen as the create script, and every caller (the `conn` fixture, `migrate`, the README's setup) would need "create, stamp if `alembic_version` is missing, upgrade", which `init-warehouse.sh:32-34` already shows as glue. The proposal's form runs the same statements as 0001 and needs no stamp. Both keep a single copy of the baseline; the proposal's needs no glue. The specific reason against upstream's form holds.
- **A4, downgrades.** Upstream writes a `downgrade()` for every revision, 0001 included (`pass`). For a non-empty baseline, `pass` is wrong (M4), and for 0002 "one statement" loses information that the older code misreads (M1). Following upstream "as far as sensible" would give: a `downgrade()` in every revision, and where there is no safe one, a `downgrade()` that refuses with the step.

## Right, and should stay

- **One transaction for all pending revisions.** Ran: with 0002 adding the column and a third revision failing, the database stayed at `0001_baseline` without the column, exit 1. Alembic 1.20.1's defaults are as D3 cites (`transaction_per_migration: bool = False`, `PostgresqlImpl.transactional_ddl = True`).
- **The baseline adopts a database made by `ensure_tables` in place.** Ran: on a database made with the statements of `store.py:62-157`, with a finished run and a record, `upgrade head` kept both rows, gave the old run `scope` NULL and recorded the version. `CREATE TABLE IF NOT EXISTS` on an existing table takes no lock; `CREATE INDEX IF NOT EXISTS` takes SHARE, which does not block `serve`'s reads; `ADD COLUMN IF NOT EXISTS` takes ACCESS EXCLUSIVE even when the column exists (ran, `pg_locks`), as `subtree-crawl`'s L2 found, which is harmless once, in `migrate`.
- **The crawl lock as the migration lock.** Ran: with a session holding `(0x6D6F, 1)`, two concurrent upgrades both logged the wait, both exited 0 after the release, and the revision was applied once; Alembic reads the current version only after `env.py` has the lock. The reasoning against a separate key (a crawl's final store against a changed schema) is sound.
- **SQLAlchemy only as Alembic's connection layer, through `creator`.** Ran: `create_engine("postgresql+psycopg://", creator=lambda: psycopg.connect(conninfo))` works with SQLAlchemy 2.1.8 and psycopg 3.3.8, so the connection settings stay in `conninfo_from_env()`.
- **The "ahead" check before upgrading.** Alembic's own message is `FAILED: Can't locate revision identified by '0003_x'` (ran), which names no step. The check also refuses a database that another Alembic user owns: pointed by mistake at the warehouse's `datasetdb` (at `0005_remove_doi`), `migrate` changes nothing.
- **The refusal in the other commands.** Exit 2 before a run is recorded or a port opened, with the versions and the command to run: probed, visible and with the step, as 2.4 asks.
- **The cost in the tests is small.** Ran: a migrated fresh database took 34-44 ms per test in process, against 15-19 ms for the statements alone; `pytest-postgresql` templates are not needed.
- **The facts the design cites are right.** `store.py` is identical at 3251cad and e35e4b4 (`git diff` empty); the `cli.py` call sites `:270`, `:402`, `:454`, `:484`; `conftest.py:44-47`; `init-warehouse.sh:19-35`; Alembic's line references; `modama-chain` checks `to_regclass('crawl_runs')` and ignores other tables (`crawler.py:102`). Every spec scenario is cited by a task, and `openspec validate schema-migrations --strict` passes.
- **Scope.** No backup inside `migrate`, no zero-downtime tooling, no `migrate --check`, no frozen schema per release: nothing beyond R42. The one-shot service rather than `migrate && exec serve` keeps the logs apart and gives `crawl-timer` the same wait.
