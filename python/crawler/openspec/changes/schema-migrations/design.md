# Design

## Context

Motivation: proposal, "Why". The research note (`docs/research/schema-migrations.md`, 22f891d) has the sources; what shapes this design:

- **Today.** `ensure_tables` (`store.py:62-157`) runs `CREATE TABLE / INDEX IF NOT EXISTS` for the five tables in one transaction. `crawl`, `timer`, `runs` and `serve` call it first (`cli.py:270`, `:402`, `:454`, `:484`), and the timer's crawl subprocesses again. The crawl lock is `pg_try_advisory_lock(0x6D6F, 1)` on the crawl's connection, held for the whole crawl (`store.py:23-33`, `cli.py:270-280`); the store lock is `(0x6D6F, 2)`. `CREATE INDEX IF NOT EXISTS` takes a SHARE lock even when the index exists, so `runs` already waits for a crawl's store transaction (review of `subtree-crawl`, `review.md:129`).
- **Staging's database** was made by 3251cad (`./downstaging.sh --reset`, run 3). `store.py` is identical at 3251cad and at e35e4b4 (`git diff 3251cad e35e4b4 -- python/crawler/src/modama_crawler/store.py` is empty).
- **Upstream.** The metadata warehouse uses Alembic since v1.8.0: an empty `0001_baseline`, `alembic stamp` after `create_db.py`, raw SQL in `op.execute`, `target_metadata = None`, a `downgrade()` per revision, no lock, run by hand. Our `init-warehouse.sh:19-35` already runs it at every start of `warehouse-init`. Airflow runs `command.upgrade` under `pg_advisory_lock` with a `lock_timeout`, and `check-migrations` compares the database's heads with the code's.
- **Alembic 1.20.1**, checked in its wheel on 2026-11-12: no advisory lock anywhere in the package; all pending revisions run in one transaction by default (`runtime/environment.py:419`, `transaction_per_migration: bool = False`); PostgreSQL DDL is transactional (`ddl/postgresql.py:79`); the package-resource form of `script_location` is untested (`util/pyfiles.py:60`).
- **Readers of the tables:** `modama-chain` reads `crawl_runs`, `records`, `datasets` and `members` and checks `to_regclass('crawl_runs')` (`search-chain/src/modama_chain/crawler.py:102`). An extra table `alembic_version` does not concern it.
- **Search stack:** `crawler` (`serve`) and `crawl-timer` share the image `search-stack-crawler` and `crawler-db` (`docker-compose.yml:69-139`); `crawl-timer` waits for `crawler` to be healthy. `upstaging.sh` runs `up -d --wait --wait-timeout 900`, which already waits for the one-shot services `warehouse-init` and `airflow-init` as long as they succeed; one that keeps failing under `restart: on-failure` blocks it without end, and `--wait-timeout` does not bound that wait (review H1).

## Goals / Non-Goals

**Goals:** a schema change is a reviewed migration that reaches every database, staging's included, in place; nothing but `migrate` changes the schema; a database that does not fit the code is refused with the step to take.

**Non-Goals:** zero-downtime migrations (one writer; the endpoint is down for the length of the migration, as on any rebuild today, D8); migrating the warehouse or other stores; a general migration framework of our own.

## Decisions

**D1. Alembic without models, as the warehouse (A1, decided).** Revisions are `versions/NNNN_name.py`, written with Alembic's operations (`op.add_column`, `op.alter_column`, `op.drop_column` with `sa` types) or `op.execute` with SQL text, whichever fits, as in the warehouse's `alembic/versions/0002` to `0005`; a linear chain, readable ids of at most 32 characters (`version_num VARCHAR(32)`). `env.py` sets `target_metadata = None`: no models, no autogenerate. The crawler keeps using psycopg directly; SQLAlchemy appears only as Alembic's connection layer, with an engine whose `creator` opens a psycopg connection from the crawler's connection string, so that there is one place for the connection settings (`cli.conninfo_from_env`). *Alternatives:* models and autogenerate (a second description of the schema); numbered SQL files with a version table of our own, about 50 lines and no dependency, but an invention where upstream uses a standard tool (research, section 4).

**D2. Layout.** `src/modama_crawler/migrations/` holds `env.py`, `script.py.mako` and `versions/`, shipped in the package (`*.mako` as package data). The `migrate` command builds Alembic's `Config` in code with `script_location` as an absolute path from the package's `__file__` (not the untested package-resource form). A small `alembic.ini` in `python/crawler/` points at the same directory, so that Alembic's own command line works for developers (`alembic revision`, `alembic history`) and, inside the image, for a downgrade (D7), from any directory: `script_location = %(here)s/src/modama_crawler/migrations` and `path_separator = os`, as upstream's `alembic.ini` (a relative path is resolved against the current directory, and the image has no `WORKDIR`: review M3). It carries upstream's logging sections, so that Alembic's command line prints `Running upgrade …`; `env.py` applies them (`fileConfig`) only when the command line runs it (`config.config_file_name` set), so that `migrate` keeps the crawler's logging (D3). `env.py` takes the connection string from `config.attributes` when `migrate` passes one, and from `conninfo_from_env()` otherwise, so the environment is still read in `cli.py` only.

**D3. `migrate`, its lock and its timeout (A2).** First look, then lock (review M2):
- `migrate` reads the version with psycopg, without a lock, and runs D4's check. Ahead: exit 2. At the head: `INFO schema up to date at <head>`, exit 0, at once, also while a crawl runs. This matters because compose starts `crawler-migrate` again on every `up`, also on one for an unrelated service (D8).
- Only when revisions are pending does it call Alembic's `upgrade`. `env.py` does what every way in that writes must do, so that `alembic upgrade` or `downgrade` from the command line is as safe as `migrate` (alembic#633 recommends the lock in `env.py`): as the first statements of the migration's transaction, before the lock timeout is set, it tries the crawl lock; if it is held, it logs `INFO waiting for the crawl lock (a crawl or another migration holds it)` and waits (`pg_advisory_xact_lock`; Ctrl-C ends the wait and changes nothing). The lock ends with the transaction. (Apply: first a session lock on a connection of its own; changed after the code review, finding 6, because that lock ended when the client was killed while the server still ran a statement.) A crawl started meanwhile is refused by the crawl lock.
- Under the lock, `env.py` reads the version again (`get_current_revision()`) and hands it back through `config.attributes` as the version "before" (review L2). A second `migrate` that waited for the first thus finds nothing pending and logs `up to date`.
- `alembic current` takes no lock (Alembic marks it `dont_mutate`). Offline (`alembic upgrade --sql`), `env.py` connects to no database, as upstream's offline branch (`metadata-warehouse/alembic/env.py:54-75`).
- The first statement inside the migration's transaction is `SET LOCAL lock_timeout = '10s'`, so that a statement waiting for a table lock fails instead of queueing `serve`'s requests behind it for longer than that. Not a `SET` before `begin_transaction()`: SQLAlchemy would begin a transaction that Alembic leaves alone and that is rolled back at the end, a silent no-op with exit 0 (review L1).
- All pending revisions run in one transaction (Alembic's default).
The command logs one line of its own: `INFO schema migrated from 0001_baseline to 0002_crawl_runs_scope`, `INFO schema up to date at 0002_crawl_runs_scope`, or, for a database without version table whose tables exist, `INFO tables made before migrations found: adopted as 0001_baseline` before the first. Of Alembic's own lines it keeps `INFO Running upgrade 0001_baseline -> 0002_crawl_runs_scope`, one per revision, which names a failing revision: the logger `alembic` is set to WARNING and `alembic.runtime.migration` to INFO (review L6: otherwise ten lines of plugin setup). Exit status: 0 done or up to date; 1 a migration failed, with `ERROR migration 0002_crawl_runs_scope failed, the database is unchanged at 0001_baseline: <the database's error>` (spec "A failed migration changes nothing"); after a lock timeout the line ends with `another transaction held a table for more than 10 s: run migrate again`; 2 the database is ahead (D4). *Why the crawl lock rather than a new key* `(0x6D6F, 3)` *as the research proposed:* a running crawl may hold table locks in an open transaction for a long time, and a migration that ran next to the walk would leave the crawl's final store writing to a schema it was not written for. Waiting for the crawl also serialises two migrations, with no second key. The price is a wait, and only when `migrate` is run by hand during a crawl: on an upgrade, compose stops the crawl before `crawler-migrate` starts (D8). Whether to wait or refuse then was question 140: wait (@weber, 2026-11-12).

**D4. The check in the other commands (A2).** A function in a small module next to the migrations, `schema.check(conn)`, replaces `ensure_tables` at the four call sites. It reads `alembic_version` with psycopg (`to_regclass` first) and compares it with a constant `HEAD = "0001_baseline"` in `schema.py`, and with the revision ids in `versions/` (file names, for "ahead"). The single-head test (D9) checks that `HEAD` is the head of Alembic's `ScriptDirectory`, so a new migration that forgets it fails the tests. So only `migrate` imports Alembic: importing `alembic.script` takes about 230 ms and pulls in SQLAlchemy and Mako, as long as importing `modama_crawler.cli` takes today, and every `runs`, timer crawl and CLI test would pay it (review L3). Equal: nothing. Missing or an older revision: `ERROR the database schema is at 0001_baseline, this crawler needs 0002_crawl_runs_scope: run modama-crawler migrate`, or `ERROR the database has no schema version, this crawler needs 0001_baseline: run modama-crawler migrate`. A revision the code does not know: `ERROR the database schema is at 0003_x, which this crawler does not know: a newer crawler migrated it; use that crawler, or downgrade with it first (README)`. Both exit with status 2, before a run is recorded or a port opened. `migrate` runs the same check for "ahead" before upgrading, so that it fails with this message rather than Alembic's "Can't locate revision". The check does not wait, unlike Airflow's `check-migrations`: compose orders the start (D8). A side effect: `runs` no longer takes a table lock at start (Context), so it no longer waits for a crawl's store transaction.

**D5. Baseline: 0001 is `ensure_tables` (A3).** `0001_baseline.upgrade()` executes `ensure_tables`' statements as they are at e35e4b4, `IF NOT EXISTS` included; `ensure_tables` is removed from `store.py`. A database without `alembic_version` is at "no revision" for Alembic, so `migrate` runs 0001 on it. On an empty database that creates the schema. On a database made by `ensure_tables` it changes nothing, and Alembic records 0001: the database is adopted without a `stamp` step. 0001's `downgrade()` refuses (D7): dropping every table is not a way back. *Compared with upstream's* empty 0001 plus `stamp`: upstream keeps its schema in a create script (`create_db.py`), so its baseline must be empty and every fresh database needs the stamp, which `init-warehouse.sh:32-34` does conditionally. We have no create script, so one source and no stamp is simpler. *Risk:* `IF NOT EXISTS` would also adopt a database that differs from the baseline. Added in apply after the code review (finding 1: tables made before c2b2afb were adopted, and `crawl` then failed on a missing column): 0001 runs its statements again in a schema `baseline_check` and refuses, with the step, when the existing tables lack a column or have it with another type or nullability; extra columns, indexes and constraints are not compared. Staging is compared once by hand (task 4.3); from 0003 on, no migration uses `IF NOT EXISTS` (Alembic's operations have none), so a drifted database fails loudly.

**D6. `scope` becomes 0002 in either order (A6).** `0002_crawl_runs_scope`: `ALTER TABLE crawl_runs ADD COLUMN IF NOT EXISTS scope TEXT` (nullable, no default, no table rewrite). Its `downgrade()` first deletes the subtree runs, `DELETE FROM crawl_runs WHERE scope IS NOT NULL`, then `ALTER TABLE crawl_runs DROP COLUMN scope`: without the delete, the older code's `last_finished()` (`store.py:271-275`) and `modama-chain`'s T would count a subtree run as a full crawl, and T would claim that every file older than its start is in the search. That is `subtree-crawl`'s own rollback step (its Migration Plan, review L4), done by the downgrade (review M1). Probed on a prototype on 2026-11-12 (after the downgrade the subtree run was gone, the full run kept, the column dropped); tested in task 2.5.
- *This change first:* 0001 is e35e4b4's `ensure_tables`; `subtree-crawl` adds 0002 as its task 3.1 instead of the `ALTER` in `ensure_tables`, with this `downgrade()`, and its D5 says so. Staging gets 0001 (adopted), later 0002.
- *`subtree-crawl` first:* staging gets the column from `ensure_tables`. This change then takes 0001 as `ensure_tables` without that `ALTER` (the e35e4b4 form), adds 0002 as above, and removes the `ALTER` with the rest of `ensure_tables`; `tests/migrations/before_migrations.sql` (D9) then includes the column, because that is what staging has. On staging, 0001 and 0002 both change nothing and are recorded.
- In both orders the chain and the final schema are the same. The `IF NOT EXISTS` in 0002 is what makes the second order work; it is the last one.

**D7. Downgrades and the way back (A4, question 160, decided 2026-11-12 with the lean; the way back revised by @weber the same day).** Every revision has a `downgrade()`, as upstream's do. It undoes the revision where the result leaves nothing that the older code would misread (0002: delete the subtree runs, then drop the column, D6), tested up-down-up. Otherwise it refuses with the step: `raise NotImplementedError("no downgrade from 0001_baseline: start from an empty database and crawl again (README, Upgrade)")`, which is the default body in `script.py.mako`. 0001 has this one; upstream's `pass` fits its empty baseline but would record "no version" here with every table still there. Without any `downgrade()`, Alembic does not refuse: it ends with `AttributeError: module '0001_baseline_py' has no attribute 'downgrade'` (review M4). With the refusal, Alembic's command line prints a traceback whose last line is the message, exits 1, and the version is unchanged (probed on a prototype on 2026-11-12).
- *An empty database and a crawl, where a downgrade refuses* (@weber, 2026-11-12, for staging and production: "we don't need to worry about a backup of the crawler + warehouse. We just need to be able to reproduce any failure in a test case, and bring up a fresh staging", and "The migration is just to avoid a recrawl, but we are working to make a recrawl cheap enough to not shed tears"). First the evidence for a test case (`docker compose ps -a`, `docker compose logs`); then `dropdb` and `createdb` of the crawler's database (or the stack's `--reset`), the older code, and a crawl, with its harvest and indexing. A `pg_dump -Fc` before the upgrade is optional: it only saves that crawl. Was: the dump as the first step of every upgrade that brings a migration, restoring it the way back. Whether a new file comes is seen without the database: `git diff --stat <deployed commit> HEAD -- python/crawler/src/modama_crawler/migrations/versions/` after the pull. Asking the database instead needs `docker compose run --rm --no-deps crawler modama-crawler runs`, which refuses with D4's message when a migration is pending. Without `--no-deps`, `docker compose run` starts `crawler-migrate` first, because `crawler` depends on it (D8), and the check migrates the database (review H2); the README names that trap.
- *The way back.* There is one image tag, `search-stack-crawler`, and the downgrade needs the newer code, so it runs before the older code is built: `docker compose stop crawl-timer`, then `docker compose run --rm crawler-migrate alembic -c /src/alembic.ini downgrade <revision>` with the image that is still there, then check out the older code and `./upstaging.sh --build`. Rolling back past this change: if `subtree-crawl` came after it, the downgrade to `0001_baseline` removes the subtree runs and `scope`, and the older code's `ensure_tables` is a no-op on that schema and ignores `alembic_version`. If `subtree-crawl` came first, the older code is `subtree-crawl`'s, which uses `scope`: no downgrade, only the older image; rolling back past `subtree-crawl` too is its rollback step (delete the subtree runs), done by hand there.

**D8. The search stack: a one-shot `crawler-migrate` (A2).** Image `search-stack-crawler` with `pull_policy: never  # built by another service`, as `crawl-timer` (`docker-compose.yml:111`; without it, `up` first tries Docker Hub: review L4), `command: modama-crawler migrate`, `environment: *crawler-env`, no `restart` line (Compose's default, `"no"`), `depends_on: crawler-db: service_healthy`. `crawler` and `crawl-timer` get `depends_on: crawler-migrate: condition: service_completed_successfully`. The staging overlay needs nothing for it: it reads no data.
- *No restart.* With `restart: on-failure`, a refusal or a failed migration is restarted for ever, and `up --wait` waits for a success that never comes, unbounded by `--wait-timeout`, with `crawler` and `crawl-timer` not started and nothing in the output pointing at the cause (review H1, probed). Without it, `up` exits 1 within seconds with `service "crawler-migrate" didn't complete successfully: exit 2` (or `exit 1`); `docker compose logs crawler-migrate` shows the reason and the step (D10). `warehouse-init` and `airflow-init` have the same `restart: on-failure` (`docker-compose.yml:212`, `:326`): a backlog note, not this change.
- *What compose does on an upgrade.* With a new image, compose stops and recreates `crawler` and `crawl-timer` before it starts `crawler-migrate`. A running crawl is stopped and recorded as failed, as on any rebuild today, so `migrate` does not wait for it; the endpoint is down from that stop until `crawler` is healthy again. On an `up` with nothing new, compose starts only `crawler-migrate` again, which reports `up to date` at once (D3), and leaves `crawler` and `crawl-timer` running (review M2, probed). *Alternative:* `sh -c "modama-crawler migrate && exec modama-crawler serve"` in `crawler`: one service less, but it migrates on every restart of `serve`, mixes two logs, and `crawl-timer` would still need its own wait.

**D9. Tests (A5).**
- `conn` (`tests/conftest.py:44-47`) migrates the fresh `pytest-postgresql` database to head with the same function as `migrate`, instead of `ensure_tables`. Every database test then runs on the migrated schema.
- `tests/migrations/before_migrations.sql` holds the statements of `ensure_tables` as they are in `git show e35e4b4:python/crawler/src/modama_crawler/store.py`, as plain SQL, with that commit in a header comment: the schema of the code before this change, which made staging. Taken from the old code, not copied from 0001, so that it stays the old schema whatever happens to 0001 (review L5). Plain SQL rather than `pg_dump` output, because a plain dump carries psql meta-commands that psycopg cannot run: the VM's pg_dump 17.11 writes `\restrict <random key>` and `\unrestrict …` lines (tried 2026-11-12). What the test proves: when this change ships first, the file equals 0001's statements, so it shows that the rows survive and that the database is adopted, not that two different schemas converge; with `subtree-crawl` first, the file has `scope` and the comparison also covers 0002. The evidence that a database made by the old code migrates is task 4.1, which runs the crawler at e35e4b4.
- `tests/test_migrations.py`, one test per spec scenario: the before-migrations database with a finished run, a dataset with a member, a stored listing and a record, migrated and compared with a fresh one (columns with type, nullability and default; index and constraint definitions from the catalog), rows and datestamps unchanged; a single head, equal to `schema.HEAD` (D4); up-down-up for every revision whose `downgrade()` undoes it; the refusal of a downgrade (`downgrade base` exits 1 with D7's message, the version unchanged); the refusals (behind, none, ahead: an unknown revision written into `alembic_version`) through the CLI; two `migrate` processes at once; `migrate` while a test holds the crawl lock, with a migration pending (waits) and at the head (returns at once); `alembic current` while the lock is held (returns at once) and `alembic upgrade --sql` without a database; a failing second revision and the lock timeout, with a scripts directory under `tmp_path` that holds 0001 and a revision made to fail.
- The search stack's `./runtest.sh e2e` covers the fresh path through `crawler-migrate`.

**D10. What the operator sees, and the step (requirement 2.4, "The operator stays in control").** Every case names its cause and the next step, in the log of the service that stopped and in the READMEs (tasks 2.6, 3.2):

| Case | What the operator sees | Step |
|---|---|---|
| Upgrade with a migration (`./upstaging.sh --build`) | `crawler-migrate` logs `INFO schema migrated from 0001_baseline to 0002_crawl_runs_scope`; `crawler` and `crawl-timer` start after it. A crawl running at that moment was stopped and is listed by `runs` as failed. | none |
| `up` with nothing to migrate | `INFO schema up to date at 0002_crawl_runs_scope`, at once, also during a crawl | none |
| Database ahead of the image (an older image started without the downgrade first) | `up` exits 1: `service "crawler-migrate" didn't complete successfully: exit 2`; the log: `ERROR the database schema is at 0003_x, which this crawler does not know: a newer crawler migrated it; use that crawler, or downgrade with it first (README)` | the newer image, or its downgrade (D7) |
| A migration fails, or a table lock is not granted in 10 s | `up` exits 1 (`exit 1`); the log: `ERROR migration 0002_crawl_runs_scope failed, the database is unchanged at 0001_baseline: …`, after a lock timeout ending `… run migrate again` | run `up` again; otherwise the error, to the developers |
| `migrate` by hand during a crawl (`docker compose run --rm crawler-migrate`) | `INFO waiting for the crawl lock (a crawl or another migration holds it)`, then the migration after the crawl | wait, or Ctrl-C (nothing changed); question 140, decided: wait |
| Any other command on a database behind the code | `ERROR the database schema is at 0001_baseline, this crawler needs 0002_crawl_runs_scope: run modama-crawler migrate`, exit 2 | `migrate` |
| A downgrade that has no way back | Alembic's traceback, last line `NotImplementedError: no downgrade from 0001_baseline: start from an empty database and crawl again (README, Upgrade)`, exit 1, nothing changed | keep the logs; an empty database and a crawl (D7) |

## Risks / Trade-offs

- [An upgrade during a crawl costs the crawl] → as on any rebuild today: compose stops `crawl-timer` before `crawler-migrate` starts (D8); the timer catches up at its next run.
- [`migrate` run by hand during a crawl waits for its end, an hour or more] → logged (`waiting for the crawl lock …`); Ctrl-C ends the wait and changes nothing; question 140, decided: wait, "we see how it handles in practice".
- [A timer still running the old image starts its crawl while a hand-run `migrate` holds the lock] → that crawl exits with status 1 and "another crawl is running on this database", which is misleading, and the timer waits for the next day (the known limitation in `subtree-crawl`'s backlog item). A migration of the kind planned takes seconds. Through compose this does not arise: the old timer is stopped first.
- [A shipped migration is edited] → nothing in the tests catches it once databases are made by the chain; the README says never, and the review checks it.
- [A failed `crawler-migrate` leaves the endpoint down] → `up` fails at once and names the service (D8); the step is in D10 and the README.
- [A second connection layer] → SQLAlchemy only inside migrations; `store.py` stays on psycopg.
- [`schema.HEAD` not updated with a new migration] → the single-head test fails (D4).

No dump and no dry run on a copy (D7, @weber 2026-11-12).
