# Design

## Context

Motivation: proposal, "Why". The research note (`docs/research/schema-migrations.md`, 22f891d) has the sources; what shapes this design:

- **Today.** `ensure_tables` (`store.py:62-157`) runs `CREATE TABLE / INDEX IF NOT EXISTS` for the five tables in one transaction. `crawl`, `timer`, `runs` and `serve` call it first (`cli.py:270`, `:402`, `:454`, `:484`), and the timer's crawl subprocesses again. The crawl lock is `pg_try_advisory_lock(0x6D6F, 1)` on the crawl's connection, held for the whole crawl (`store.py:23-33`, `cli.py:270-280`); the store lock is `(0x6D6F, 2)`. `CREATE INDEX IF NOT EXISTS` takes a SHARE lock even when the index exists, so `runs` already waits for a crawl's store transaction (review of `subtree-crawl`, `review.md:129`).
- **Staging's database** was made by 3251cad (`./downstaging.sh --reset`, run 3). `store.py` is identical at 3251cad and at e35e4b4 (`git diff 3251cad e35e4b4 -- python/crawler/src/modama_crawler/store.py` is empty).
- **Upstream.** The metadata warehouse uses Alembic since v1.8.0: an empty `0001_baseline`, `alembic stamp` after `create_db.py`, raw SQL in `op.execute`, `target_metadata = None`, a `downgrade()` per revision, no lock, run by hand. Our `init-warehouse.sh:19-35` already runs it at every start of `warehouse-init`. Airflow runs `command.upgrade` under `pg_advisory_lock` with a `lock_timeout`, and `check-migrations` compares the database's heads with the code's.
- **Alembic 1.20.1**, checked in its wheel on 2026-11-12: no advisory lock anywhere in the package; all pending revisions run in one transaction by default (`runtime/environment.py:419`, `transaction_per_migration: bool = False`); PostgreSQL DDL is transactional (`ddl/postgresql.py:79`); the package-resource form of `script_location` is untested (`util/pyfiles.py:60`).
- **Readers of the tables:** `modama-chain` reads `crawl_runs`, `records`, `datasets` and `members` and checks `to_regclass('crawl_runs')` (`search-chain/src/modama_chain/crawler.py:102`). An extra table `alembic_version` does not concern it.
- **Search stack:** `crawler` (`serve`) and `crawl-timer` share the image `search-stack-crawler` and `crawler-db` (`docker-compose.yml:69-139`); `crawl-timer` waits for `crawler` to be healthy. `upstaging.sh` runs `up -d --wait`, which already copes with the one-shot services `warehouse-init` and `airflow-init`.

## Goals / Non-Goals

**Goals:** a schema change is a reviewed migration that reaches every database, staging's included, in place; nothing but `migrate` changes the schema; a database that does not fit the code is refused with the step to take.

**Non-Goals:** zero-downtime migrations (one writer; harvesters retry on 503); migrating the warehouse or other stores; a general migration framework of our own.

## Decisions

**D1. Alembic with plain SQL (A1).** Revisions are `versions/NNNN_name.py` with `op.execute("""…""")`, a linear chain, readable ids of at most 32 characters (`version_num VARCHAR(32)`). `env.py` sets `target_metadata = None`: no models, no autogenerate. The crawler keeps using psycopg directly; SQLAlchemy appears only as Alembic's connection layer, with an engine whose `creator` opens a psycopg connection from the crawler's connection string, so that there is one place for the connection settings (`cli.conninfo_from_env`). *Alternatives:* models and autogenerate (a second description of the schema); numbered SQL files with a version table of our own, about 50 lines and no dependency, but an invention where upstream uses a standard tool (research, section 4).

**D2. Layout.** `src/modama_crawler/migrations/` holds `env.py`, `script.py.mako` and `versions/`, shipped in the package (`*.mako` as package data). The `migrate` command builds Alembic's `Config` in code with `script_location` as an absolute path from the package's `__file__` (not the untested package-resource form). A small `alembic.ini` in `python/crawler/` points at the same directory, so that Alembic's own command line works for developers (`alembic revision`, `alembic history`) and, inside the image, for a downgrade (D7). `env.py` takes the connection string from `config.attributes` when `migrate` passes one, and from `conninfo_from_env()` otherwise, so the environment is still read in `cli.py` only.

**D3. `migrate`, its lock and its timeout (A2).** `env.py` does what every way in must do, so that `alembic upgrade` from the command line is as safe as `modama-crawler migrate` (alembic#633 recommends the lock in `env.py`):
- On a connection of its own it tries the crawl lock; if a crawl holds it, it logs `INFO waiting for the running crawl to end` and then waits for it (`pg_advisory_lock`). It holds the lock until the migration's transaction has ended. A second `migrate` therefore waits too, and then finds nothing to do. A crawl started meanwhile is refused by the crawl lock.
- On the migration's connection it sets `lock_timeout = '10s'`, so that a statement waiting for a table lock fails instead of queueing `serve`'s requests behind it for longer than that.
- Then it runs the pending revisions in one transaction (Alembic's default).
The command around it reads the version before and after and logs one line: `INFO schema migrated from 0001_baseline to 0002_crawl_runs_scope`, `INFO schema up to date at 0002_crawl_runs_scope`, or, for a database without version table whose tables exist, `INFO tables made before migrations found: adopted as 0001_baseline` before the first. Exit status: 0 done or up to date; 1 a migration failed (its revision and the database error in the message, nothing changed, spec "A failed migration changes nothing"); 2 the database is ahead (D4). *Why the crawl lock rather than a new key* `(0x6D6F, 3)` *as the research proposed:* a running crawl may hold table locks in an open transaction for a long time, and a migration that ran next to the walk would leave the crawl's final store writing to a schema it was not written for. Waiting for the crawl also serialises two migrations, with no second key. The price is the wait (proposal, questions).

**D4. The check in the other commands (A2).** A function in a small module next to the migrations, `schema.check(conn)`, replaces `ensure_tables` at the four call sites. It reads `alembic_version` with psycopg (`to_regclass` first) and compares it with the head of the migrations directory (Alembic's `ScriptDirectory`, which does not need SQLAlchemy to connect). Equal: nothing. Missing or an older revision: `ERROR the database schema is at 0001_baseline, this crawler needs 0002_crawl_runs_scope: run modama-crawler migrate`, or `ERROR the database has no schema version, this crawler needs 0001_baseline: run modama-crawler migrate`. A revision the code does not know: `ERROR the database schema is at 0003_x, which this crawler does not know: a newer crawler migrated it; use that crawler, or downgrade with it first (README)`. Both exit with status 2, before a run is recorded or a port opened. `migrate` runs the same check for "ahead" before upgrading, so that it fails with this message rather than Alembic's "Can't locate revision". The check does not wait, unlike Airflow's `check-migrations`: compose orders the start (D8). A side effect: `runs` no longer takes a table lock at start (Context), so it no longer waits for a crawl's store transaction.

**D5. Baseline: 0001 is `ensure_tables` (A3).** `0001_baseline.upgrade()` executes `ensure_tables`' statements as they are at e35e4b4, `IF NOT EXISTS` included; `ensure_tables` is removed from `store.py`. A database without `alembic_version` is at "no revision" for Alembic, so `migrate` runs 0001 on it. On an empty database that creates the schema. On a database made by `ensure_tables` it changes nothing, and Alembic records 0001: the database is adopted without a `stamp` step. 0001 has no `downgrade()` (dropping every table is not a way back). *Compared with upstream's* empty 0001 plus `stamp`: upstream keeps its schema in a create script (`create_db.py`), so its baseline must be empty and every fresh database needs the stamp, which `init-warehouse.sh:32-34` does conditionally. We have no create script, so one source and no stamp is simpler. *Risk:* `IF NOT EXISTS` would also adopt a database that differs from the baseline. Staging is compared once by hand (task 4.3); from 0003 on, migrations use plain DDL, so a drifted database fails loudly.

**D6. `scope` becomes 0002 in either order (A6).** `0002_crawl_runs_scope`: `ALTER TABLE crawl_runs ADD COLUMN IF NOT EXISTS scope TEXT` (nullable, no default, no table rewrite), `downgrade()` `ALTER TABLE crawl_runs DROP COLUMN scope`.
- *This change first:* 0001 is e35e4b4's `ensure_tables`; `subtree-crawl` adds 0002 as its task 3.1 instead of the `ALTER` in `ensure_tables`, and its D5 says so. Staging gets 0001 (adopted), later 0002.
- *`subtree-crawl` first:* staging gets the column from `ensure_tables`. This change then takes 0001 as `ensure_tables` without that `ALTER` (the e35e4b4 form), adds 0002 as above, and removes the `ALTER` with the rest of `ensure_tables`; `tests/migrations/before_migrations.sql` (D8) then includes the column, because that is what staging has. On staging, 0001 and 0002 both change nothing and are recorded.
- In both orders the chain and the final schema are the same. The `IF NOT EXISTS` in 0002 is what makes the second order work; it is the last one.

**D7. Downgrades and the dump (A4).** A `downgrade()` is written where it is one obvious statement (0002's `DROP COLUMN`) and tested up-down-up; otherwise there is none, and Alembic refuses the downgrade. It runs from the new image, which has the code: `docker compose run --rm crawler-migrate alembic -c /src/alembic.ini downgrade 0001_baseline`. Before an upgrade that has migrations, the operator takes `pg_dump -Fc` of `crawler-db`; restoring it is the way back from anything else. Whether migrations are pending is shown by `modama-crawler runs` in the new image (D4) before `up`. Rolling back past this change needs nothing: the code before it runs `ensure_tables`, which is a no-op on the adopted schema and ignores `alembic_version`, and ignores `scope` as well.

**D8. The search stack: a one-shot `crawler-migrate` (A2).** Image `search-stack-crawler`, `command: modama-crawler migrate`, `environment: *crawler-env`, `restart: on-failure`, `depends_on: crawler-db: service_healthy`. `crawler` and `crawl-timer` get `depends_on: crawler-migrate: condition: service_completed_successfully`. The staging overlay needs nothing for it: it reads no data. *Alternative:* `sh -c "modama-crawler migrate && exec modama-crawler serve"` in `crawler`: one service less, but it migrates on every restart of `serve`, mixes two logs, and `crawl-timer` would still need its own wait.

**D9. Tests (A5).**
- `conn` (`tests/conftest.py:44-47`) migrates the fresh `pytest-postgresql` database to head with the same function as `migrate`, instead of `ensure_tables`. Every database test then runs on the migrated schema.
- `tests/migrations/before_migrations.sql` holds `ensure_tables`' statements as plain SQL: the schema of the code before this change, which made staging. Plain SQL rather than `pg_dump` output, because a plain dump carries psql meta-commands that psycopg cannot run: the VM's pg_dump 17.11 writes `\restrict <random key>` and `\unrestrict …` lines (tried 2026-11-12).
- `tests/test_migrations.py`, one test per spec scenario: the before-migrations database with a finished run, a dataset with a member, a stored listing and a record, migrated and compared with a fresh one (columns with type, nullability and default; index and constraint definitions from the catalog), rows and datestamps unchanged; a single head; up-down-up for every revision with a `downgrade()`; the refusals (behind, none, ahead: an unknown revision written into `alembic_version`) through the CLI; two `migrate` processes at once; `migrate` while a test holds the crawl lock; a failing second revision and the lock timeout, with a scripts directory under `tmp_path` that holds 0001 and a revision made to fail.
- The search stack's `./runtest.sh e2e` covers the fresh path through `crawler-migrate`.

## Risks / Trade-offs

- [`migrate` waits for a crawl of an hour or more; `crawler` stays down meanwhile] → logged (`waiting for the running crawl to end`); question in the proposal. The operator can stop `crawl-timer` first, which records the crawl as failed.
- [The old image's timer starts its crawl while `migrate` holds the lock] → that crawl exits with status 1 and "another crawl is running on this database", which is misleading, and the timer waits for the next day (the known limitation in `subtree-crawl`'s backlog item). A migration of the kind planned takes seconds.
- [A shipped migration is edited] → nothing in the tests catches it once databases are made by the chain; the README says never, and the review checks it.
- [`restart: on-failure` repeats a refusal (exit 2, database ahead) forever] → the log shows the error each time; the operator acts.
- [A second connection layer] → SQLAlchemy only inside migrations; `store.py` stays on psycopg.
- [The check imports Alembic in every command] → it reads one directory of small files; measured in task 2.3.

## Migration Plan

1. In the VM, on the search stack's test deployment (task 4.2): a database made by the current code, copied, migrated by the new image, compared with a fresh one, read by `runs` and `modama-chain status`; then `./runtest.sh e2e` on a fresh stack.
2. Staging (task 4.3, with @weber): `pg_dump -Fc` of `crawler-db`; restore it into a scratch database in the same container; migrate the scratch database with the new image (`MODAMA_CRAWLER_DB` set to it); compare its schema with a fresh one; then `./upstaging.sh --build`, which runs `crawler-migrate` before `crawler` and `crawl-timer`; then `runs` and `modama-chain status`.
3. Rollback: D7.
