# Proposal

## Why

A schema change today means dropping the crawler's database (`README.md:96`, `store.py:63`). On staging that costs a full crawl, harvest and indexing, about a night, and in production it would cost the datestamps that incremental harvesting relies on. The first schema change is already waiting: `crawl_runs.scope` in the open change `subtree-crawl` (D5). @weber decided on 2026-11-12: "Let's go with alembic, now, to test it properly", after "We will need migration in production, so we may start testing it safely while we are running dev iterations here. [...] Let's follow upstream as far as sensible." The research behind it is `docs/research/schema-migrations.md` (commit 22f891d, branch of worktree `agent-a5e0aa836a67afb2f`): upstream's metadata warehouse adopted Alembic in v1.8.0.

Serves the request of 2026-11-12, to be recorded as R42 (task 1.1):

> - **R42 (must for production, @weber 2026-11-12)** A schema change reaches an existing crawler database in place, without recreating it.
>   - Datasets, extractions, records with their datestamps and the run history are kept, so a change costs no re-crawl, re-harvest or re-indexing (staging: about a night; `field-tests/search-stack-staging-findings.md`).
>   - The change is applied by one explicit step before the crawler's services start, never by two processes at once and never during a crawl.
>   - A crawler refuses a database whose schema is not the one its code expects, and names the step to take.
>   - Example: staging's database, made by commit 3251cad, gains `crawl_runs.scope`, with its 1.45 million records and their datestamps unchanged.
>   - Accepted when a database made by the code before this change migrates in a test and compares equal to a fresh one, and a copy of staging's database migrates before staging does.

## What Changes

- **New command `modama-crawler migrate`**: brings the database's schema to the code's, with Alembic, and exits. Safe to run again, and at once when there is nothing to do, also during a crawl: `INFO schema up to date at 0001_baseline`.
- **The other database commands stop creating tables.** `crawl`, `runs`, `timer` and `serve` check the schema version instead and refuse a database that is behind or ahead of the code, with exit status 2 and the step to take. `records` needs no database and is unchanged. **BREAKING** for developers: a new database needs `migrate` once before `crawl`.
- **The search stack gets a one-shot service `crawler-migrate`** that `crawler` and `crawl-timer` wait for, as `warehouse-init` and `airflow-init` do.
- **Migrations live in `src/modama_crawler/migrations/`**, written with Alembic's operations (`op.add_column`, …) or `op.execute` with SQL text, whichever fits, no SQLAlchemy models, as the warehouse does (A1). Revision 0001 is today's `ensure_tables`, so staging's database migrates in place.
- **New dependencies**, accepted with the decision: `alembic` 1.20.1 (2026-10-22), `SQLAlchemy` 2.1.8 (2026-11-04), `Mako` 1.4.3 (2026-09-22), all MIT, current on PyPI on 2026-11-12. What they need besides (`typing-extensions`, `MarkupSafe`) is installed already, through `psycopg-pool` and `Werkzeug`.

Behaviour towards the user:
- *Operators:* a `migrate` step before the services start, which compose runs on every `up`; before an upgrade whose code brings a new migration, a `pg_dump` of `crawler-db` as the first step (their step for now). When `crawler-migrate` refuses or fails, `up` stops within seconds and names it (`service "crawler-migrate" didn't complete successfully: exit 2`); `docker compose logs crawler-migrate` gives the reason and the step. The OAI-PMH endpoint is down from the stop of `crawler` until the migration has ended, as on any rebuild today. A crawler on a database that does not fit says so: `ERROR the database schema is at 0001_baseline, this crawler needs 0002_crawl_runs_scope: run modama-crawler migrate`. Each case, with its message and step, is in design D10 and goes into the READMEs (requirement 2.4, "The operator stays in control").
- *Developers:* a schema change is a new file in `migrations/versions/` (`alembic revision -m "crawl_runs scope" --rev-id 0002_crawl_runs_scope` from `python/crawler/`), never an edit of `store.py`'s DDL or of a migration that has shipped. Every test database is built by the migrations, so a local `pytest` runs the new one (CI runs no crawler tests yet).
- *Harvesters and searchers:* nothing changes. `serve`'s responses are the same, and `modama-chain` reads the same tables.

## Assumptions

The research's leans, A2 and A4 revised after the review (`review.md`, 2026-11-12). A1 is decided; the others stand with @weber's answers to the questions 140, 141, 142 and 160 (2026-11-12), all with the leans.

- **A1, decided by @weber 2026-11-12: "We should follow the warehouse's practice unless there are specific reasons against it."** The warehouse (v1.10.0, `alembic/versions/0002` to `0005`, `alembic/env.py:46`) has no models (`target_metadata = None`, no autogenerate) and writes each migration with Alembic's operations (`op.add_column`, `op.alter_column`, `op.drop_column` with `sa` types) or `op.execute` with SQL text, whichever fits; so do we. Its revision ids are `NNNN_name`. The rest of this assumption stands as written: one linear chain, in `src/modama_crawler/migrations/` with a small `alembic.ini` in `python/crawler/`. Was: **Plain SQL, no models.** `op.execute` with the DDL as text, `target_metadata = None`, readable revision ids `NNNN_name` (at most 32 characters, Alembic's `version_num`), one linear chain, in `src/modama_crawler/migrations/` with a small `alembic.ini` in `python/crawler/` for Alembic's own command line. *Alternative:* SQLAlchemy models with autogenerate; a second description of the schema next to the SQL that `store.py` runs through psycopg.
- **A2 An explicit step, under a lock, and a refusal.** `modama-crawler migrate` runs in the one-shot service; the other commands only read the version and refuse when it differs from the code's head, in either direction, as Airflow and toolmeta-harvester do. The lock is the existing crawl lock, taken in `env.py` by every way of running Alembic that writes (alembic#633 recommends a lock in `env.py`), so a migration that has something to do waits for a running crawl. `migrate` looks at the version first and takes the lock only when a migration is pending; `alembic current` takes none, and `alembic upgrade --sql` connects to no database (review M2). *Alternatives:* migrate-on-start in every command under the lock (today's path, grown up); `migrate && exec serve` in `crawler` instead of a service; a new lock key `(0x6D6F, 3)` that does not wait for crawls (the research's form); warn and continue on a database that is ahead, which relies on every migration being expand-only.
- **A3 Baseline: 0001 is today's `ensure_tables`,** `IF NOT EXISTS` included. A database without Alembic's `alembic_version` table is at "no revision" for Alembic, so `migrate` runs 0001 on it: on an empty database that creates the schema, on one made by `ensure_tables` it changes nothing, and in both cases Alembic then records 0001. No `stamp` step, one source of the schema. *Alternative:* upstream's form, an empty `0001_baseline` plus `alembic stamp` when `alembic_version` is missing, with the schema kept in a create script (`init-warehouse.sh:32-34` shows the conditional stamp that needs).
- **A4 A `downgrade()` in every revision, as upstream, that undoes the revision or refuses with the step** (revised after the review, M1 and M4; design D7). It undoes the revision where the result leaves nothing that the older code would misread: 0002 deletes the subtree runs, then drops `scope`. Otherwise it refuses: "no downgrade from 0001_baseline: restore the dump taken before the upgrade (README, Upgrade)". The way back from those is the `pg_dump` taken before the upgrade, the operator's step until production backups exist (`/prototypes/search-stack/README.md`, "Backups"). Was: downgrades only where trivial (`DROP COLUMN` for an added column), none otherwise. *Alternatives:* forward-only, every downgrade refuses and the dump is the only way back; the dump as part of `migrate`.
- **A5 Tests on migrated databases.** The `conn` fixture migrates every fresh test database; one test loads the schema the code before this change makes, adds rows, migrates, and compares the result with a fresh database. *Alternative:* pytest-alembic (0.13.2, MIT), one more dependency for checks of a few lines each.
- **A6 `scope` becomes 0002 in either order** with `subtree-crawl` (design D6).

## Not now

- A backup inside `migrate`, and backups of `crawler-db` in general (backlog).
- Migrations that cannot run in a transaction (`CREATE INDEX CONCURRENTLY`), and zero-downtime tools such as pgroll: one writer, and the endpoint is down for the length of the migration, as on any rebuild today.
- A `migrate --check` or a dry-run option: whether the new code brings a migration is shown by `git diff` of `migrations/versions/` without a database, or by `docker compose run --rm --no-deps crawler modama-crawler runs` (without `--no-deps`, compose runs `crawler-migrate` first and migrates: review H2, design D7); Alembic's `--sql` prints the SQL.
- `modama-chain` checking the schema version: it reads an interface and keeps its own checks (`crawler.py:102`).
- An automatic comparison of an adopted database with the baseline: done once by hand for staging (task 4.3).
- A frozen schema per release for the tests: there are no releases yet.

## Questions for @weber

All four are decided (2026-11-12), each with its lean; the other leans above stand.

- **140** When someone runs a migration by hand while the nightly crawl is running, should it wait for the crawl or refuse at once? This only arises by hand. On an upgrade, `./upstaging.sh --build` stops the running crawl before the migration starts (it is recorded as failed, as on any rebuild today), and an `up` with nothing to migrate returns at once. Example: at 02:30, during a crawl that started at 01:00, the operator types `docker compose run --rm crawler-migrate`, and a migration is pending. *Wait:* it prints `INFO waiting for the crawl lock (a crawl or another migration holds it)`, sits there until the crawl ends (perhaps 04:00), then migrates; Ctrl-C ends the wait and changes nothing. *Refuse:* it exits at once with an error such as `ERROR a crawl is running on this database: run migrate after it ends, or stop crawl-timer first`, and the operator comes back later. Lean: wait, since by hand the operator is watching. **Decided by @weber, 2026-11-12: wait.** "yes, go with your lean here! We see how it handles in practice."
- **141** The command's name: `modama-crawler migrate`, or `modama-crawler db migrate` as in Airflow (`airflow db migrate`)? Only the name differs. Example: a developer with a new database types `modama-crawler migrate` before the first `modama-crawler crawl`, and the refusal says `run modama-crawler migrate`; with the other name, both say `modama-crawler db migrate`, which leaves room for more database commands under `db` later (none is planned). Lean: `migrate`. **Decided by @weber, 2026-11-12: `modama-crawler migrate`.** "yes, migrate sounds good"
- **142** Which ships first, `subtree-crawl` or this change? Both work and end with the same schema (design D6). Example: *this change first:* the next `./upstaging.sh --build` records staging's existing tables as the first migration and changes nothing; `subtree-crawl` then adds the column `scope` as the second migration, and its special code in `ensure_tables` is not needed. *`subtree-crawl` first:* `scope` is added by `ensure_tables` at the next start; this change later records both migrations on staging without changing anything. Lean: this change first. **Decided by @weber, 2026-11-12: this change first.** "yes, exactly!" Staging's existing tables become 0001; `scope` becomes 0002 with `subtree-crawl` (task 2.5, first order not taken: a note only).
- **160** Does "follow the warehouse's practice unless there are specific reasons against it" also decide how the first migration is made and how downgrades work? The facts, with the lean for each:
  - *The first migration (A3).* The warehouse keeps its tables in a separate create script, frozen at the start, and its first migration is empty; after creating a new database it marks it with `alembic stamp` as being at that migration, and `init-warehouse.sh` does that only when the mark is missing. We have no create script: our tables are made by `ensure_tables`. The warehouse's way here would mean keeping `ensure_tables` frozen as that script, and every place that makes a database (`migrate`, the test fixture, the README's setup) doing "create the tables, mark them if not marked, then migrate". This proposal instead makes the first migration run `ensure_tables`' statements, so `migrate` alone does it. Example: a developer with an empty database types `modama-crawler migrate` in both ways and gets the same tables; on staging both ways change nothing. The specific reason against the warehouse's way: the extra steps buy nothing here. Lean: as proposed.
  - *Downgrades (A4).* The warehouse writes a downgrade in every migration, its empty first one included (it does nothing). Copied as is, ours would be wrong twice: "do nothing" for our first migration would mark the database as having no tables while all are still there; and simply dropping `scope` would make the older crawler count subtree crawls as full crawls, so the search's freshness date would claim files are in that are not. Following the warehouse as far as sensible gives: a downgrade in every migration, which undoes it where nothing is misread afterwards and otherwise refuses with the step. Example, once `scope` exists: `docker compose run --rm crawler-migrate alembic -c /src/alembic.ini downgrade 0001_baseline` deletes the subtree crawls' rows from the run history, drops `scope` and exits 0; `… downgrade base` refuses, exit 1, ending in `NotImplementedError: no downgrade from 0001_baseline: restore the dump taken before the upgrade (README, Upgrade)`, and nothing changes. *The alternative, forward-only:* the first command refuses too, and the dump taken before the upgrade is the only way back. Lean: the downgrade in every migration, as described.
  - **Decided by @weber, 2026-11-12: both leans.** "Yes, go with your lean, we see how it handles and fix issues as we encounter them." The first migration runs today's create statements; every migration has a `downgrade()` that undoes it safely or refuses with "restore the dump".
