# Proposal

## Why

A stored extraction is reused while the format id, the hand-raised `extractor_version` and the dataset's stamp are the same (`extraction.py:114-121`). The label does not identify the code. A changed reader, a RosettaSciIO upgrade or a reverted experiment leaves the label alone, so the old output stays in the index and in the search. Nothing shows that it is stale. The open change `subtree-crawl` waits for this: its review finding H3 is that an experiment's output outlives the revert (its design D3, "Reverting an experiment").

@weber (question 90, 2026-11-12): "In a typical scenario we will have raised the extractor version anyway. My only concern is that we will raise it to 'high heaven' when running many loops, and we may run into merge conflicts with real world implications when several people raise it in separate git clones. So I'd not call it a version per se, but a hash that is unique for a specific version? Also, it only needs to be valid within one deployment." His answers to the walk-through of seven scenarios, S1 to S7 (2026-11-12, quoted in the design's "Evidence"), make that a requirement: "We should consider what is simple and robust to make sure we re-extract, without collisions and without burden to developers and operators" (S4). He also added (2026-11-12): "that is also sth to monitor in staging and production: Does it work as intended, what actually happens, and why?"

I read "hash" as a rule, not as a single case: the identity is *derived* from what is installed, never typed. I read the "description" of a record as its `dc:description`, not the glossary's Description (a project's README, `/CONTEXT.md`).

## What Changes

- **The extractor's identity is a digest of the installation, computed at the start of every crawl** (design D1). It covers the Python version, the name and version of every installed distribution (RosettaSciIO, numpy, dask and the rest), and the content of every source file of the distributions that provide formats (the crawler, `modama-formats-em`), of those installed from a path or a repository rather than a package index, and of any package imported from outside site-packages, whatever the metadata says (for example a RosettaSciIO checkout on `PYTHONPATH`; review finding 2). Tests and fixtures are left out. No one sets it, so there is nothing to raise and nothing to merge.
- **Settings and numerical noise are not ingredients** (D4). Insignificant numerical noise is left out, whatever its source: a thread count that changes the 12th digit of a number does not re-extract anything. The memory and time limits and the number of processes are left out too: they decide only whether an extraction fails.
- **A failure is never reused** (D9, answer 185). A success is reused while the dataset's files and the identity are unchanged; a failure is tried again by every crawl, whatever caused it. Example: the memory limit is lowered to test, 3,000 DM files fail, the limit is set back, and the next nightly crawl extracts those 3,000 again and nothing else. Today only operating-system and import errors, time-outs and a dead worker are retried (`extraction.py:46`, `:266-302`); a `MemoryError` and every other error stay until the files change.
- **A spot check on real data** (D10, answer 186, review finding 1). Each crawl extracts again a random sample of what it reuses, 20 datasets per format, compares the result with what is stored and reports `spot check (seed 9f2c41d07a3be815): em/dm4 20 of 20 as stored, …`, or names the dataset and the field that differ. This is how something the identity misses becomes visible. A new seed is drawn per crawl and logged, so the sample can be reproduced.
- **One identity for the whole installation, shared by all formats** (D2). A change anywhere in the net extracts every dataset of every format with an extractor again. On staging that is about 50 minutes on 8 processes, almost all of it DM (run 3: DM4 18,294 s and DM3 5,377 s, summed over the processes). This is accepted (S3): "It is more important that the search reflects the desired state than to save CPU."
- **Reuse needs the same identity, compared for equality only** (D3). There is no ordering, so a rollback or an alternate deploy is a change like any other, and two different installations cannot share an identity.
- **BREAKING for format authors: `Format.extractor_version` goes away.** The attribute (`formats/__init__.py:200`) and the four formats that set it (`dm`, `k2is`, `empad`, `merlin`) lose it, and `TEMPLATE.md` stops asking for it. A format that still sets it changes nothing.
- **Monitoring** (D6, the second requirement below). Every crawl reports, per format, how many datasets were extracted again because the identity changed, what changed (for example `rosettasciio 0.15.0 -> 0.16.0`, or `source of modama_formats_em.dm changed`) and how many of their extraction results actually changed. The results are compared, not the records, so a fixed typo in the description template shows as `0 results changed` (review finding 4). The run keeps these numbers, and `runs` and `modama-chain status` show them. The report also says how many failures were tried again and how many now succeed (D9), and the spot check's outcome (D10). `modama-chain trace` names the identity that produced a record's description and whether it is the current one. The `records` summary names the identity it extracted with.
- **After an upgrade, the operator is told what the next crawl will do** (D7). `modama-crawler runs` prints a note when stored datasets carry an identity other than the installed one (also after an experiment on one path that a later crawl elsewhere did not undo; review finding 7), with what changed, how many datasets per format will be extracted again and roughly how long it will take. `prototypes/search-stack/upstaging.sh` prints this note, and the command to start the crawl now, at its end. The next scheduled crawl does the re-extraction by itself.
- **The pytest plugin records each fixture's extraction next to its recognition result** (D5, decision T4 extended), so a dependency upgrade that changes the output fails in CI with a diff before it reaches a deployment.
- **Schema:** `datasets.extractor_version` is renamed to `extractor_identity`, `datasets.extract_retry` goes away (D9 makes it decide nothing), and `crawl_runs` gets the identity, its ingredients, the per-format re-extraction counts and the spot check's outcome. These are the next migration of the change `schema-migrations` (D8), on which this change builds.
- **Build hygiene:** `.dockerignore` files for the `em` and `chain` build contexts keep the host's stale bytecode out of the image (review finding 5).

Behaviour towards the user. *Format authors* no longer raise a number. *Operators* get one more report line per format that was extracted again, one per format with failures tried again, a spot-check line, more fields in `runs`, `modama-chain status` and `trace`, a note from `runs` and `upstaging.sh` after an upgrade, and one more summary line from `records`. A failure no longer stays until its files change: a file that fails every night is extracted every night, and a setting that fixes a failure brings its datasets back by the next crawl. The first crawl after this change extracts everything once, because no stored label equals a digest. *A harvester* sees new datestamps after a code or dependency change only on the records whose content changed, and none after a refactoring that changes no output; also on a failure that now succeeds, and on a spot-checked dataset whose new result differs. *A searcher* then sees the deployed code's output everywhere, after the incremental harvest and indexing.

Out of scope (design, "Not now"): the same identity for recognition (the rule set), which is a question below; a self-test on the fixtures at the start of a crawl in a deployment, also a question; an identity per format or per collection; a forced re-extraction without a code change; the search stack's move to `deploy/` (`upprod.sh` does not start the crawler yet); a workaround for partial DM dates (answer 187); a lock file for the image (review finding 8).

Serves: the new R44 and R45 below; R10 (a re-crawl only does work for what changed: "changed" now includes the code); R14 (developing a format is easy: no number to raise); R23; requirements-pipeline 2.4, "The operator stays in control"; review finding H3 of `subtree-crawl`; T-D in `design/testing.md` (telling a change in the system apart from a change in the data).

### Proposed requirement wording

`design/requirements.md`, next to R41 to R43 of the open changes (written by task 1.1 once accepted):

> - **R44 (must, @weber 2026-11-12)** A stored extraction is redone when the code that produced it may have changed, without anyone raising a number ("I'd not call it a version per se, but a hash that is unique for a specific version"). The extractor's identity is derived from the installation, not typed: a digest over a wide net of what may change an extractor's output: the crawler's and the format packages' source, and the names and versions of the installed distributions (RosettaSciIO and its dependencies), with the source of those installed from a path or a repository. "We can't always know what may alter behavior, e.g. RosettaSciIO development"; "rather re-extract than missing sth important." It is valid within one deployment and compared for equality only, so separate clones, rollbacks and upgrades cannot collide. An influence whose only effect is insignificant numerical noise is not an ingredient ("let's not be too pedantic about the 12th significant digit"), nor are the settings that decide only whether an extraction fails, such as the memory and time limits: a failure is never reused, every crawl tries it again whatever its cause, so a setting that fixes a failure brings back what failed without extracting everything again (185). Re-extracting more than strictly needed is accepted ("It is more important that the search reflects the desired state than to save CPU"); the effort goes into cheap extraction. Upgrading a deployment with its start script (`./upstaging.sh`, later `./upprod.sh`) brings everything up to date with the next crawl, or tells the operator what to run (requirements-pipeline 2.4). Evidence: the walk-through of 2026-11-12, S1 to S7 (change `extractor-identity`, design, "Evidence").
> - **R45 (must, @weber 2026-11-12)** Whether R44 works is visible in staging and production: "Does it work as intended, what actually happens, and why?" Every crawl reports per format how many extractions ran again because the identity changed, which ingredient changed, and how many of those extraction results changed, so that a re-extraction that changed nothing is visible as such. The run keeps these numbers (`runs`, `modama-chain status`), and for one item `modama-chain trace` says which identity produced its record's description. So that what the identity misses becomes visible too, each crawl extracts again a random sample of what it reuses, across the formats, and reports each dataset whose result differs from the stored one ("a random sample of different formats and files so that over time we hit the weird edge cases we are missing", 186). Checked in practice on the staging crawls (`design/field-tests/search-stack-staging-findings.md`).

## Questions

In the examples the search stack runs on staging, crawled nightly at 19:00 UTC.

- **Is one identity for the whole installation right, even when the change has nothing to do with extraction?** The chain tool `modama-chain` is installed in the same image from a local path, so its source is in the net. Fixing a typo in its `status` output, rebuilding and redeploying makes the next nightly crawl extract every DM, K2IS, EMPAD and Merlin file again: about 50 minutes on staging, with no record changed and so nothing harvested. A pytest upgrade in the image does the same. *Lean, one identity:* simple, and it also catches imports nobody declared. *Alternative:* only the distributions that the format packages require, followed through their dependencies. This leaves the chain tool and pytest out, but misses a module an extractor imports without declaring it.
- **Should a crawl in the deployment also run a self-test on the fixtures?** (your S6 idea, and T-D's "frozen sample") Say the image is rebuilt a week after CI ran, and pip picks a newer numpy that CI never saw. The identity changes and the night's crawl extracts everything again, as it should. With a self-test, the crawl would first extract the 12 representative fixtures of the `em` collection (a few seconds) and compare them with the recorded results that D5 adds. It would report `self-test: em/dm4 cl_image_dm4: summary differs` before the 50 minutes, or `self-test: 12 fixtures as recorded`. *Lean:* not in this change. The recorded results in CI come first (D5), and the start-up check follows T-D as a change of its own, because the fixtures are not part of the installed package data today (`pyproject.toml`, package-data; the image installs editable for that reason).
- **Should recognition follow the same identity?** The gap is the same there. You change K2IS's rule for which `.bin` files belong to a `.gtg` and forget to raise the format's `version`. The next crawl takes every unchanged directory over (`selection.py:138`, "the extractor versions are left out") and keeps the old grouping until the files change. With the identity in the rule set, every code change also means a full recognition: on staging the walk with content sniffing, about 17 minutes in run 3, on top of the extraction. *Lean:* yes, but in a small change of its own after this one, which then also drops the format's `version`.
- **After an upgrade, should the next crawl start at once?** You pull and run `./upstaging.sh --build` at 10:00 with RosettaSciIO going from 0.15.0 to 0.16.0. *Lean, as today:* the script prints `the next crawl extracts about 177,000 datasets again (rosettasciio 0.15.0 -> 0.16.0), about 50 minutes; it starts at 19:00 UTC, or now with: docker compose ... run --rm crawl-timer modama-crawler crawl`. You choose. *Alternative:* the script starts the crawl. That would put NFS load into business hours (requirements-pipeline 2.11, "crawl outside business hours"), and a harvest of the changed records after it.

### Answers by @weber, 2026-11-12 (179 to 182 in the conversation, on the open-items page)

- **179, one identity for the whole installation:** "Yes, simple sounds good."
- **180, a self-test in the deployment:** "We keep that for later. 179 sounds robust enough that we just need to watch out for anything in the wild that is missed from the fingerprint. Maybe one can also do a bit of independent review here, what should go into such a fingerprint, and what shouldn't, i.e. what can influence results that are not changes of the file system we crawl? We already covered many in 179, but to close 180 we need to be sure enough we are not missing anything we may hit in staging or production." So: no self-test now; an independent review checks the ingredients for completeness: everything outside the crawled files that can change an extraction's result. Done in `review.md` (33 influences, 8 findings); its outcomes are folded in below and in the design.
- **181, recognition under the same identity:** "yes sounds reasonable": as a small change of its own (Not now).
- **182, the crawl after an upgrade:** "We do inform the operator about that, and have an option to trigger it by hand before, if desired?" So: no automatic start; the upgrade script tells the operator what will be re-extracted and how long it takes, and offers a way to start the crawl at once by hand (the printed command, or an option of the script), so the operator can choose before the nightly run.

### Answers by @weber after the review, 2026-11-12 (185 to 187; `review.md`)

The answers are quoted in full in the design's "Evidence".

- **Numerical noise:** "let's not be too pedantic about the 12th significant digit" (thread counts were "an example for a small numerical difference that is insignificant in practice"). So, as a rule: an influence whose only effect is insignificant numerical noise is not an ingredient (D4).
- **185, failures:** a setting such as the memory limit "should not influence 'good' results", and "the normal regular crawl should naturally find and update things that were missed in a previous run because of a failure". So: a failure is never reused, whatever its cause; limits and settings are not ingredients; the report shows the failures tried again and how many now succeed (D9). Cost: a file that fails every night is extracted every night, about a minute on 8 processes for run 3's 2,871 failures; a time-out costs its 60 s each time.
- **186, the spot check:** "yes sounds perfect! Ideally a random sample of different formats and files so that over time we hit the weird edge cases we are missing". So: 20 datasets per format, drawn anew each crawl from a logged seed; a difference is a finding to look at, not a reason to extract everything again (D10).
- **187, partial dates:** "Watch for now and keep as a finding. Do such date tags exist in the wild? Only if a real world writer actually produces such files it is a finding reportable upstream." So: no workaround; the spot check and the staging check watch for it, and task 6.3 finds out whether staging's DM files have such tags.

### Open after the review

**Decided by @weber, 2026-11-12 (question 192 in the conversation): "yes, replace, please!"** The new success replaces the stored result; the record gets a new datestamp and is harvested; both values stay in the run; a new failure never replaces a stored success. The design's D10 and the spec scenario "A spot-check difference is reported, not spread" follow this when the change is applied.

- **What happens to the record of a dataset whose spot check differs?** Say the spot check re-extracts `adhoc/x/a.dm4` and its date now reads `2021-05-12` instead of the stored `2021-05-11`. *Lean:* the new result replaces the stored one, because it is what the installed code gives ("the search reflects the desired state", S3); the record gets a new datestamp and is harvested, and the old and new value stay in the run for whoever looks into it. A new failure (say a time-out under load) does not replace a stored success. *Against:* a value that changes on every extraction, such as a date completed from the day of the crawl, then changes the record each time its dataset is sampled. *Alternative:* keep the stored result and only report; the record then stays stale until the next new identity.

### Modified Capabilities
- `extraction` (added by the open change `em-formats-and-extraction`, which is archived first): reuse follows the derived identity instead of the version label, and a failure is never reused; taken-over directories still have their extractions checked; the identity's ingredients, and what is left out; the report of re-extraction and its cause, and of failures tried again; the spot check.

## Impact

- Crawler: a new module `identity.py` (ingredients, digest, what changed between two); `extraction.py` (reuse by identity, failures always tried again, re-extraction counts per format and cause, results compared, the spot check); `formats/__init__.py` (`Extraction.version` becomes `identity`, `Extraction.retry` and `Format.extractor_version` removed); `store.py` (the renamed and dropped columns, the run's columns); `cli.py` (identity per crawl, the report, `runs`' note, `records`' summary); `testing.py` (recorded extractions); `TEMPLATE.md`, README, BACKLOG.
- Depends on `schema-migrations` (being built: Alembic, `modama-crawler migrate`): the storage change is its next migration.
- `modama-formats-em`: the four `extractor_version` lines and `testing.py:99`; recorded extraction results per fixture.
