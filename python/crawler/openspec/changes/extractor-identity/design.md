# Design

## Context

What the code does today (`crawler` at 50533f9):

- **Reuse.** A stored extraction is reused while `(extractor, version, stamp)` equals `(format id, Format.extractor_version, dataset stamp)` and the failure, if any, was not an environment failure (`extraction.py:114-121`). New results are stored under the same triple (`:135-140`), in `datasets.extractor`, `datasets.extractor_version` (`store.py:89`). `Extraction.version` holds the label (`formats/__init__.py:52`). The label is a string raised by hand per format: `dm` `"4"` (`modama_formats_em/dm/__init__.py:76`), `k2is` `"3"` (`k2is/__init__.py:41`), `empad` `"2"`, `merlin` `"1"`, default `"1"` (`formats/__init__.py:200`).
- **Failures.** A failure is reused like a success unless it counts as one of the environment: an `OSError` or `ImportError` (`ENVIRONMENT`, `extraction.py:46`), a time-out or a dead worker process (`:266-302`). These set `retry`, stored in `datasets.extract_retry`. A `MemoryError` under the worker's memory limit, and every other exception, is reused until the dataset's files change (review finding 3). Run 3 had 2,871 failures: 2,036 `.dmw` and 33 `.gtg` files without an image (F15), 604 RGBA images (F14), 104 Merlin headers and 94 other DM errors. F14 and F15 have fixes under review (branches `dm-handle`, `dm-containers`).
- **Taken-over datasets are still checked.** A dataset taken over with its unchanged directory carries its stored extraction, and `extract()` compares it like any other (`extraction.py:114`). So a new identity re-extracts without recognising again: the walk stays a take-over.
- **The rule set** (`selection.fingerprint`, `selection.py:138-165`) covers the format `version`s, the MIME XML, the selection, the exclusions and the versions of the distributions that provide formats. It leaves the extractor versions out on purpose, and it sees no source. The distribution versions are static (`0.0.1.dev0`), and the search stack's image installs the crawler, `modama-formats-em` and `search-chain` editable (`prototypes/search-stack/crawler.Dockerfile`). So a code change without a bump changes neither the rule set nor the extractor's label.
- **Code is shared across formats.** K2IS reads its `.gtg` with DM's reader (`k2is/__init__.py:15`, `from ..dm import parsed`). DM3 and DM4 are one class. RosettaSciIO is pinned exactly (`modama-formats-em/pyproject.toml`), but its own dependencies (numpy, dask, …) are not.
- **Records and datestamps.** Records are rebuilt from the datasets on every crawl. A record's datestamp moves only when its metadata differs (`store.py:470`). The harvest is incremental, and the DAG indexes only what it harvested (`subtree-crawl` design, Context, "Harvest").
- **The timer** starts every crawl as a process of its own (`cli.py:391`), so anything computed at a crawl's start sees the code installed at that time.
- **Staging, run 3** (`design/field-tests/search-stack-staging-findings.md`, Run 3): 177,166 extractions in about 52 minutes on 8 processes. Summed over the processes: DM4 18,294 s, DM3 5,377 s (23,671 s together, about 50 minutes on 8 processes), Merlin 88 s, EMPAD 10 s. The walk took about 17 minutes, the whole crawl 1 h 17 min, the harvest of 1.45 million changed records 5 h 14 min (F16). For about 170,000 DM records, `subtree-crawl` estimates about 40 minutes of harvest and 45 minutes to two hours of indexing at F16's rates (its Non-Goals).
- **A probe in the VM** (2026-11-12, `importlib.metadata` and `hashlib` only, the scratchpad script `identity_probe.py`): 63 distributions, 39 source files of the crawler, `modama-formats-em` and `search-chain` outside `tests/`, about 250 ms, and the same digest on two runs. It found one pitfall. An editable install leaves a stale `*.egg-info` in the source tree, and `importlib.metadata.distributions()` lists it as a second distribution of the same name, without `direct_url.json`. Only the first one found counts, as `importlib.metadata.distribution(name)` resolves it.

## Goals / Non-Goals

**Goals:** the stored extractions always come from the installed code, or are redone by the next crawl. No developer or operator types an identity. Every crawl shows what it redid, why, and with what effect, and checks a sample of what it reused. A failure never outlives the crawl that met it: the next crawl tries again.

**Non-Goals:** saving re-extractions that turn out to change nothing (S3). Making extraction cheaper is the other side of S3, and it is separate work (F14, `cpu-budget`). Identities that are comparable across deployments.

## Decisions

**D1. The identity is a digest of the installation, a wide net (S6).** The crawl computes it once at its start, in the main process, before the workers are spawned. Workers are spawned from the same interpreter and `sys.path`, so they import the same files. The ingredients, as a JSON object with sorted keys, hashed with SHA-256:

| Ingredient | Catches | Example |
|---|---|---|
| `python`: implementation and version (`cpython 3.14.0`) | a base-image upgrade that changes float formatting or a standard-library parser | `python:3.14-slim-trixie` rebuilt with 3.14.1 |
| `distributions`: name → version of every installed distribution, the first one found per name (Context, the probe) | an upgraded reader or one of its dependencies (S4) | `rosettasciio 0.15.0 -> 0.16.0`; numpy picked newer at an image build |
| `source`: path → SHA-256 of every file of three kinds of import package: (a) those of the distributions that provide formats (entry-point group `modama.formats`: the crawler itself and `modama-formats-em`); (b) those of the distributions installed from a path, an archive or a repository (PEP 610: `direct_url.json` present); (c) every top-level import package that `importlib.util.find_spec` finds outside the site-packages and standard-library directories, whatever the metadata says. Paths are relative to the package's parent directory, and `tests/`, `__pycache__` and `*.pyc` are left out. | code moving without a version (S2): our static `0.0.1.dev0`, an editable checkout, RosettaSciIO installed from a git clone during its development; (c) code imported from somewhere the metadata does not tell (review finding 2) | `modama_formats_em/dm/__init__.py` edited; a K2IS change hidden in DM's reader; `PYTHONPATH=~/rosettasciio` with a changed reader, while `importlib.metadata` still says `rosettasciio 0.15.0` |

*Code imported from outside the net (c), review finding 2.* The review ran three ways in which a crawl imports code that (a) and (b) do not hash: a package on `PYTHONPATH` that shadows an installed one, an editable install of a non-setuptools backend that is only a `.pth` file (no import name mapped to it), and a stale `*.egg-info` in the working directory that is found before the real metadata (no `direct_url.json`). In all three the code is imported from outside site-packages, so (c) catches them with one rule. The names to look up are the top-level names of every installed distribution (`packages_distributions()`) and the modules on every `sys.path` entry outside site-packages and the standard library (`pkgutil.iter_modules`): that covers `PYTHONPATH`, the working directory of `python -m` and the directories a `.pth` file adds. A distribution of kind (b) for which no file is found gives a warning in the crawl's report and log, for example `warning: rosettasciio is installed from a path, but none of its source was found; a change to it does not change the identity`. "The first one found" (Context, the probe) then matters for the versions only.

*Why so wide.* An extractor's output depends on code that nobody can list by hand: K2IS imports DM's reader, the DM reader imports RosettaSciIO, and RosettaSciIO imports numpy and dask. Following the imports would be fragile (they are lazy, "in the worker only", `dm/__init__.py:27`). Listing the requirements misses an undeclared import. The whole installation is the simplest net that misses nothing that is installed. *What it does not catch:* system libraries outside Python (libc, the kernel's NFS client), environment variables (D4), data files that a reader loads from outside its package, stale bytecode (review finding 5: a same-size edit within the same second runs the old `.pyc`; task 6.1 keeps the host's `__pycache__` out of the image) and the date of the crawl (review row 20, D10). The spot check (D10) is what looks for their effect on real data. *Why the files and not RECORD:* an editable install's RECORD lists only the `.pth` file, not the source. Following the import packages (`packages_distributions()`, which `selection.py` already uses, plus `importlib.util.find_spec`) works for editable and regular installs alike, and hashes the code that is actually imported, wherever the checkout is. *Cost:* about 250 ms per crawl (the probe), and the ingredients take about 5 kB as JSON.

The identity's short form, for people, is its first 12 hexadecimal digits (`6d881430e7c8`). The store keeps the full digest.

*Alternatives:* (a) the hand-raised label: the problem (question 90, S1, S2). (b) An identity per format, from the format's module and the modules it imports: K2IS → DM shows that this misses changes, and the lazy imports make it guesswork. (c) A git commit: there is no git in the image, it does not cover dependencies, and an uncommitted change in a clone has the same commit.

**D2. One identity for all formats.** Every dataset of a format with an extractor is compared against the same identity. A change anywhere in the net extracts all of them again. Today one collection has extractors, so one identity per collection would differ only in leaving out the crawler's own source, which the extractors run in (`_storable` and `Extracted` are in the crawler). *Cost, staging:* all of run 3's 177,166 extractions, about 52 minutes on 8 processes, 50 of them for DM, whatever changed. A change that leaves every output as it was then moves no datestamp, so nothing is harvested or indexed (D6 shows that this happened). *Alternative:* the requirements closure of each format's distribution. This is a question in the proposal, with the chain-tool example.

**D3. Equality only, no ordering, no collisions.** A stored extraction is reused when its stored identity equals the running crawl's identity, and is redone otherwise. "Newer" and "older" are never compared, so a rollback (S5) or a deployment that alternates between two clones (S2) is a change like any other. Two installations that differ in any ingredient get different digests. A SHA-256 collision is not a practical concern. Two installations with the same ingredients get the same digest and rightly share their extractions: two clones at the same commit with the same dependencies. The identity is valid within one deployment (question 90). It is not meant to compare deployments, because their dependencies differ.

**D4. What does not change a good result is not an ingredient.** Two kinds of influence are left out on purpose:
- *Insignificant numerical noise, whatever its source* (@weber, Evidence: "let's not be too pedantic about the 12th significant digit"). Examples: thread counts (`OPENBLAS_NUM_THREADS`, `OMP_NUM_THREADS` and `MKL_NUM_THREADS`, which the change `cpu-budget` sets to 1), a BLAS build, the CPU's SIMD features. A value printed as `3.0001000000000002` on one machine and `3.0001` on another is noise. The review found no such noise with today's extractors, which read headers and do no linear algebra (review, C). If the spot check (D10) ever reports a difference only in the last digits of a number, it is noted, not fixed with an ingredient. A library upgrade that changes a number by more is not noise: under NumPy 2, `np.float32(3000.1) / 1e3` prints `3.0001001358032227` rather than `3.00010009765625` (review, C), and the library's version catches it.
- *The settings that decide only whether an extraction fails, or how fast it runs*: the memory limit (`MODAMA_CRAWLER_EXTRACT_MEMORY`, `extraction.py:38`), the time limit (`:31`), the number of extraction processes. They do not change a good result, only whether there is one, and every failure is tried again on the next crawl (D9). So a setting that fixes a failure brings back what failed, without extracting everything again.

`cpu-budget` and this change touch `cli.py` near each other and are otherwise independent. The identity is computed without importing numpy, so it does not depend on the order in which `cpu-budget` sets its variables.

**D5. The self-test (S6): recorded extraction results in the plugin now, a check at crawl start later.** There are three options:
- *(a) As part of the identity*, a fingerprint of the fixtures' outputs. It adds nothing. If the code and the dependencies are unchanged, the outputs are too, so a different output always comes with a different digest. It cannot replace the digest either: the fixtures cover a few files, and a change that matters only for real files (a tag that only ER-C's microscopes write) would be missed. S3 and S6 rule that out ("rather re-extract than missing sth important").
- *(b) In the pytest plugin (lean, this change).* The plugin records each fixture's extraction (summary, subjects, values, or the error's type) next to the recognition result in `tests/expected/<name>.json`, and compares and regenerates it as decision T4 does for recognition. The fixtures and `fixtures.toml` stay as they are, and the hand-written checks in `test_extract.py` stay too. A RosettaSciIO upgrade in `pyproject.toml` then fails CI with the changed fields, at the developer's desk before any deployment (S4). It also gives (c) something to compare with.
- *(c) At crawl start in the deployment*, the T-D idea (`design/testing.md`: an expectation file "evaluated … to detect system changes", decision of 2026-10-16). The crawl extracts the representative fixtures before the tree and reports `self-test: 12 fixtures as recorded`, or names the fixture and the field that differ. A difference means that the deployment's environment is not the one in which the expectations were recorded with the code. It is a check that flags, not part of the identity. It needs the fixtures in the deployment: today only because the image installs editable, since they are not package data. This is a question in the proposal, and "Not now" here. It is also what would catch the consequence of the missing lock file (review finding 8): the image has no lock or constraints file, and its `pip install` layer is rebuilt on every crawler change, so a deployment can run newer numpy, dask or pint than CI tested. The identity catches that, but D6's "why" then lists several distributions next to the source change, and (b)'s recorded results do not vouch for what was deployed. The spot check (D10) is not the same: it compares with what is stored in the deployment, not with what CI recorded.

**D6. Monitoring: the report says what was redone, why, and with what effect (R45).** For each dataset, `extract()` already decides between "reuse" and "run". "Run" gets a reason: *new or changed files* (no stored extraction, or another stamp), *earlier failure* (D9), *forced* (a subtree crawl), or *new identity* (only the identity differs). For *new identity*, the crawl groups by format and by the stored identity, and names what changed between that identity's ingredients and the current ones:
- a distribution's version, added or removed: `rosettasciio 0.15.0 -> 0.16.0`;
- source files, grouped by module: `source of modama_formats_em.dm changed`;
- the Python version;
- an identity whose ingredients are not stored (labels from before this change, `"4"`): `earlier identity "4", ingredients unknown`.

More than five differences are cut to five and `and N more` (R36: summarise, don't crowd).

*What changed is counted on the results, not on the records* (review finding 4). For each dataset extracted again, `extract()` holds the stored result (`before`) and the new one, and compares the two in their stored form (summary, subjects, values, or the error). Counting records instead would mix two causes: records are rebuilt on every crawl (`store.py:455`), and `records.py` and `render.py` are in the same net as the extractors. Example: a typo fixed in `records.py`'s description template gives every record a new datestamp, but no extractor result changes, so the line says `0 results changed` and the "why" stays right. The store needs no change for this. The report gets one line per format with such datasets:

```
em/dm4: 150,000 extracted again for a new identity (rosettasciio 0.15.0 -> 0.16.0), 1,200 results changed
em/dm4: 2,069 tried again after a failure, 640 now succeed
```

The second line is D9's. The counts in these examples are round numbers made up for illustration, not measurements. A line with `0 results changed` is a refactoring made visible (S3). After a deployment that changes no output, a count above 0 points at an influence that varies between runs, such as a date completed from the day of the crawl (D10). Where it shows:
- **the crawl's report and log**: the lines above, plus the run's identity in short form, and the spot check's line (D10);
- **`runs`**: the run's line ends with `identity 6d881430e7c8` and, when there were any, `extracted again: em/dm4 150,000 (1,200 results changed)`;
- **`modama-chain status`**: the same on its crawl line;
- **`modama-chain trace`**: the crawler line names the dataset's extractor and identity, and whether that is the last finished crawl's (spec `chain-trace`). This answers "why does this record say what it says" for one item;
- **`records`**: its summary names the identity. `records` extracts afresh and has no database, so a note per record would always say the same thing (records-cli, "Routine datasets are counted, not commented").

The self-test's outcome joins the report if (c) is adopted. Where it is checked in practice: the next staging crawls, recorded in the findings file (task 6.2).

**D7. A deployment upgrade (S7): the next crawl does it, and the operator is told.** `./upstaging.sh --build` after `git pull` recreates `crawler` and `crawl-timer` from the new image. Nothing else is needed for extraction. The timer's next crawl (19:00 UTC, or at once if the last finished crawl is more than a day old) computes the new identity and extracts again what it covers (D3). The operator learns what will happen before it happens:
- `modama-crawler runs` prints a note on stderr when any stored dataset carries an identity other than the installed one (spec `crawl-runs`). It counts the stored datasets per format and per stored identity that differ from the installed one (one `GROUP BY` on `datasets`), names what changed for each such identity (D6's wording), and estimates the time as their stored `extract_seconds`, summed and divided by the number of extraction processes. For example: `note: extraction identity 6d881430e7c8 is installed; stored under 77b1e2d4a0c9 (rosettasciio 0.15.0 -> 0.16.0): the next crawl extracts again em/dm4 150,000, em/dm3 27,000 datasets, about 50 minutes on 8 processes`. The counts here are made up; the 50 minutes is run 3's DM time. *Why the stored datasets and not the last crawl* (review finding 7): after an experiment with `crawl --path` under `h1` on one path, a revert, and a subtree crawl under `h0` on another path, the last finished crawl has `h0` like the installation, but the first path's datasets still carry `h1`, and the next nightly crawl extracts them again. The note says so.
- `upstaging.sh` runs `modama-crawler runs` in the `crawler` container after `up --wait`. It prints its note and, when there is one, the command to start the crawl now (`docker compose -p search-staging … run --rm crawl-timer modama-crawler crawl`, the one-off container of `subtree-crawl` D6). Starting it is the operator's choice (requirements-pipeline 2.4: "what it chose, and why, is visible; overriding it is easy"). Whether the script should start it by itself is a question in the proposal.
- *Downstream:* the re-extraction rewrites the datasets. The records are rebuilt, and only those whose metadata differs get a new datestamp (`store.py:470`). The harvest the crawl triggers is incremental, so the warehouse and the index see only those records. After a refactoring, nothing. After a RosettaSciIO upgrade that changes a number in every DM description, about 170,000 records: about 40 minutes of harvest and 45 minutes to two hours of indexing (Context).
- *Production:* `deploy/upprod.sh` does not start the search stack yet. When the stack moves to `deploy/`, `upprod.sh` gets the same call to `runs` (Not now). The behaviour of the crawl itself is the same there.

**D8. Storage: the next migration of `schema-migrations`.** This change builds on the change `schema-migrations` (Alembic, `modama-crawler migrate`, being built), and its storage change is the next migration there: after 0001, and after `subtree-crawl`'s 0002 only if that ships first. The migration:
- renames `datasets.extractor_version` to `extractor_identity`. The values stay, and no stored label equals a digest, so the first crawl extracts everything once (Migration Plan). The rename keeps the column's name honest for `search-chain`, which reads the crawler's tables as an interface;
- drops `datasets.extract_retry`: with D9, every failure is tried again, so the flag decides nothing;
- adds `crawl_runs.identity TEXT` (the digest) and `crawl_runs.identity_ingredients JSONB` (D1's object, about 5 kB per run). D6 and D7 look up the ingredients of a stored identity in the newest run that has that digest;
- adds `crawl_runs.reextracted JSONB`: per format, the datasets extracted again for a new identity, how many of their results changed, and the differences, as reported (D6);
- adds `crawl_runs.spot_check JSONB`: the seed, per format the datasets checked and how many are as stored, and each difference with the dataset, the field and the stored and new value, cut as in the report (D10).

**D9. A failure is never reused (185).** A stored success is reused while the dataset is recognised with the same extractor, its stamp is unchanged and its identity equals the crawl's. A stored failure is never reused: every crawl runs the extractor on it again, whatever the cause (the file's content, a `MemoryError` under the memory limit, a time-out, a dead worker process, a missing module). This replaces the classification in `ENVIRONMENT` (`extraction.py:46`) and the `retry` flag (`:266-302`). With no classification, none can be wrong: the review ran a 2×2-pixel DM4 fixture under a 400 MB limit, which failed with `MemoryError()` and was kept as the file's own failure (finding 3).

*Example.* To test, the operator lowers `MODAMA_CRAWLER_EXTRACT_MEMORY` to 400 MB. That night, 3,000 DM files fail with `MemoryError`. The limit is set back. The next nightly crawl tries those 3,000 again, and they succeed; the other datasets are reused. Nothing is extracted again in full, because limits are not ingredients (D4): "Only if necessary it should update everything."

*The report* says per format how many failures were tried again and how many of them now succeed: `em/dm4: 2,069 tried again after a failure, 640 now succeed` (made-up counts). A file that fails every night shows up in every night's report and in the warnings with its error, so it stays visible.

*Cost.* Every failure is extracted again every night. In run 3 an extraction took about 0.13 s of a process on average (23,769 s summed over 177,166), so run 3's 2,871 failures would cost about 6 minutes summed, under a minute on 8 processes. Most of them have fixes under review (F14, F15). A time-out costs its full 60 s each time: 100 files that time out every night cost 100 minutes summed, about 13 minutes on 8 processes. Run 3 had none. A file that times out under load one night and succeeds the next gets a basic description, then its full one, and is harvested twice (review row 29). That is accepted.

*Taken-over directories.* Their datasets' stored extractions are checked like any other (Context), so a failed dataset in an unchanged directory is extracted again. The requirement "Unchanged directories are not recognised or extracted again" says so now.

*Alternatives:* (a) add `MemoryError` to `ENVIRONMENT` (the review's fix): smaller, but the next cause nobody listed is kept again. (b) Retry failures only when a setting changed: that needs the settings as a second identity, more machinery for a saving of about a minute a night.

**D10. A spot check on real data (186, review finding 1).** What the identity misses re-extracts nothing, so D6 can only show the identity working, never where it falls short. Example: a future reader loads a calibration table from outside its package, and the table is updated in the image; the identity stays the same, every crawl reuses the old results, and `runs`, `status` and `trace` all say "current". The spot check looks for such cases on the files ER-C actually has.

*What it does.* After deciding what to reuse, each crawl draws a random sample of the datasets whose stored success it reuses: 20 per format with an extractor, or all of them when a format has fewer. It extracts them again in the same process pool with the same limits, and compares each new result with the stored one in stored form, as D6 does. The spot check's extractions are counted on its own line, not as run or reused. The sample size is an argument of `extract()`, 20 by default; it is not a setting for the operator. A crawl that reuses nothing (the first after a new identity, or a subtree crawl, which reuses nothing under its path) reports `spot check: nothing reused`.

*Why 20 per format.* The cost: 5 formats with extractors give 100 extractions, about 13 s summed at run 3's average, about 2 s on 8 processes, plus cold reads on NFS (measured on staging, task 6.2). The chance to see a problem: a missed change that alters 10 % of a format's results shows in the first night with a probability of about 88 % (1 − 0.9²⁰); one that alters 1 % shows within a week with about 75 % (1 − 0.99¹⁴⁰). Per format, so that the small formats are not drowned by DM ("a random sample of different formats and files"). Over many crawls the samples, drawn anew each night, cover more of the tree: a format with 500 datasets is about 9 in 10 checked after two months, while for 150,000 DM4 datasets a year of nightly crawls checks about 7,100 different files, under 5 %. Rare edge cases in a large format are therefore found slowly; making the sample larger is cheap if staging shows that it is needed.

*The seed.* Each crawl takes a new 64-bit seed from the operating system (`secrets.randbits(64)`) and names it in the report, the log and the run (`crawl_runs.spot_check`). The sample is drawn with `random.Random(seed)` from each format's reused datasets sorted by anchor, formats in the order of their ids, so the same seed over the same stored datasets gives the same sample (a test). To reproduce one difference, the dataset named is enough: `modama-crawler records --verbose <its path>` extracts it afresh with the installed code, and `modama-chain trace` shows what is stored. There is no option to set the seed (Not now).

*The report.* One line, for example `spot check (seed 9f2c41d07a3be815): em/dm4 20 of 20 as stored, em/dm3 20 of 20, em/empad 20 of 20, em/merlin 20 of 20, em/k2is 3 of 3`. With a difference: `spot check (seed …): em/dm4 19 of 20 as stored; differs: adhoc/x/a.dm4 (values: General.date)`, and a warning in the log with the stored and the new value. More than five differences per format are cut to five and `and N more` (R36). The run keeps the line's content, and `runs` shows `spot check: 1 differs` on the run's line when there is a difference. The crawl's exit status does not change.

*What happens to the record.* A difference is a finding to look at, not a reason to extract anything else again: the rest of the format is reused as decided. For the dataset itself (lean): a new success replaces the stored result, because it is what the installed code gives (S3: "the search reflects the desired state"); its record gets a new datestamp if its metadata changed, and is harvested. The stored and the new value stay in the run, so the finding is not lost. A new failure (the reader now raises, or a time-out under load) does not replace a stored success; it is reported as a difference, `differs: adhoc/x/a.dm4 (now fails: timed out after 60 s)`. Against the lean: a value that changes on every extraction then changes the record each time its dataset is sampled. This is a question in the proposal.

*What it watches for, by example: partial dates (187, review row 20 and finding 6).* RosettaSciIO's DM reader parses the acquisition date with `dateutil.parser.parse`, which fills missing parts from today: a tag `"May 2021"` gives `2021-05-12` on 12 November. Such a record changes whenever it is extracted again, and in the spot check it shows as a difference only in `General.date`. There is no workaround: "Watch for now and keep as a finding." Task 6.3 records whether staging's DM files have such tags, and only if a real writer produces them does it go to the backlog's "Sync with upstream" as a finding for RosettaSciIO.

*Not the self-test.* The fixture self-test that 180 deferred (D5 c) compares with what CI recorded and needs the fixtures in the image. The spot check needs no fixtures and compares the deployment with itself.

## Risks / Trade-offs

- [Every deployment of any change in the net costs a full re-extraction (about 52 minutes on staging)] → accepted (S3). The report shows when it changed nothing (D6). If it becomes a burden, narrow the net with a concrete example (proposal question).
- [An unpinned dependency picked newer at an image build re-extracts everything, although nobody changed anything] → the note and the report name it (`numpy 2.3.4 -> 2.4.0`). This is S4's case, and it is caught on purpose.
- [A source file edited during a crawl in an editable install: the workers, which are replaced every 100 tasks (`extraction.py:39`), import the new code, while the identity is the old one] → the results are stored under an identity that did not produce them. The next crawl computes the new identity and extracts again, so this heals by itself. It happens only in development.
- [A stale `*.egg-info` in a source tree is a second distribution of the same name] → for the versions, the first one found counts (D1, the probe); for the source, D1 (c) finds the package where it is imported from. Tests cover both, with the egg-info ahead through the working directory.
- [Code outside the net changes output: a system library, a data file loaded from outside its package] → not covered by the identity. The spot check (D10) looks for its effect on real data, and the recorded fixture results (D5 b) catch it in CI where a fixture exercises it.
- [Stale bytecode: Python checks a `.pyc` by the source's size and its mtime in whole seconds, so a same-size edit within the same second runs the old code under the new identity, and it does not heal; the image also copies the host's `__pycache__` of `modama-formats-em` (30 files; only `python/crawler` has a `.dockerignore`)] → `.dockerignore` files with `**/__pycache__/` and `*.egg-info/` for the build contexts `em` and `chain`, and a pitfall line in the README (task 6.1, review finding 5). Not an ingredient.
- [Every failure is extracted again every night (D9)] → about a minute on 8 processes for run 3's 2,871 failures; a time-out costs its 60 s each time. A file that fails every night stays visible in the report.
- [A spot-check difference that is noise, or that depends on the day of the crawl] → reported and kept in the run; the record takes the new result (D10, lean). No workaround (187).
- [No lock or constraints file for the image: a deployment can run newer dependencies than CI tested] → the identity catches it, but D6's "why" then lists several distributions at once, and the recorded fixture results (D5 b) do not vouch for the deployed versions. Noted (D5 c, review finding 8); task 6.2 records which versions changed between two deployments.
- [The first crawl after this change extracts everything, because the stored labels are not digests] → once, reported as `earlier identity "4", ingredients unknown`. About 52 minutes on staging. Production has no extractions stored yet.
- [`subtree-crawl` and this change both modify the requirement "Extraction follows the identified extractor"] → whichever is archived second takes the other's text: `subtree-crawl`'s sentence "In a crawl of the whole tree" and "A subtree crawl reuses no stored result under its path" go into this change's wording, or the other way round (task 7.1).

## Migration Plan

Deploy after `schema-migrations`, with an image rebuild; `modama-crawler migrate` applies D8's migration. The first crawl extracts everything once. Rollback: the migration's downgrade renames the column back, adds `extract_retry` back empty and drops the run columns. The old code then compares its label (`"4"`) with a digest and extracts everything once more, which fills `extract_retry` again. Both directions cost one re-extraction and harvest only what changed.
