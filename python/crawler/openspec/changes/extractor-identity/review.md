# Review of the change `extractor-identity` (2026-11-12)

Scope: the proposal, design (D1 to D8), specs and tasks of this change at 98c3686, before any code, judged against @weber's answers S1 to S7 and 179 to 182, R44 and R45 as proposed, requirements-pipeline 2.4, the open changes `em-formats-and-extraction`, `parallel-walk` ("the same data gives the same result or a failure"), `subtree-crawl` (H3) and `schema-migrations`. The central question is @weber's 180: what outside the crawled files can change an extractor's output, and does the proposed fingerprint (D1) catch it? Method: one reviewer that did not write the change, reading the code of the crawler and `modama-formats-em` on `crawler` 50533f9 (the extraction code is unchanged at f00f6bb) and RosettaSciIO 0.15.0, and running the four extractors on all 13 extracted datasets of the `em` fixtures in `~/.venv` and in throwaway containers of the VM's `search-stack-crawler` image (`docker run --rm --network none`; the compose project `search-stack` was not touched). The scripts are in the session's scratchpad, not committed.

Two decisions by @weber came in during the review and are applied below: thread counts and numerical libraries that change only the last digits of floating-point results are left out on purpose ("let's not be too pedantic about the 12th significant digit"), read as a general rule: an influence whose only effect is insignificant numerical noise, whatever its source, is no reason for the fingerprint to change. The check whether such noise can still reach a record is in section C.

**CONFIRMED** means read in the code or run (marked "ran"); **PLAUSIBLE** means it follows from the code or a library's documented behaviour, but was not seen happen here. Severity: **H** defeats the purpose of R44/R45 in a reachable case; **M** a wrong result or a wrong "why" in a reachable case; **L** an edge case or cleanliness.

Tally: 33 influences checked; the fingerprint misses 6 that can change an output (rows 5, 6, 7, 9, 20, 28); 4 of them have a fix to add, 2 are to watch. 8 findings: 1 H, 3 M, 4 L; 6 confirmed, 2 plausible.

## B. Findings, most severe first

Each finding ends with its outcome after @weber's answers 185 to 187 (2026-11-12, quoted in the design's "Evidence"). All eight are addressed in the planning artifacts; none is in code yet.

**1 (H, CONFIRMED). What the fingerprint misses is invisible by construction.** D6 gives every re-extraction a reason, and R45 asks "does it work as intended?". But an influence that the fingerprint misses re-extracts nothing, so no line appears; the report can only show the fingerprint working, never where it falls short. Example: RosettaSciIO loaded from `PYTHONPATH` with a changed reader (row 6): every crawl reuses the old descriptions under an identity that equals the stored one, and `runs`, `status` and `trace` all say "current". 180 asks to "watch out for anything in the wild that is missed from the fingerprint"; as designed there is nothing to watch with. *Fix:* a spot check on real data: each crawl extracts a small sample of the datasets it would reuse again (say 20 per format, a second or two on 8 processes at run 3's rates) and compares the output with the stored one; the report says `spot check: em/dm4 20 of 20 as stored`, or names the dataset and the differing field. This is not the fixture self-test that 180 deferred (D5 c): it needs no fixtures in the image and checks the files ER-C actually has. It is a new mechanism, so it is @weber's call; requested by 180 and R45.

*Outcome: addressed.* Accepted by @weber (186: "a random sample of different formats and files"). Design D10 (20 per format, a new seed per crawl from `secrets.randbits(64)`, in the report, the log and `crawl_runs.spot_check`; a difference is reported, not spread; a new success replaces the stored result, which is still open as a question in the proposal); R45's wording; spec `extraction`, "Each crawl spot-checks a sample of what it reuses" and "A spot-check difference is reported, not spread"; tasks 4.5 and 6.2.

**2 (M, CONFIRMED). Code imported from outside the net.** D1 hashes the source of a distribution only when its first metadata has `direct_url.json` and `packages_distributions()` maps its import names. Three ways a crawl imports code that is not hashed, each run here (rows 5, 6, 7): a bare-`.pth` editable of a non-setuptools backend (no import name mapped), a package on `PYTHONPATH` or in the working directory shadowing an installed one (metadata says 0.15.0, the import is the shadow), and a stale `*.egg-info` in the working directory found first (no `direct_url.json`). Scenario: during RosettaSciIO development (S2, S6), a developer runs `python -m modama_crawler crawl --path …` from the RosettaSciIO clone; its reader changes, the identity does not, and the old descriptions stay. *Fix:* one rule instead of `direct_url.json`: hash the files of every top-level import package that `importlib.util.find_spec` finds outside the site-packages and standard-library directories (mapping names from `top_level.txt`, RECORD, or the directories a `.pth` adds), and report a path-installed distribution for which no package was found. Tests: the egg-info ahead through the working directory, a `PYTHONPATH` shadow, a `.pth` editable. This also makes "the first one found" (D1, Risks) unnecessary for the source, and leaves it only for the versions.

*Outcome: addressed as suggested,* except that the `direct_url.json` rule stays beside the new one: a non-editable install from a path lands in site-packages, where the new rule does not look. Design D1, the `source` row (c) and "Code imported from outside the net"; Risks; spec `extraction`, "The extractor identity is derived from the installation" (scenarios for the `PYTHONPATH` shadow and the egg-info ahead) and "A path install without source is named"; task 2.1 (with the bare-`.pth` editable).

**3 (M, CONFIRMED). A `MemoryError` from the worker's limit is kept as the file's failure.** `ENVIRONMENT = (OSError, ImportError)` (`extraction.py:46`); `MemoryError` is neither. Ran: a 2×2-pixel DM4 fixture under a 400 MB limit fails with `MemoryError()` and `retry: False`, so it is reused until its files change. The limit comes from `MODAMA_CRAWLER_EXTRACT_MEMORY` and the address space grows with the CPUs (README: about 400 MiB on 8), neither of which is in the fingerprint, by D4's choice. D4's justification ("failures of the environment are retried anyway") is therefore wrong for memory. Scenario: on a 64-core production host before `cpu-budget`, or with a limit lowered to test, thousands of DM files fail; raising the limit again does not bring their descriptions back. *Fix:* add `MemoryError` to the retried failures, with a scenario in the `extraction` delta ("A memory failure is retried on the next crawl"); a file that really needs too much memory then costs one attempt per crawl, which is visible as a failure each time.

*Outcome: addressed, more broadly than suggested* (185: "retry what failed or was missed because of that failure, no matter what caused it"). No failure is reused, whatever its cause; `ENVIRONMENT`, `Extraction.retry` and `datasets.extract_retry` go away; limits and settings stay out of the identity. Design D4, D9, D8 and the sequence "185: a limit lowered, then set back"; spec `extraction`, "Extraction follows the identified extractor" (scenario "A failure under a lowered memory limit"), "Unchanged directories are not recognised or extracted again" and "The crawl reports failures tried again"; tasks 3.1, 3.2, 4.1.

**4 (M, CONFIRMED). "Records changed" mixes two causes, so the "why" can be wrong.** D6 counts how many of the re-extracted datasets' records changed, from the upsert (`store.py:470`). Records are rebuilt on every crawl (`store.py:455`), and `records.py` and `render.py` are in the same net as the extractors. Scenario: one deployment fixes a typo in `records.py`'s description template; every dataset is re-extracted (new identity), and the report says `em/dm4: 150,000 extracted again for a new identity (source of modama_crawler changed), 150,000 records changed`, as if the extractor's output had changed. The same happens for a changed `OAI_BASE_URL`. *Fix:* count what the re-extraction changed, not the record: `extract()` already holds the stored `Extracted` (`before`) and the new one, so `outputs changed` is one comparison per dataset, with no change to the store. The record count can stay beside it. This count is also the instrument for row 20 and for numerical noise (C): after a deployment that changes no output, anything above 0 is an influence that varies between runs.

*Outcome: addressed as suggested,* without the record count beside it (the crawl's report already counts changed records), so the store needs no `RETURNING`. Design D6 ("What changed is counted on the results"); spec `extraction`, "The crawl reports re-extraction and its cause" (scenario "A change in building records only"), spec `chain-trace`; task 4.1.

**5 (L, CONFIRMED mechanism, PLAUSIBLE in practice). Stale bytecode runs under the new identity.** Python validates `.pyc` by the source's size and mtime in whole seconds; ran: a same-size edit with the same mtime keeps the old code, while the digest of the source changes. The stored output is then filed under an identity that did not produce it, and it does not heal: the next crawl has the same identity and the same stale bytecode. Likely only in fast development loops (S1) or with tools that keep mtimes. The image also copies the host's `__pycache__` of `modama-formats-em` (30 files; only `python/crawler` has a `.dockerignore`). *Fix:* `.dockerignore` files with `**/__pycache__/` and `*.egg-info/` for the `em` and `chain` contexts (one line each in the README's pitfalls for development); no ingredient.

*Outcome: addressed as suggested.* Design D1 ("What it does not catch") and Risks; proposal, "Build hygiene"; task 6.1.

**6 (L, PLAUSIBLE). A date that depends on the day of the crawl.** Row 20: for a partial DM date tag, RosettaSciIO fills in today. Before this change such a value moved only when someone raised `extractor_version`; now it moves on every deployment that re-extracts, and the record is harvested again although nothing changed. Whether ER-C's files contain such dates is not known. *Fix:* none now; finding 4's count after a no-output deployment shows it, and a fix then follows the concrete file (for example the DM format refusing a date without a year).

*Outcome: addressed as a watch, no workaround* (187: "Only if a real world writer actually produces such files it is a finding reportable upstream"). The spot check and the staging check watch for it; task 6.3 records in the staging findings whether staging's DM files have such tags, and only then adds an item to the backlog's "Sync with upstream". Design D10 ("partial dates"), Not now; task 6.3.

**7 (L, PLAUSIBLE). The `runs` note can stay silent while datasets will be re-extracted.** The spec `crawl-runs` prints the note "when the installed identity differs from that of the last finished crawl". Scenario: a subtree crawl with experimental code C1 (`h1`) on one path, the code reverted to C0, then a subtree crawl with C0 (`h0`) elsewhere: the last finished crawl has `h0`, the note says nothing, and the next nightly crawl re-extracts the first path's datasets. *Fix:* trigger the note on D7's own `GROUP BY` over `datasets` (any stored identity other than the installed one), not on the last run's identity.

*Outcome: addressed as suggested.* Design D7; spec `crawl-runs` (scenario "Left over from an experiment"); task 4.2.

**8 (L, CONFIRMED). CI and the deployment run different versions.** The image has no lock or constraints file, and its `pip install` layer is rebuilt on every crawler change (`COPY . /src` before it), so each crawler deployment can also bring a newer numpy, dask or pint than CI (D5 b) tested. The fingerprint catches it (row 31); but D6's "why" then lists several distributions at once next to the source change, and D5 b's recorded results do not vouch for what was deployed. *Fix:* nothing in this change; note it where the deferred self-test (D5 c) is described, since that is what it would catch, and in the field-test checks of task 6.2 (which versions changed between two deployments).

*Outcome: addressed as suggested,* noted with its consequence. Design D5 (c), Risks, Not now; task 6.2.

## C. Numerical noise (@weber's decision, applied)

Influences whose only effect is a difference in the last digits of a float are left out (rows 15, 16, and any library change that only rounds differently). Can such noise still change a record? **Not with the current extractors.** Ran: the 13 outputs are byte-identical between the VM's Python (Clang) and the image's (GCC), with SIMD dispatch reduced, with one BLAS thread and with one CPU. The floats come straight from file headers or through one correctly rounded operation (`x / 1e3`, `x * 1e-3`, `rsciio/digitalmicrograph/_api.py:923-943`), which gives the same bits on every IEEE-754 machine; nothing sums, multiplies matrices or calls `exp`.

Where it can happen: a library version that changes how a number is computed. Ran: under NumPy 2's promotion rules `np.float32(3000.1) / 1e3` stays float32 and prints `3.0001001358032227`; as float64 it would be `3.00010009765625`. A DM description prints such values with all their digits (since the no-rounding change), so that kind of upgrade changes the text of many records. The fingerprint changes anyway (the numpy version), so it is visible, not hidden. *Smallest remedy:* none in the fingerprint and no rounding; finding 4's per-format count of changed outputs makes it visible, and if it turns out to cost a large harvest, the report can say how many outputs differ only in the last digits of numbers. A future extractor that computes (sums over frames, statistics) is the case to watch; its recorded fixture results (D5 b) will show whether CI's machine and a developer's differ.

*Outcome:* the rule is in design D4 and in R44's wording; the spot check (D10) and the count of changed results (D6) are where noise would show.

## D. What is right and should stay

- The identity is derived, never typed, and compared for equality only (D1, D3): rollbacks, alternating clones and reverted experiments (S1, S2, S5, H3) need no special case.
- The net is wide on purpose and simple: the whole installation's versions plus our own source (179). Of the 33 influences, every one that can change an output is caught, except six: code imported from outside the net (rows 5, 6, 7, finding 2), stale bytecode (row 9), the date of the crawl (row 20) and the memory limit (row 28, finding 3).
- What D1 keeps out is right: relative paths, no mtimes, no `direct_url.json` URL, no `sys.version` build string, no tests or bytecode. Ran: the same output under different data roots and Python builds, so path- and build-independence costs nothing.
- Computing it once in the main process from metadata alone, without importing numpy (D4): measured 0.13 s in the VM and 0.31 s in the image for the metadata part, for 63 and 61 distributions.
- The pitfall of the stale egg-info is found and handled for the versions (first found); the image has it too (`/src/src/modama_crawler.egg-info`, written by `pip install -e` itself).
- Leaving out thread counts and the memory and time limits from the fingerprint (D4) is right; only the `MemoryError` classification needs fixing (finding 3).
- D5 b (recorded fixture extractions in CI) is the cheapest guard against a dependency upgrade, and the outputs are deterministic enough for exact comparison (C).
- No automatic crawl after an upgrade, the note with the command instead (D7, 182, requirements-pipeline 2.4).

## Not verified

- A real non-setuptools editable install (row 5 was simulated with a hand-made dist-info) and a real non-UTF-8 locale (none is installed in the VM or the image).
- How the worker's address space grows beyond 8 CPUs (OpenBLAS caps its threads at the CPUs present; this VM has 8).
- Whether ER-C's DM files contain partial dates (row 20), and the cost of the spot check on staging's NFS.
- The code itself: this change has none yet. The findings are about the design and the existing code it builds on.

## E. Review of the code (task 8.1, 2026-11-12)

An independent reviewer read ec204fb..1998574 and e5d8359 against the specs, R44 and R45; decisions by the main session. Verdict: sound; migration 0002 loses nothing and its downgrade gives the older code what it reads correctly. Nine findings, each verified here before it was acted on, with its outcome:
