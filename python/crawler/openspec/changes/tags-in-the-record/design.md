# Design

Measured on the DM and K2IS fixtures of `modama-formats-em` (DM/K2IS branch, `worktree-agent-a454075836693a33a`), in the VM, 2026-11-12. The chain's code read is the pinned submodules: metadata-crawlers 9c120f5, metadata-warehouse v1.10.0 (0b461ce), data-commons-search v0.10.2 (6c07bdc), with our patches in `prototypes/search-stack/patches/`.

## D1: sorted by name, not the file's order

A record is built from the dataset's extraction: on the first crawl from the extraction that ran, on later crawls from the stored one (`datasets.extracted`, JSONB), when the dataset is taken over or its extraction reused. JSONB does not keep the order of an object's keys (PostgreSQL's documentation, "JSON Types": "jsonb does not preserve white space, does not preserve the order of object keys"). Lines in the file's order would therefore change between the first and the second crawl of an unchanged file, and every such record would move its datestamp and be harvested and indexed again (records spec, "Unchanged crawl").

Sorted by name (code points) is the same on both paths. It is close to the file's order, which in the three fixtures with tags is nearly sorted but follows no rule we could name: `Acquisition.Device.Camera Number` comes before `Acquisition.Device.CCD.Pixel Size (um)` in the file (as if case did not count), `Microscope Info.STEM Camera Length` before `Microscope Info.Stage Position` (as if it did). Names that share a group keep together when sorted, as strings with a common prefix do.

Alternative, for @weber: the file's order, kept by storing `datasets.extracted` as `json` instead of `jsonb` (a migration; the stored extractions keep JSONB's order until extracted again, which the DM branch's new identity does anyway). Not done: a migration for an order that sorting nearly gives.

## D2: values as JSON text, numbers as the database gives them back

A string on one line stands as it is (`K2-IS-0001`, `inf` for an infinity, as the DM part stores it); any other value as its JSON text on one line: `300000.0`, `[1920, 1792]`, `-2.4043772802208405`, not rounded, no unit added; a string with line breaks too (D6). An object's keys are sorted in its JSON text, for the same reason as the lines (D1): JSONB gives them back in its own order (the review's round trip, 2026-11-12, `{"zz": 1, "a": 2, "bbb": 1e20}`).

JSONB keeps a number's decimal digits, not Python's type: `1.3166796483380824e+17` (Capture52's `Acquisition.Frame.Sequence.Acquisition Start Time (epoch)`, a DM time stamp) comes back from the database as the integer `131667964833808240`, and `-0.0` as `0.0`. Found by the test that crawls Capture52 twice: the second crawl changed the record in exactly these two lines. `as_stored` writes such numbers as the database gives them back, on both paths; the spot check, which compares with `==`, never saw the difference. The stored values are not changed.

## D3: a line longer than the storage's limit for a string is cut

Storage cuts every string of an extraction to 4,096 characters and every list to 1,000 entries (`extraction.MAX_STRING`, `MAX_ITEMS`). A list of 1,000 numbers is still about 20 kB of JSON text on one line; the formats' skip lists leave out large arrays before (TEMPLATE.md, e9fbf9a8), so this is a guard only: a non-string value's JSON text longer than 4,096 characters is cut to that length and ends in `…` (strings are at most 1,000 characters since the formats' shared check, `values.textual`). The longest line of the fixtures is 113 characters (Capture52), so nothing is cut there.

## D4: what the chain does with two descriptions

- **The harvester** (`dc_to_datacite.xsl`, `descriptions`): every non-empty `dc:description` becomes a `datacite:description descriptionType="Abstract"` of `normalize-space(.)`, so **the lines are joined with single spaces**: from DataCite on, the tags are one long line, `Acquisition.Device.Active Size (pixels): [1920, 1792] Acquisition.Device.CCD.Pixel Size (um): [10.0, 10.0] …`. Only the crawler's own record (and `modama-crawler records`) keeps one tag per line.
- **The warehouse** (schema and tables): `descriptions[].description` is a JSON-schema string without a length limit; the tables keep the XML and JSON as `XML`, `TEXT` and `JSONB` without limits. No limit is reached.
- **The index** (`opensearch_mapping.json`): `descriptions.description` is `text`, copied to `_all_fields` and `_description`; the search API's keyword leg queries `_description` (our patch `search-api/0001`), so a word of a tag's value is found. `_source` keeps the descriptions and, in `_additional_metadata`, the oai_dc record again.
- **The embedding** (`utils/embedding_utils.py`, `get_embedding_text_from_fields`): titles, subjects and **all** descriptions, joined with spaces; the stack embeds locally with `BAAI/bge-small-en-v1.5` (`EMBED_API_URL: ""`), whose tokenizer fastembed truncates at 512 tokens (`preprocessor_utils.py`, `enable_truncation`), CLS pooling. The summary comes before the tags, so it is never cut; the tags fill the rest of the 512 tokens. Measured with the warehouse's own functions and model (scripts outside the repository, commands in the hand-over), on `crawler` 4cef5532's formats: tokens without → with tags, Capture52 105 → 5,105, the DM4 test image 109 → 2,777, the DM3 one 102 → 2,511, the block file test2.blo 81 → 622, all cut to 512. Cosine between a record's vector without and with tags 0.94 to 0.96 (the RGBA DM4, 38 → 359 tokens, 0.87); four queries scored 0.791 → 0.795, 0.728 → 0.755, 0.589 → 0.604, 0.797 → 0.797; between different records the vectors grow more alike, by 0.00 to 0.11 (for example DM4 against DM3 0.788 → 0.853). Embedding a 512-token text took 427 ms against 46 ms for a summary record (one thread, the VM).
- **The search API's hit** (`models.py`, `description`): the first description with `lang` `en`, else the first; ours have no language, so the summary. **Matchmaker's** cited entry (`CitedDatasets.tsx`, `SearchResultItem.tsx`; the browser's `upstream.cited_entry`) shows the hit's description: the summary, cut at 300 characters. The reranker (`mcp_server.py`, title and `hit.description`) and the chat model's context (`main.py`, `hit.description` cut at 800 characters) use the summary only. `/search` returns all descriptions in each hit's `_source`, so a K2IS hit carries about 19 kB more.

For @weber (not decided here): (a) leave it, the tags make up about 80 % of the embedded tokens of an EM record and make EM records a little more alike; (b) a patch to the warehouse that embeds titles, subjects and the first description only, which keeps today's vectors and cost, the tags staying in the keyword leg; (c) fewer tags in the record. The measurement is of four fixtures and four queries, not of a search's ranking.

## D5: size

Per record, the second description of the fixtures (`crawler` 4cef5532, from the formats' recorded extractions): Capture52 18,881 bytes (296 lines of 307 entries, 11 empty), the DM4 test image 7,803 (118 of 120), the DM3 one 6,991 (106 of 110), the RGBA DM4 901 (16 of 19), the block files 1,405 to 1,768 (39 of 39), Merlin headers 888 to 1,454 (27), EMPAD headers 742 to 4,438 (19 to 80). In the crawler's `records` table (JSONB, TOAST with pglz, PostgreSQL 17): Capture52 612 → 5,293 bytes, DM4 615 → 2,376, DM3 606 → 2,229.

Staging (run 4: 156,779 DM4 and 19,457 DM3 datasets extracted, 700 Merlin, 230 EMPAD; K2IS acquisitions were not a format of their own then): about 176,000 DM records × 7 to 8 kB, about 1.2 to 1.4 GB of tag text per copy before compression; the `records` table grows by about 1.6 to 1.8 kB per DM record stored, about 300 MB. Merlin and EMPAD add under 2 MB. Copies along the chain: the warehouse keeps the record as DataCite XML and oai_dc text in each harvest event and in its `records` row (raw XML, `datacite_json`, `additional_metadata`), the index twice in `_source` (the descriptions and the oai_dc record in `_additional_metadata`) and in three inverted fields (`descriptions.description`, `_all_fields`, `_description`). Not measured: an estimate of 1 to 2 GB each for the warehouse database and the index, to be measured on staging (`pg_total_relation_size`, `_cat/indices`) after the first harvest. Indexing: the embedding of each such record goes from about 100 tokens to 512, which took 427 ms against 46 ms per record here (one thread): for 176,000 records about 19 CPU hours more for a full indexing run, about 1.2 hours on staging's 16 transform processes if the embedding scales with them, against F16's finding that harvest and indexing spend little of their time on the embedding until now.

The records change once, when the change reaches a deployment: with the formats' new extractor identity, which re-extracts and changes these records anyway, there is no second full run.

## D6: block files, and a string with line breaks

The rule is generic: any format whose values hold `original_metadata`, a flat mapping (TEMPLATE.md). Since `crawler` 4cef5532 the DM, K2IS, block file, Merlin and EMPAD formats store it flat, so each gets the second description; a block file's lines are `blockfile_header.Beam_energy: 200000` and so on, 39 of them.

The block file's `blockfile_header.Note` is a string with line breaks (`\r\n`), and in Stingray16bit_7_11.blo its lines look like tags of their own (`Detector: AVT Stingray F046B`, `Exposure (ms): 1.6`). Such a string is written as its JSON text, quoted, with `\r\n` as escapes, on one line (the coordinator's decision on the review, 2026-11-12), so that no line of a value can pass for a tag. The cost: the search's standard analyzer reads `\r\nDetector` as `rnDetector`, so the first word after each line break of such a value is not found as itself; the record's summary line is not affected. A dict value would be written as its JSON text with sorted keys (D2); no format stores one now.
