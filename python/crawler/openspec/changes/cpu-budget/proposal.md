# Proposal

## Why

Where several processes run, each math library sizes its thread pool for the whole machine, on its own. On the dev server (24 cores, 48 logical CPUs) a transform batch process starts about 119 threads (1 + 47 OpenBLAS + 23 ONNX Runtime, pinned to the same 23 cores in every process, + 48 Rayon; a prediction from the code that fits the 95 to 143 observed), and four of them ran at a load of 56 to 106 on 48 CPUs (F16, F17). In the VM, 4 processes × 2 threads embedded 194 texts/s against 118 with the defaults (`docs/research/cpu-oversubscription.md`, on `crawler` since d0dca90). The search API runs 6 uvicorn workers with the same defaults: 25 threads each, 7 of them pinned one each to CPUs 1 to 7, the same in all six (measured in the VM, review finding 5). In the crawler, each extraction worker starts CPUs − 1 idle OpenBLAS threads of about 41 MB address space each, which count against its 4 GiB `RLIMIT_AS` (measured 430 MB against 143 MB on 8 CPUs). @weber (2026-11-12): "we will run on big machines where this is super super important to avoid oversubscription. Of course we need to adapt to the local machine always. The dev server is not the same as the production server", "the whole code should do it right by itself and not rely on the admin for this", and "admin gets help, but not arcane magic, and gets easy way to influence what is happening" (requirements-pipeline 2.4, "The operator stays in control").

## What Changes

- **The crawler counts the CPUs it may use** (its affinity, a cpuset included, and its own cgroup's CPU quota, rounded up) instead of the machine's (`os.cpu_count()`), for its worker processes: the walk's matching processes and the extraction processes, still at most 8. `MODAMA_CRAWLER_EXTRACT_WORKERS` stays as the override.
- **The crawler's worker processes start with one thread per math library** (`OPENBLAS_NUM_THREADS`, `OMP_NUM_THREADS`, `MKL_NUM_THREADS` set to 1 before the processes start, once in `cli.py` around the walk and the extraction), with LiberTEM's `set_num_threads_env` copied under its MIT notice (@weber: "let's just copy the few lines here"; no dependency on LiberTEM).
- **The transform worker of the search stack computes its own budget** before Celery starts: processes P and threads per process T from the physical cores it may use, the memory it may use and the per-process peak measured for a batch, and Airflow's task limits; it sets the threads of ONNX Runtime (through patch 0002's `EMBEDDING_THREADS`, which also stops ONNX Runtime's pinning), of Rayon and of OpenBLAS. The compose files lose their `--concurrency` for that worker. Without settings the machine governs (@weber: "without any settings it should run the full thing"); the dev server limits the indexing DAG to 16 active tasks with one variable in its `staging.env` ("here (devvms running etc) we restrict it. 16 sounds sensible").
- **The search API computes its own budget the same way**: its number of uvicorn workers from the CPUs it may use, all of them (@weber, 158: "Let's run on all usable CPUs"), and one ONNX Runtime thread per worker (a patch like 0002 for its `TextEmbedding`), instead of upstream's fixed `WORKERS=6` with the libraries' defaults.
- **One JSON-schema validator per batch process** (@weber, decision 177: "yes, take the validator patch in"): patch 0001 in our Airflow image, beside 0002, builds the validator once instead of `jsonschema.validate` per record (`transform_core.py:179`, which checks the schema itself on every call: 21 ms against 0.18 ms per record, about 60 % of a batch of 250, staging finding F16). The same records pass and fail as before.
- **Background services run at a lower CPU weight** (@weber, 163: "What about LOWERING the priority of crawler, harvest and indexing tasks, and keeping the live requests at normal prio?"): `cpu_shares: 512` on the crawler, the crawl timer, both Airflow workers and the transform service; the search API and the search frontend keep Docker's default. A weight only acts when the CPUs are contended and reserves nothing.
- **Pools are counted by kind** (@weber, 2026-11-12, decision on question 115): I/O-bound pools may count logical CPUs (SMT threads), math pools count physical cores unless a measurement shows otherwise. No per-container CPU split by default; a limit set later for a service is honoured because each process counts what it may use.
- **One log line** at start, per service, states the budget, where each number came from, and which override is active.
- **A diagnostic for the operator**, `prototypes/search-stack/cpu-budget.sh` (the pattern of the `up`/`down` scripts, requirements-pipeline 1.4): it prints, per service on this machine, what it will choose and why (CPUs usable, physical cores, cgroup version and quota, memory, the DAG limits, the resulting processes × threads), which override is active and how to set one. It runs the services' own counting code, in containers started like the services, so it shows their limits and answers the cgroup-version question (152) on any machine.
- **Operator documentation of who does what and why** (which service counts what, the defaults, the overrides and when to use them), one home in the search stack's README, linked from the crawler's README and the staging runbook.
- Requirement wording for @weber's decisions: `design/requirements.md` R43 and `design/requirements-pipeline.md` 2.4 (below; written into the files by a task once accepted).

Behaviour towards the user (operators): the defaults follow the machine. The compose files keep no numbers per machine for the CPU budget; the one number left is the dev server's DAG limit of 16, in its `staging.env`, by @weber's decision; staging's `--concurrency 4` and the base file's `--concurrency 1` go away. `crawl` and `records` log one more INFO line, for example `CPU budget: 8 worker processes, 1 math thread each; 8 CPUs usable (affinity 8, no quota)`; the transform worker and the search API log one each before their own start banner. A new script `cpu-budget.sh` and a new command `modama-crawler cpu-budget` print the same, with the reasons. On a machine with fewer usable CPUs than `os.cpu_count()` (a container with `--cpus` or a cpuset), the crawler starts fewer processes than today. In the VM's test deployment the transform worker runs 8 batch processes instead of 1, and the search API 8 workers with 1 thread each instead of 6 with 7 pinned threads each; on the dev server the search API would run 48 workers. When the CPUs are contended, searches go before crawling, harvesting and indexing. What a harvester or a searcher sees does not change; indexing gets faster (to be measured).

Out of scope (see design, "Not now"): a per-container CPU split in the compose files (@weber: "no split"); CPU limits in production (@weber: "I don't think we have any limits beyond what we do with docker at this time"; a backlog item) and the cgroup version on the dev server and in production (152, later; a backlog item; the diagnostic shows it); cgroup v1; the default Airflow worker's own pool and the other services' pools (PostgreSQL, OpenSearch); a package of our own for the count (spun out once LiberTEM wants it); parent cgroups' quotas; Windows and macOS.

Serves: the new R43 and requirements-pipeline 2.4 (CPU budget, and "The operator stays in control", 7f2ed86 on `crawler`); R10 (scale), F16 and F17 (indexing time on staging); R23 (extraction failures from the memory limit, not from the machine's CPU count).

### Proposed requirement wording

`design/requirements-pipeline.md`, 2.4 Operating conditions, a new bullet next to "The operator stays in control":

> - **CPU budget** (@weber, 2026-11-12): every service adapts its processes and threads to the machine it runs on and, by default, does not oversubscribe it ("we will run on big machines where this is super super important to avoid oversubscription. Of course we need to adapt to the local machine always. The dev server is not the same as the production server."). The code computes the budget itself at start ("the whole code should do it right by itself and not rely on the admin for this. I wouldn't want to maintain this myself as an admin of the service."): in each process tree, processes × threads per process stays within the CPUs that process may use (affinity or cpuset, and the cgroup CPU quota), not the machine's total. Math pools (BLAS, ONNX Runtime, tokenizers) count physical cores; I/O-bound pools may count logical CPUs, since "for I/O bound tasks, hyperthreading works very well" (@weber, 2026-11-12); a measurement may change the count for a math pool. No service relies on a library's default thread count where several of its processes run. No CPU split per container by default ("no split. We may want to reduce the number of available CPUs to specific services since a lot of them are running in parallel"); a limit set for a service later is honoured by the same count. Background services (crawl, harvest, indexing) run at a lower CPU weight than the services that answer users' searches, so that live requests, and other work on the machine, go first when the CPUs are contended ("What about LOWERING the priority of crawler, harvest and indexing tasks, and keeping the live requests at normal prio? That also helps to keep dev work running on the machine, and services we don't see / handle.", @weber, 2026-11-12). Overrides are few, named and documented, for measurements and for the operator; the defaults must be right without them. Each service logs its budget at start and says when an override is active; a diagnostic script shows every service's budget and its reasons on the machine at hand (2.4, "The operator stays in control"). Checked on staging during an indexing run, per container: CPU time over the run (`cpu.stat`) not above the CPUs the container may use, and no batch process with more threads than its budget; the machine's load average is context, not the criterion (it counts NFS waits and the devvms). Background: `docs/research/cpu-oversubscription.md`.

`design/requirements.md`, Scale:

> - **R43 (must, @weber 2026-11-12)** The crawl follows the stack's CPU budget (`requirements-pipeline.md`, 2.4): its worker processes count the CPUs the crawler may use on the local machine (affinity or cpuset, and the CPU quota), and the math libraries inside them start one thread each, so that a worker's memory limit (`RLIMIT_AS`) does not depend on the machine's CPU count. The crawler's pools count logical CPUs: the extraction is I/O-bound (header reads over NFS), the matching is CPU-bound pure Python with one thread per process; under the cap of 8 the difference shows only in a container with fewer than 8 cores. `MODAMA_CRAWLER_EXTRACT_WORKERS` overrides the count.

## Capabilities

### New Capabilities
- `cpu-budget`: how many processes and threads the crawler's worker pools, the search stack's transform worker and its search API start, counted from what the process may use on the machine, the log line that states it, and the diagnostic that shows it. The search stack's requirements live here because the stack has no OpenSpec of its own and the requirement's home, `requirements-pipeline.md`, is in this project's `design/`.

### Modified Capabilities
None. The extraction workers' count is in the pending changes `em-formats-and-extraction` and `parallel-walk` only as README text ("by default the number of CPUs up to 8"), not as a requirement; the README is updated by a task.

## Impact

- Crawler: new module `src/modama_crawler/cpus.py` (count, the copied LiberTEM lines with their notice); `extraction.py` (`default_workers`), `cli.py` (the context around the walk and the extraction, the log line, the command `cpu-budget`). README configuration, BACKLOG.
- Search stack: new `prototypes/search-stack/cpu-budget/budget.py` (count, budgets of the transform worker and the search API, start of Celery and of uvicorn, `explain`), copied into both images; `prototypes/search-stack/cpu-budget.sh`; patch 0002 for the warehouse applied in an image build of ours (`patches/warehouse/`, following `search-api.Dockerfile`), a patch 0002 for the search API (`patches/search-api/`); `docker-compose.yml`, `docker-compose.staging.yml`, the runbook's `staging.env`; `perf/` committed from the main checkout (`perf/docker-compose.perf.yml`, `perf/batch-probe.py` extended); the stack's README.
- No new third-party dependency (standard library only; psutil is not used). LiberTEM's code is copied, not depended on.
