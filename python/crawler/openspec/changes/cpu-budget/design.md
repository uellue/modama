# Design

## Context

See proposal.md, "Why". The facts, measurements and sources are in `docs/research/cpu-oversubscription.md` (on `crawler` since d0dca90, shortened in 602ce5d), cited below as "the note" with its section. The review of this change is `review.md` here; each finding's fix is marked there with where it went (R1 to R14 below).

Today:
- **Crawler.** `extraction.default_workers()` is `min(os.cpu_count() or 1, MAX_WORKERS)` with `MAX_WORKERS = 8` (`extraction.py:33,49-50`). `cli._workers()` reads `MODAMA_CRAWLER_EXTRACT_WORKERS` (`cli.py:235-238`) and passes it, or the default, to the walk's matching pool (`cli.py:213`, `520`) and to extraction (`cli.py:223`, `529`). Both pools use the spawn context (`walk.py:131-136`, `extraction.py:224,241-247`); extraction replaces a worker after 100 tasks (`max_tasks_per_child`), and its initializer sets `RLIMIT_AS` to 4 GiB (`extraction.py:38,194-198`). `cmd_crawl` starts a heartbeat thread that connects to PostgreSQL before the walk (`cli.py:282-283`, `131`). `os.cpu_count()` counts the machine, not the affinity or the quota (the note, section 3).
- **Transform worker.** `airflow-worker-transform` runs `celery worker --queues transform --concurrency 1` (`prototypes/search-stack/docker-compose.yml:422`), staging overrides it with `--concurrency 4` (`docker-compose.staging.yml:52`), `perf/docker-compose.perf.yml` with `${PERF_CONCURRENCY:-1}`. `--concurrency` wins over `AIRFLOW__CELERY__WORKER_CONCURRENCY: "4"` (`docker-compose.yml:39`), whose value is only the option's default (Airflow's celery provider, `cli/definition.py:77-82` in the image). Each batch is a fresh Python of the transform venv (`@task.external_python`, `transform_index.py:68-75`), which copies the worker's environment (`inherit_env=True`). `transform_core.py` imports fastembed, and with it numpy and ONNX Runtime, at module level (line 10), creates `TextEmbedding` without `threads` (line 64), and embeds the whole batch with one `embed(texts)` call, whose sub-batch is fastembed's default of 256 texts (`embedding_utils._embed_locally`; fastembed 0.8.0). The DAG runs one run at a time (`max_active_runs=1`, `transform_index.py:31`); the image's Airflow limits it to 16 active tasks (`core.max_active_tasks_per_dag`) and all DAGs to 32 (`core.parallelism`), and fails or retries a task that stays queued longer than 600 s (`scheduler.task_queued_timeout`; all read 2026-11-12 with `airflow config get-value` in the image). The transform batches share the 16 with the file-metadata batches on the default queue (F16). Patch 0002 (`perf/patches/0002-embedding-threads-setting.patch`, untracked in the main checkout) passes `EMBEDDING_THREADS` to fastembed; it is not applied. The airflow image is built from upstream's Dockerfile without patches (`docker-compose.yml:20-27`); the image has no `patch` and no `git`.
- **Search API.** `search-stack-search-api:0.10.2-patched` is upstream's image with `patches/search-api/0001` (`search-api.Dockerfile`). Upstream's Dockerfile sets `ENV WORKERS=6` and starts `sh -c "uvicorn … --workers $WORKERS"` (`prototypes/EOSC-Data-Commons/data-commons-search/Dockerfile:14,21`; the same in the image's config); the compose files set nothing. Each worker imports `mcp_server.py`, which creates `TextEmbedding(settings.embedding_model)` at import (line 29 in the image; fastembed 0.7.4, onnxruntime 1.23.2), and embeds one query per search in `asyncio.to_thread` (line 145). Reranking is an HTTP call (`embeddings.rerank`), not a local model. Measured in the running VM stack (read only, `/proc`): 7 Python processes of 0.43 to 0.46 GB RSS each (uvicorn's parent and 6 workers), 25 threads per worker, 7 of them pinned one each to CPUs 1 to 7 (review finding 5). Settings are pydantic `BaseSettings` without a prefix (`config.py:8,147`), so a field `embedding_threads` reads `EMBEDDING_THREADS`.

## Goals / Non-Goals

**Goals:** the defaults right on any machine without numbers per machine; what each service chose, and why, visible in its log and in one diagnostic (requirements-pipeline 2.4, "The operator stays in control"); few, named, documented overrides; one small module per environment with a tight interface.
**Non-Goals:** a split of the machine between containers (@weber, question 115: "no split"); tuning P × T on the dev server here (that is the measurement task); the default Airflow worker's pool, PostgreSQL and OpenSearch; CPU limits in production and cgroup v1 (Not now).

## Decisions

**D1. Which pool is which, and what it counts** (@weber, question 115: "for IO bound tasks, hyperthreading works very well in my experience"; 2026-11-12: "In my experience it worked well to have physical cores for math, and background work done by hyperthreading in parallel").

| Pool | Kind | Counts | Size |
|---|---|---|---|
| Crawler: the walk's threads (`MODAMA_CRAWLER_WALK_THREADS`, 32) | I/O: wait on NFS (parallel-walk D1) | nothing; outside the CPU budget | unchanged |
| Crawler: matching processes | CPU-bound pure Python, one thread each (pyxdg holds the GIL, parallel-walk D5; the note, section 6), fed by the NFS-bound walk | logical CPUs | min(usable, 8) |
| Crawler: extraction processes | I/O: header reads over NFS (`em-formats-and-extraction` D1, D7) | logical CPUs | min(usable, 8), the same setting |
| Crawler: BLAS/OpenMP inside those processes | math, but idle: nothing heavy is computed | – | 1 |
| Transform: batch processes (Celery) | mixed: `jsonschema` validation pure Python (about 60 % before patch 0001, F16), embedding | physical cores | P |
| Transform: ONNX Runtime intra-op | math | physical cores | T, explicit (no pinning) |
| Transform: tokenizers (Rayon) | math-like, runs between the ONNX Runtime calls (the note, section 4, last bullet) | physical cores | T |
| Transform: OpenBLAS (numpy) | math, but only pooling and normalising small vectors (the note, section 5) | – | 1 |
| Search API: uvicorn workers | I/O: each request waits on OpenSearch and the rerank API; the math per request is one short query | logical CPUs | min(usable, 6) |
| Search API: ONNX Runtime, Rayon, OpenBLAS inside a worker | math, latency-bound: one query of tens of tokens | – | 1 |

Because the crawler's cap of 8 is below both machines' counts, logical against physical matters for it only in a container with fewer than 8 cores; there logical is the decision. For the transform worker the choice is real (24 against 48 on the dev server) and stays open to the measurement (task 6.4); until then physical, as @weber agreed and as ONNX Runtime and oneMKL do by default (the note, section 3).
*Alternative:* logical everywhere, as dask, OpenBLAS and Rayon do: simpler, one count; but no evidence that SMT helps the embedding.

**D2. The count, modelled on `dask.system.cpu_count`** (dask 2026.8.0, `dask/system.py:17-89`, BSD-3-Clause; read in the crawler's venv), as a model, not a copy (R8: dask reads the last line's path and v1 at the hierarchy root):
- *Logical CPUs* = `len(os.sched_getaffinity(0))` (affinity and cpuset), in both modules. Not `os.process_cpu_count()`, which also obeys `PYTHON_CPU_COUNT` (measured: 3 against an affinity of 8), so that the overrides of D8 stay the only ones (R9).
- *Quota*, cgroup v2 only: the own group is the path of the `0::` line of `/proc/self/cgroup`, and its `cpu.max` is `/sys/fs/cgroup/<path>/cpu.max`. That covers a container's private namespace (`0::/`, measured with `--cpus 2.5`: `250000 100000`), `--cgroupns host` (`0::/system.slice/docker-<id>.scope`, the root file missing) and the host (`0::/user.slice/…/session-5.scope`, `max 100000`; the root group has no `cpu.max`). `max` means no quota; a missing file means no quota; ⌈quota ÷ period⌉ caps the count. No `0::` line (cgroup v1, or a hybrid without v2) means "quota not read (no cgroup v2)", said in the log line and the diagnostic; a v1 branch is written once a machine needs it (152: the diagnostic shows the version; the VM is v2, Docker 26.1.5 with the systemd driver) (R8).
- *Physical cores* (transform worker only) = the distinct `topology/core_cpus_list` among the affinity's CPUs, or `thread_siblings_list` (the same content under the old name) where the first is missing, then capped by the same ⌈quota⌉; without either file, the logical count, said so (R8).
- *Memory* (transform worker only): the own group's `memory.max` if it is a number, else `MemAvailable` from `/proc/meminfo` at start (D7).
- *Failures* (R10): a file that exists but cannot be parsed (a `cpu.max` that is not `max|N N`, a topology list or `memory.max` that is not a list or a number) stops the start with a message that names the file and its content; a missing file falls back as above, with a note in the log line.
- Not psutil (absent in the transform venv, only transitive in the crawler's; the note, section 2): about 25 lines in each module.
*Alternative:* `nproc` in shell: ignores the quota and obeys `OMP_NUM_THREADS` (measured, the note, section 3).

**D3. Crawler: `src/modama_crawler/cpus.py`.** Interface:
- `usable(root: Path = Path("/")) -> Usable`, a frozen dataclass with `affinity: int`, `quota: float | None`, `cgroup_v2: bool` and the property `cpus` (min of the two, the quota rounded up). `root` is the seam for tests (fake `sys/fs/cgroup` and `proc/self/cgroup` under `tmp_path`).
- `set_num_threads_env(n: int = 1)`: LiberTEM's context manager (`src/libertem/common/threading.py:240-284` at `d6aa0fa`), copied without the numba branch (lines 260-262, 268-269; numba is in neither environment, the note, section 2). It sets `MKL_NUM_THREADS`, `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS` and restores the old values afterwards. The module's header carries LiberTEM's copyright line ("Copyright (c) 2024 LiberTEM creators") and the MIT permission notice, with the source URL and commit; the crawler is MIT too (`python/crawler/LICENSE`).
- Users: `extraction.default_workers()` becomes `min(cpus.usable().cpus, MAX_WORKERS)`. `cli.py` enters `set_num_threads_env(1)` once in `cmd_crawl` and `cmd_records`, before the heartbeat thread starts, around the walk and the extraction together, and leaves it after the heartbeat has stopped; `walk.py` and `extraction.py` do not touch the environment (R4). `cli.py` stays the only module that reads or writes it, as the code map says, and no other thread runs while it is changed: libpq reads its `PG*` defaults with `getenv` during the heartbeat's connect, and glibc's `setenv` is not safe against a concurrent `getenv`.
- `cli.py` logs the budget (D8) and has a command `cpu-budget` that prints it with its reasons, for the diagnostic (D11).

**D4. Crawler: the variables are in the parent's environment around the pools' lifetime, not set in the worker's initializer.** Spawned workers then have them from `exec` on, before any import (unpickling the initializer imports `modama_crawler.extraction` and `.formats`), and replacement workers after 100 tasks get them too (LiberTEM's pattern, its docstring: the other methods "only limit the number of threads that are _used_, not the number of threads that are created"). The parent imports no numpy (measured, the note, section 6), so the variables do not shrink a pool the parent uses (LiberTEM #1053 was that leak); the context restores them at the end.
*Alternative:* three `os.environ` lines in `_limit_memory`: shorter, but depends on nothing importing numpy before the initializer runs, and @weber chose the copy ("let's just copy the few lines here").

**D5. Search stack: one start script, not patches of the services' code.**
- *(a) Start script* `prototypes/search-stack/cpu-budget/budget.py`, standard library only, copied into the two images that use it (`COPY` in the warehouse image of D9 and in `search-api.Dockerfile`, so that the script travels with the patches it depends on and needs no bind mount of the source tree; R14). Commands: `budget.py transform -- celery worker --queues transform` and `budget.py search-api -- uvicorn src.data_commons_search.main:app --host … --port …`. It computes the budget, logs it, sets `EMBEDDING_THREADS=T`, `RAYON_NUM_THREADS=T`, `OPENBLAS_NUM_THREADS`, `OMP_NUM_THREADS`, `MKL_NUM_THREADS` to 1 in its own environment and `exec`s the command with `--concurrency P` or `--workers P`. For the transform worker it `exec`s through `/entrypoint`, so the entrypoint's wait for the broker still runs (it does so only for `celery` and `scheduler` commands; it runs `python …` commands directly). Celery's children, every batch process and uvicorn's workers inherit the variables. Runs on the images' Python 3.13. `budget.py explain transform|search-api` prints the same budget with its reasons and exits (D11).
- *(b) Patch the services' code* to compute T when `EMBEDDING_THREADS` is unset: the batch needs P in the environment anyway (the effective `--concurrency` is not visible to it), and it is too late for OpenBLAS, which reads its variable when numpy loads, at `transform_core.py:10`. A larger patch to upstream code for each upgrade, twice.
- *Lean: (a).* The patches stay small and are candidates upstream. *Strongest argument against:* the script replaces a plain `command:` with our own program in front of Celery and uvicorn; if it fails, the service does not start (D10, Risks).
- Interface: `machine(root: Path = Path("/")) -> Machine` (logical CPUs, cores, quota, cgroup v2 or not, memory and its source), `transform(machine, *, slots, per_process, processes=None, threads=None) -> Budget`, `search_api(machine, *, workers=None, threads=None) -> Budget` (P, T, the reasons and the active overrides for the log line), `main(argv)`. Tests with a fake `/sys` and `/proc` under `tmp_path` and a patched `os.sched_getaffinity`; they need no Airflow (`main` imports `airflow.configuration` for `transform` only).
- No LiberTEM copy here: the script sets the variables once for the whole process tree and `exec`s, so nothing is to be restored.
- The crawler keeps its own `cpus.py` (another package and image); the two counts share the scenarios and fake files, not code (Risks).

**D6. Transform worker: the task limits, and P capped by them** (@weber, 2026-11-12: "without any settings it should run the full thing, but here (devvms running etc) we restrict it. 16 sounds sensible").
- *Slots* = min(`core.max_active_tasks_per_dag`, `core.parallelism`), both read from `airflow.configuration.conf`; both are in the log line (R2). P = min(cores, ⌊memory ÷ per process⌋, slots).
- *Without settings the machine governs.* The base compose file sets both limits in `x-airflow-common`'s environment from one compose variable, `AIRFLOW__CORE__MAX_ACTIVE_TASKS_PER_DAG` and `AIRFLOW__CORE__PARALLELISM` from `${AIRFLOW_TASK_LIMIT:-1024}`, so that the scheduler and the worker see the same value (YAML anchors do not cross files, and a line under one service alone splits them; R1). 1024 is a ceiling no machine of ours reaches, not a number per machine. The dev server's `staging.env` sets `AIRFLOW_TASK_LIMIT=16`, documented in the runbook; the start script reads it as any other setting. On the dev server that gives 16 × 1 on 24 cores, leaving 8 for PostgreSQL and OpenSearch.
- *Queued tasks.* With a ceiling of 1024 the scheduler queues every batch of a run at once, up to 1024, but only P run; a batch that waits longer than `task_queued_timeout` (600 s) is retried and then failed (`scheduler_job_runner.py:3017-3064` in the image). A run as long as F16's 19 hours, with many batches per process, would lose the batches at the back; with today's 16 the queue never holds more than 16. (Found while folding in the decision; read from the image, not run; task 3.5 shows it.) Options:
  - *(i) Pools.* The DAG's two mapped tasks get a pool each (`transform` and `filemeta`; a one-line patch per task to upstream's `transform_index.py`), sized by what consumes them: the start script sets `transform` to P (`airflow pools set`, through the database connection the worker has from `x-airflow-common` today), `init-airflow.sh` sets `filemeta` to the default worker's concurrency. Batches beyond the pool wait as scheduled, not queued, so the timeout does not apply (Airflow's documented pool behaviour; to be shown by task 3.5); the pools and their sizes show in Airflow's UI, which suits "not arcane magic".
  - *(ii) A longer `task_queued_timeout`*, for example a day: two lines in the base file, no patch. But the setting also sets the lifetime of the workload token sent with every task (`config.yml:2800-2806` in the image), and a lost task is noticed a day late.
  - *(iii) A ceiling close to P*, for example `AIRFLOW_TASK_LIMIT` defaulting to the cores: the scheduler cannot see the worker's P, so the number would again be one per machine.
  - *Lean: (i).* It uses Airflow's own mechanism for "at most n of these at once" and keeps the queue at P. *Strongest argument against:* two more lines of patch to upstream code, and the transform worker writes to Airflow's database at start; with two transform workers they would overwrite each other's pool size (there is one).
- *Alternatives to the cap:* let T absorb the rest (24 ÷ 16 → 1 now; a rule like 12 × 2 would use all 24); for the measurement on the dev server to settle (task 6.4).

**D7. Memory as the second limit, from a measured peak** (decision 153: measure one whole batch at the VM's batch size; R3).
- *Measured* (2026-11-12, `scratchpad/batchmem/batch.py`; command and numbers in "Measurement of one batch" below): one whole batch of 250 events, run as `run_transform_batch` runs it (load, transform, validate, embed, bulk body), with the writes replaced. Peak RSS (`VmHWM`): 0.69 GB with the VM's records (19 to 62 tokens per text), whatever the threads; 2.33 GB at about 190 tokens; 5.30 GB at the model's 512 tokens, the same with 1 thread (5.31 GB). The peak follows the texts' length and the sub-batch of fastembed's `embed` (256 texts by default): at 512 tokens a sub-batch of 32 peaks at 1.40 GB, of 64 at 2.47 GB, of 256 at 5.30 GB (time for the batch 48.0, 49.3 and 45.0 s). With 256 it also grows with the batch, to about 9 GB (8.99 GB for 1,000 texts of 512 tokens, 9.05 GB for 2,000); with 32 it does not, 1.42 GB for 2,000 (the cause of the growth was not found; fastembed's pooling copies, it keeps no views). Staging's 2.3 to 4.4 GB at batch 2,000 (RSS; F16, the staging probe log) fits texts of a few hundred tokens. The worker's slot adds its Airflow supervisor process, 0.25 GB (`airflow supervisor` in the running worker, read only).
- *Lean:* bound the peak instead of predicting the texts: patch 0002 also passes a fixed sub-batch of 32 to `embed` (`batch_size`, which fastembed documents as "higher values will use more memory, but be faster"), and the per-process figure is the measured worst case for it, 1.42 GB + 0.25 GB, about 1.7 GB, one constant in `budget.py`, the same for batches of 250 and 2,000. *Strongest argument against:* a second change in upstream's embedding call, and smaller sub-batches cost time (7 % at 512 tokens and batch 250; for short texts and at T > 1 to be measured, task 6.3).
- *Alternative:* keep fastembed's 256 and take its worst case, which then depends on `CELERY_BATCH_SIZE` (5.6 GB per process at 250, 9.3 GB from 1,000 on): safe, but the VM gets P = 1 (below), and the constant becomes a table by batch size. Or drop the term: 8 × 5.6 GB with long texts is more than the VM has.
- *What memory:* the container's `memory.max` if set, else `MemAvailable` at start, which leaves out what the services running at that moment use (the review: `MemTotal` is shared; the VM has 24.6 GB in total, 9.1 GB available with the stack up, `free -m` 2026-11-12). The log line says which. A service that grows later, or starts after the worker, is not counted (Risks).
- *The VM's P, derived:* 8 cores, 9.1 GB available: with the lean ⌊9.1 ÷ 1.7⌋ = 5, so 5 × 1 (the number @weber accepted, now from the measurement; with more memory free at start, up to 8 × 1). Without the bound ⌊9.1 ÷ 5.6⌋ = 1, so 1 × 8. The dev server is not limited by memory either way (251 GB in total).

**D8. Overrides and the log lines** (2.4, "The operator stays in control": overrides few, named, documented; R1, R11).
- Overrides, each documented in the stack's README (task 5.4) with when to use it: crawler `MODAMA_CRAWLER_EXTRACT_WORKERS` (as today); transform `TRANSFORM_PROCESSES` and `EMBEDDING_THREADS` (patch 0002's name); search API `WORKERS` (upstream's name; our Dockerfile clears upstream's `ENV WORKERS=6`, so that only an operator's value counts as set) and `EMBEDDING_THREADS`; the dev server's `AIRFLOW_TASK_LIMIT` (D6). The BLAS threads have none (nothing to measure there). `perf/docker-compose.perf.yml` sets `TRANSFORM_PROCESSES` from `PERF_CONCURRENCY` instead of the command.
- Each log line names an active override with its variable. The crawler's goes to stderr at INFO, except under `records --verbose`, which logs errors only (`cli.py:509-510`; R11); the transform worker's and the search API's go to the container log before their banners.

**D9. Patch 0002 in the image.** As `search-api.Dockerfile`: a `warehouse-airflow.Dockerfile` that copies `/opt/airflow/project/src` and `/opt/airflow/dags` from the built airflow image into a busybox stage, applies `patches/warehouse/*.patch` (a patch that does not apply fails the build), copies the result back and adds `budget.py` (D5). Since the base is itself built by compose, it is referenced through `additional_contexts` with `service:` (Docker Compose 2.26.1 in the VM; to be confirmed that it builds in order) or the airflow image is built by our Dockerfile from the submodule's context; decided in task 3.1 by what builds. The search API gets `patches/search-api/0002-embedding-threads-setting.patch` (a field `embedding_threads: int | None = None` in `config.py`, `threads=settings.embedding_threads` at `mcp_server.py:29`) and `budget.py` in the same way.

**D10. When the start script fails** (R10). A malformed file (D2) or an override that is not a positive integer stops the script with a message naming the file or variable. The services have `restart: unless-stopped`, so the container restarts in a loop and its health check never runs; meanwhile the harvest and the scheduler go on and the transform batches wait in the `transform` queue with no consumer, as the default queue did in F17. The loop and the message show in `docker compose ps` and the logs, and the diagnostic (D11) prints the same message without starting anything.

**D11. The diagnostic: `prototypes/search-stack/cpu-budget.sh`** (2.4, "The operator stays in control": "any complex thing the operator of the service needs to know when setting it up should be supported by appropriate helpers"; @weber, 2026-11-12: "a helper script to check the local machine with everything we need to know"). It takes the deployment as the `up` scripts do (the test deployment by default; `staging` adds `staging.env` and `docker-compose.staging.yml`) and prints:
- the machine as Docker sees it: `docker info` cgroup version and driver, CPUs, memory (answers 152 wherever it runs);
- per service, from `docker compose run --rm --no-deps <service> <explain>`, so in a container with that service's limits (checked in the VM with a throwaway project: `cpus: 2.5`, `cpuset: "0-3"`, `mem_limit: 1g` reach the container as `250000 100000`, `0-3`, `1073741824`): the crawler (`modama-crawler cpu-budget`), the transform worker (`budget.py explain transform`) and the search API (`budget.py explain search-api`). Each prints its inputs (logical CPUs of the affinity, cores, cgroup version, quota, memory and its source, the task limits), the result P × T, the active overrides, and one line per override on how to set it.
The numbers come from the same functions the services run at start, so the diagnostic shows what the next start chooses; the running services' choices are their log lines.
*Lean: this script, not env variables to maintain.* @weber's earlier "the whole code should do it right by itself" (114) and the new "admin gets help … easy way to influence" meet here: the code chooses, the script shows the choice and its reasons, and the few overrides of D8 are the easy way to influence it. *Strongest argument against:* a script and three `explain` paths to keep in step with the services, and a `docker compose run` of the airflow image takes a few seconds (importing `airflow.configuration` alone 2.9 s); mitigated by `explain` calling the same functions as the start.

## Measurement of one batch (decision 153)

Throwaway containers of `search-stack-airflow:3.3.2` (the transform venv) on the stack's network, the fastembed cache volume read-only, the warehouse read with the read-only role `chain_reader`; the running project `search-stack` was not stopped, restarted or rebuilt, and nothing was written to it. `batch.py` (in the session's scratchpad, `…/scratchpad/batchmem/`; committed as `perf/batch-memory.py` by task 3.0) loads the VM's 17 real events (`load_batch`, every closed run; about 1,500 characters of XML each), repeats them to N with distinct identifiers, and runs `transform_batch_impl` with psycopg's connection replaced by a fake that counts the statements and the OpenSearch bulk replaced by the serialization opensearch-py does. Optionally it appends K filler words to each embedding text, passes `threads=T` to `TextEmbedding` (what patch 0002 does) or a sub-batch size to `embed`.
