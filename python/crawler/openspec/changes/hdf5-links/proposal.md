# Proposal

## Why

@weber, 2026-11-13 (321): "A compound HDF5 dataset, with scan_00026_master.h5 as the master hdf5 file that references the others. Such compound HDF5 datasets should be one dataset and record, anchor is the master file. Usually called master, but that is not a guarantee. One recognizes them only from referencing the other files." The five points below were approved "with this as a typical example": the Eiger master is an example of a rule (an HDF5 file whose external links or virtual-dataset sources name HDF5 files of its folder), not the whole ask.

Today each file of such an acquisition is a record of its own: the master's summary is the largest arrays of its calibration (316: `entry.instrument.detector.detectorSpecific.flatfield [2167, 2070] <f4, …pixel_mask [2167, 2070] <u4, …detectorModule_000.flatfield [256, 1024] <f4`), its 441 links are not in its values at all (`walked` lists hard links only), and each of the 45 data files is a record that does not say it belongs to a scan. Serves R30 (findable by what the data is: one acquisition, one result), R22 (incomplete data seen, not hidden: the dangling links are counted).

The real case (private sample `.claude/field-tests/samples/scan_00026_master.h5`, opened with h5py without following a link; shape and names only here): a DESY ptychography scan, Eiger 4M master of 91 MB, 684 objects (28 groups, 656 datasets), no soft links, no virtual datasets, no title and no root `file_time`; the group `/entry/data` holds 441 external links `data_000001` … `data_000441`, each to `/entry/data/data` in `scan_00026_data_000001.h5` … `scan_00026_data_000441.h5`, stored in HDF5's dense form (stored order: the names' hashes). The folder (`eiger4m_01` in the October listing) holds the master and `…_000001.h5` to `…_000045.h5`: 396 links dangle. The link messages are written at the end of the file (offsets 87.0 to 87.2 MiB of 87.2): a format reading a file's first bytes cannot see them.

## What Changes

- **Links in the values (every HDF5 file).** The HDF5 walk lists each external link (link name, target file name, target path) and each virtual dataset's sources in other files (source file name, source dataset path) as written, without opening or following them. Consecutive links that count up are one entry, not 441: `entry.data.data_000001 … data_000441.external_link: ["scan_00026_data_000001.h5 … scan_00026_data_000441.h5", "/entry/data/data"]`. Counts go to `mapped_metadata`: `external_links 441`, `found 45`, `dangling 396` (design D2, D3).
- **One dataset, anchored at the linking file.** In a folder with two to 200 HDF5 files, recognition lists the links of its `*.h5` files in worker processes, bounded by counts and killed past 60 s (design D1, D5). An `.h5` file whose links name other HDF5 files of the folder, and which no other `.h5` file names (back-links from its own targets aside), anchors one dataset with those that exist as members, whatever the master's name (design D4). One new format, `common/hdf5links` (priority 62, before `common/nexus`, `common/hspy` 61 and `common/hdf5` 60); NeXus, `.emd` and `.hdf5` anchors go to the backlog (first review, SHOULD 5; second review, S4).
- **Dangling links are normal**: no warning, a count in the values and at the end of the summary line (331).
- **The linked data described from the members**: the first existing target of each run of links gives the linked dataset's `shape` and `dtype` under the link's name (`entry.data.data_000001.shape [N, 2167, 2070]`), read from the member, never through the link. No array is read, so no filter plugin is needed (the Eiger data files are bitshuffle/LZ4-compressed). The members' own walks are left for later: nothing would render them (decision 234; review, SHOULD 9).
- **Summary line** from the anchor: 316's rule as amended by 324 to 326, plus the detector's `description` first (Q5, lean) and the counts last (331). The real case would read `<description>, entry.data.data_000001 [N, 2167, 2070] <u4, entry.instrument.detector.detectorSpecific.flatfield [2167, 2070] <f4, entry.instrument.detector.detectorSpecific.pixel_mask [2167, 2070] <u4, external_links 441, dangling 396`, then the core's `…, 46 files, … in eiger4m_01/` (design D7).
- **Core (recognition)**: `Directory.inspect(entries, fn, budget)` runs a format's function on files of its folder in one pool of worker processes per crawl, one folder at a time, each file opened without following a symlink and only if it is a regular file, through a file object with a byte budget per file, with a time limit enforced from outside; a file that times out, fails or kills its worker is retried next crawl (design D5). `Directory.read` opens files the same way. ADDED and MODIFIED in `specs/recognition`.

## Assumptions and leans (to be agreed before the code)

- **A1 Depends on 311 fixed** (332): later formats see only unclaimed entries. Also on `common-pydata` archived, so that `specs/formats/pydata` exists.
- **A2 libhdf5 never runs in the crawler's own process for recognition** (first review, MUST 1 and 2): a malformed file that crashes or hangs libhdf5 must not stop or hang the crawl, and h5py's global lock would serialise the walk's 32 threads. One pool of worker processes per crawl, one folder at a time (second review, M1: a pool per call could reach 256 processes, about 12 GB); a call waiting for the pool blocks its walk thread.
- **A3 Bounds by counts, the same on every crawl** (second review, M2; Q15): two to 200 HDF5 files per folder, at least one `.h5` (the largest folder with a `*master*` file in the October listing holds 170); 5,000 objects and links and 4 MiB per file (the real master: 1,125 and 483 KB); time only from outside, the worker killed at 60 s (the real master needs 968 reads, 15 to 42 s on NFS). Each cut is recorded.
- **A4 A target is matched by its file name in the folder**: a bare name as it is, an absolute path by its last part, as HDF5 itself looks it up when the absolute path does not exist (HDF5 reference manual, `H5Lcreate_external`; Q4, 341); a relative path with a folder part (`../x.h5`, `sub/x.h5`, `./x.h5`) or a printf-style virtual-dataset name (`%b`) is counted `elsewhere`, never looked up. A name is only compared, never joined into a path and opened.
- **A5 Self-links, back-links, cycles, shared targets** (review, SHOULD 7 and 8): a link to the file's own name is listed but no target; a link back from a member whose only target is the anchor does not stop the anchor; two files each the other's only target stay datasets of their own; a file named by two anchors belongs to neither, and each anchor's basis says so. A member's own targets are not added (no chains: nobody has seen one).
- **A6 `found` and `dangling` by the folder's names** (Q12): the extractor lists the file's folder once (`scandir`) and compares the target names in memory, opening nothing: `found` is a regular file of that name, `dangling` none; an error of the listing fails the extraction, tried again next crawl. Membership is the record's member list.
- **A8 Only `*.h5` files are listed and may anchor** (second review, S4; Q16): in folders with two to 200 HDF5 files, 51 % are `.emd`, which hold many objects and have never been seen as masters.
- **A7 Fixtures are generated by h5py at test time** (as `generate.py` does for the other HDF5 fixtures; `ExternalLink`, `VirtualLayout`), shaped after the real master's structure (names and shapes, no values). The real master stays private; a cut of it would need its owner's agreement (Q11).

## Out of scope

Following or opening anything through a link (`common-pydata`, "Never read outside the file", stays); reading arrays or chunks; NeXus, `.emd` and `.hdf5` anchors and their links (backlog); the members' own walks in the values (backlog, with a way to render them); HDF5 external raw storage (`H5Pset_external`: raw files, not HDF5; already given shape and dtype only); targets in other folders (claims stay within the directory, recognition spec; architecture A); soft links (they stay unlisted); chains of links; Eiger-specific values (frame counts from `nimages`, `ntrigger`); HyperSpy and MATLAB 7.3 anchors; the HDF5 files of a collapsed folder (never recognised, Q3).

## Behaviour towards the user

- An Eiger acquisition (master and data files in one folder) is one record instead of 46, anchored at the master; the data files' 45 records disappear (deleted records for the harvester). Its summary line names the detector, the linked data's structure and how many links dangle.
- Every HDF5 file's values (and the record's second description) gain its external links and virtual-dataset sources as written, summarised by runs, and the counts in `mapped_metadata`; the summary line of an HDF5 file with links ends with the counts.
- Recognition opens the `.h5` files of folders with two to 200 HDF5 files in worker processes, once per change of the folder's listing and once per release of any format distribution or of the crawler (the rules' fingerprint covers them all): 2,855 files in 141 folders in the October listing, about 10 to 45 minutes per full recognition (design D5, Q14). A file whose listing times out or fails stays its own record for that crawl, with a warning, and is tried again next crawl.
- The extractor identity changes: the next crawl extracts every dataset again.

None.
