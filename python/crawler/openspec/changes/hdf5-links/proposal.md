# Proposal

## Why

@weber, 2026-11-13 (321): "A compound HDF5 dataset, with scan_00026_master.h5 as the master hdf5 file that references the others. Such compound HDF5 datasets should be one dataset and record, anchor is the master file. Usually called master, but that is not a guarantee. One recognizes them only from referencing the other files." The five points below were approved "with this as a typical example": the Eiger master is an example of a rule (an HDF5 file whose external links or virtual-dataset sources name HDF5 files of its folder), not the whole ask.

Today each file of such an acquisition is a record of its own: the master's summary is the largest arrays of its calibration (316: `entry.instrument.detector.detectorSpecific.flatfield [2167, 2070] <f4, …pixel_mask [2167, 2070] <u4, …detectorModule_000.flatfield [256, 1024] <f4`), its 441 links are not in its values at all (`walked` lists hard links only), and each of the 45 data files is a record that does not say it belongs to a scan. Serves R30 (findable by what the data is: one acquisition, one result), R22 (incomplete data seen, not hidden: the dangling links are counted).

The real case (private sample `.claude/field-tests/samples/scan_00026_master.h5`, opened with h5py without following a link; shape and names only here): a DESY ptychography scan, Eiger 4M master of 91 MB, 684 objects (28 groups, 656 datasets), no soft links, no virtual datasets, no title and no root `file_time`; the group `/entry/data` holds 441 external links `data_000001` … `data_000441`, each to `/entry/data/data` in `scan_00026_data_000001.h5` … `scan_00026_data_000441.h5`. The folder (`…/raw/scan_00026/eiger4m_01/` in the October listing) holds the master and `…_000001.h5` to `…_000045.h5`: 396 links dangle. The link messages are written at the end of the file (offsets 87.0 to 87.2 MiB of 87.2): a format reading a file's first bytes cannot see them.

## What Changes

- **Links in the values (every HDF5 file, single or grouped).** The HDF5 walk lists each external link (link name, target file name, target path) and each virtual dataset's sources (source file name, source dataset path) as written, without opening or following them (the security rule of `common-pydata`, "Never read outside the file", stays). Consecutive links that differ only in a counting number are one entry, not 441: `entry.data.data_000001 … data_000441.external_link: ["scan_00026_data_000001.h5 … scan_00026_data_000441.h5", "/entry/data/data"]`. Counts go to `mapped_metadata`: `external_links 441`, `found 45`, `dangling 396` (design D2, D3).
- **One dataset, anchored at the linking file.** In a folder with two or more HDF5 files, recognition lists the links of each one (bounded, design D5); a file whose external links or virtual-dataset sources name other HDF5 files of the folder by a bare file name becomes one dataset with those that exist as members, whatever the names (design D4). New formats `common/hdf5links` and `common/nexuslinks` (priority 62, before `common/nexus`, `common/hspy` 61 and `common/hdf5` 60), one per type of the anchor, since a format gives its datasets one type.
- **Dangling links are normal**: no warning, a count (`dangling`) in the values and in the summary line.
- **Members described from themselves**: the first existing target of each run of links gives the linked dataset's `shape` and `dtype` under the link's name (`entry.data.data_000001.shape [N, 2167, 2070]`), read from the member, never through the link; each member's own walk goes to a values section `members`, bounded together (design D6). No array is read, so no filter plugin is needed (the Eiger data files are bitshuffle/LZ4-compressed).
- **Summary line** from the anchor, by 316's rule unchanged (three largest arrays, then `file_time`), which now finds the linked data; plus, as leans for @weber (Q5, Q6): a detector's `description` first and the counts last. The real case would read `<description>, entry.data.data_000001 [N, 2167, 2070] <u4, entry.instrument.detector.detectorSpecific.flatfield [2167, 2070] <f4, entry.instrument.detector.detectorSpecific.pixel_mask [2167, 2070] <u4, external_links 441, dangling 396`, then the core's `…, 46 files, … in eiger4m_01/` (design D7).
- **Core (recognition)**: a format may read a file of its folder at any offset through a file object charged to the call's byte budget (`Directory.opened`), so that h5py can list links during recognition; a format may declare a larger byte budget than the core's 1 MiB (design D5). Both MODIFIED in `specs/recognition`.

## Assumptions and leans (to be agreed before the code)

- **A1 Collection: `common`, part `pydata` (Q1).** The mechanism is plain HDF5 (external links, virtual datasets), written by h5py, NeXus writers, Dectris, MATLAB, and read by every HDF5 reader; only the detector's `description` (Q5) is a NeXus convention, and NeXus is already in `pydata`. Strongest argument against: the case that motivates it is a detector's; if more Eiger-specific behaviour comes (frame counts from `nimages`), it belongs in `em`, which can subclass these formats.
- **A2 Depends on 311 fixed first.** The runner still lets a later format see entries an earlier one claimed (`formats/__init__.py`, `run_post`: `d.entries` is never narrowed; the later claim is rejected with "already claimed by"), although the spec `recognition` says they "SHALL NOT be available". With this change, `common/nexus` and `common/hdf5` would yield a dataset for each member that `common/hdf5links` claimed, and each would be rejected with a warning: 45 false warnings for the real folder, the outcome right. Lean: fix 311 first, as a small change of its own (later formats see only unclaimed entries and child datasets), then this one (Q2). Working around it inside the pydata formats is not possible: a format cannot see another's claims.
- **A3 Grouping is decided by recognition, which opens each HDF5 file of a folder with two or more** (one HDF5 file alone has nothing in its folder to link to). Measured: listing all links of the real master reads 967 times, 483 KB; a small data file (one 3-D dataset, two groups) 23 times, 8 KB. On NFS (16 to 43 ms a round trip) the real folder costs about 2,000 reads, 30 to 90 s in one format call, once per change of its listing. The October listing has 309 folders with two or more HDF5 files by name (13,336 files; `.emd` included, which are HDF5 by content), 305 of them with at most 200 (8,548 files). Every release of `modama-formats-common` recognises the whole tree again (README, "How it works"), so this cost recurs with each release (Q10).
- **A4 Bounds, recorded where they cut**: at most 200 HDF5 files per folder (the largest folder with a `*master*` file in the October listing holds 170); at most 5,000 objects and links listed per file (the extractor's object limit); a byte budget of 32 MiB per call. Past the file bound, the folder's HDF5 files stay single datasets and the folder gets a warning; past the object bound, a file groups with the targets found so far and its dataset gets a warning; past the byte budget, the core discards the format's result for the folder with a warning (as for every format) (Q10).
- **A5 A target is matched by its bare file name only.** A link whose file name has a folder part (`../x.h5`, `sub/x.h5`, `/beamline/…/x.h5`) or a printf-style virtual-dataset name (`%b`) is listed as written, counted as `elsewhere`, never looked up (Q4, Q7).
- **A6 Direct targets only, each member in one dataset.** An anchor is a file that names at least one HDF5 file of the folder and is named by none; its members are the files it names. A file named by two anchors belongs to neither, stays its own dataset, and carries a remark naming both (an accidental split beats an accidental grouping, R30, decision 2026-10-16). A member's own links are listed in its walk; its targets are not added (no chains: nobody has seen one) (Q8).
- **A7 Fixtures are generated by h5py at test time** (as `generate.py` does for the other HDF5 fixtures; `ExternalLink`, `VirtualLayout`), shaped after the real master's structure (names and shapes, no values). The real master stays private; a cut of it (structure only, values zeroed) would need its owner's agreement (Q11).

## Out of scope

Following or opening anything through a link (`common-pydata`, "Never read outside the file", stays); reading arrays or chunks; HDF5 external raw storage (`H5Pset_external`: raw files, not HDF5; already given shape and dtype only); targets in other folders (claims stay within the directory, recognition spec; architecture A: "an HDF5 external link to `../other/` is out of reach"); soft links (listed by nobody yet; they stay unlisted); chains and cycles of links (A6); Eiger-specific values (frame counts from `nimages`, `ntrigger`); a link format for HyperSpy and MATLAB 7.3 files (they are not seen to link); the crawl of a collapsed folder (its HDF5 files are never recognised, Q3).

## Behaviour towards the user

- An Eiger acquisition (master and data files in one folder) is one record instead of 46, anchored at the master; the data files' 45 records disappear (deleted records for the harvester). Its summary says what is linked and how many links dangle; its type is the master's (`application/vnd.hdfgroup.hdf5`, or `application/x.nexus` for a `.nxs` anchor).
- Every HDF5 file's values (and the record's second description) gain its external links and virtual-dataset sources as written, summarised by runs, and the counts in `mapped_metadata`.
- Recognition opens the HDF5 files of folders with two or more of them, once per change of the folder's listing and once per release (A3).
- The extractor identity changes: the next crawl extracts every dataset again.

## Capabilities

### New Capabilities
None.

### Modified Capabilities
- `formats/pydata` (in the change `common-pydata`, not yet archived; archive it first): links listed in the values; linked HDF5 files as one dataset; the linked dataset's members, summary line and bounds; the modified requirements "Nothing is read from outside the file", "The walk of an HDF5 file is bounded" (its scenario "External links are not followed": the link's name is now listed), "An HDF5 file without a title is summarised by its structure".
- `recognition`: a reader at any offset for a format's own folder's files; a byte budget a format may declare.
