# Proposal

## Why

Improving a format's recognition or extraction and seeing the result in the search takes a whole crawl today: on staging (run 3, 2026-11-11) the walk took 17 minutes, the crawl 1 h 17 min, the harvest 5 h 14 min, the indexing hours more. @weber asked on 2026-11-12 for commands that give fast turn-around instead, without waiting for the whole re-crawl:

1. re-run extraction, harvest and indexing for a specific path (to test an updated extractor);
2. the same for all files of a specific kind (to make an improved format available everywhere);
3. crawl, recognise, extract, harvest and index a whole subtree on demand, for example `adhoc/libertem/libertem-test-data`.

I read the three as rules, not as single cases. In (1) and (3), "path" is a canonical path in the glossary's sense (`/CONTEXT.md`: the same on every way of access, `adhoc/testproject/session2`), which is also how the crawler names datasets: an anchor such as `/adhoc/libertem/libertem-test-data/dm/a.dm4` is relative to `MODAMA_DATA_ROOT`. In (2), "kind" is a format, named by its id as in `--select` (`em/dm4`; there is no `em/dm`: DM3 and DM4 are `em/dm3` and `em/dm4`, and they share one extractor).

Today's `crawl --root PATH` does not help with (1) or (3), and it is a trap. It treats PATH as the whole repository: anchors become relative to PATH, so the identifiers change (`walk.py:354`), and the store deletes every dataset, listing and record it did not see (`store.py:425`, `:438`, `:459`). Staging's other workaround, `--root` on the data root with exclusions (`stagingconf/libertem.toml`), keeps the identifiers but deletes everything outside the subtree too. It also changes the rule set (`selection.fingerprint` includes the exclusions), so the next full crawl recognises the whole tree again and gives every record a new datestamp, which means a full re-harvest.

Request (2) already works without a new command: bumping a format's `extractor_version` makes the next crawl extract that format's datasets again and nothing else, and only records whose content changed get a new datestamp. That behaviour is the scenario "A new extractor version" in the open change `em-formats-and-extraction`. What is missing there is the documentation and a way to run it now rather than at 19:00 (design D7).

Serves R14 (developing a format is easy for humans and agents), R10 (a re-crawl only does work for what changed), R9 (inspect the outcome for one directory, now with harvest and search included) and the request of 2026-11-12, to be recorded as R41 (task 1.1).

## What Changes

- **New option `modama-crawler crawl --path PATH`**: a *subtree crawl* of the directory PATH (a canonical path; a leading and a trailing `/` are accepted). It walks only that subtree and recognises and extracts it from scratch: nothing is taken over from the stored state, and no extraction is reused, so an extractor changed without a version bump runs again. Within the subtree it brings datasets, members and records up to date, and records of datasets that disappeared are deleted. Outside the subtree, nothing changes, datestamps included; a sibling whose name starts the same (`adhoc/a/bc` next to `adhoc/a/b`) is outside. Identifiers are the same as a full crawl's. A file as PATH stands for its directory.
- PATH must be a directory that a full crawl would enter: valid UTF-8, below the data root and not the data root itself, with no symlink on the way, not excluded by `[crawl] exclude`, not inside a collapsed directory (environment, `.git`, Zarr store), and every directory down to it listable; and the data root must be the one of the last crawl of the whole tree. Otherwise the crawl exits with status 2 and an error naming the reason, and records nothing. PATH itself may be collapsed (a Zarr store): it becomes one dataset, as in a full crawl.
- If PATH cannot be listed when the walk reaches it (after the check passed), the crawl fails with status 2 and its run is `failed`; nothing under PATH is deleted.
- A subtree crawl takes the same crawl lock, reacts to SIGTERM in the same way (run `failed`, status 143, no record changed) and starts the same harvest when it finishes. Only the records it changed are harvested and indexed, because the harvest is incremental (`from` = the end of the last closed harvest) and the harvest DAG indexes only the runs it harvested. In the search stack it runs as a one-off container of `crawl-timer` (`docker compose run --rm`), which leaves the timer running.
- **Runs record their subtree.** `crawl_runs` gets a `scope` column (NULL for a full crawl), and `runs` shows it. Only full crawls count for the timer's catch-up and for `modama-chain`'s freshness time T. A subtree crawl says nothing about the rest of the tree. The column is the schema's first change; with the change `schema-migrations` it becomes migration 0002, whichever ships first (design D5).
- The next full crawl recognises a crawled subtree again: the subtree crawl leaves no stored listings for it. Its extractions are reused, so this costs one more recognition of the subtree, and the state stays consistent even when the subtree crawl ran under other rules (another `--config`, a changed format).
- **Format-wide re-extraction (request 2) is documented, not built**: bump `extractor_version`, rebuild, run `crawl` (design D7, with the alternative `crawl --format ID`).
- `--root`'s help text and the README say that it sets the data root and that a crawl treats it as the whole tree.

Behaviour towards the user: an operator or developer gets `crawl --path`, a `scope` on run lines in `runs` (`… /data  adhoc/libertem/libertem-test-data`), new exit-2 errors for a path that a full crawl would not enter (among them the data root itself, a path that is not UTF-8, and a `--root` other than the full crawls'), and an exit-2 failure when PATH becomes unreadable during the walk. A harvester sees new datestamps only on records under the path whose content changed. A searcher sees those records re-indexed within one incremental harvest and its indexing, provided no harvest is running; otherwise after the running one, which after a full crawl that changed much takes hours (design D6). Records under the path whose datasets disappeared drop out of the crawler's endpoint (the warehouse keeps them, as after a full crawl, until the purge). `modama-chain status` shows subtree crawls but does not move T for them. No change for full crawls, `serve` or `records`.

Out of scope (see "Not now" in `design.md`): several paths in one crawl; a subtree crawl that keeps the stored state (no forced re-run); re-extraction without a walk; tombstones (`deletedRecord`) and the purge; the timer retrying when a subtree crawl holds the lock; the inotify watcher; subtree crawls below a format that adopts datasets of subdirectories (none exists yet); the extractor's identity (a hash of its code instead of a version), which is the walk-through of request 2.

## Questions

The review's findings whose fix is clear are in the design, each with its finding; these have no obvious answer. In the examples, the search stack runs on staging, the deployment's configuration is `/stagingconf/full.toml`, and the folder `adhoc/libertem/libertem-test-data` holds a DM file `dm/a.dm4` and an EMPAD scan `empad/scan.xml` with its raw file `empad/scan_x256_y256.raw` (one dataset of two files in a full crawl).

- **May a subtree crawl use only some of the formats?** (finding M4 in `review.md`) You are improving the DM reader and want it quick: `docker compose run --rm crawl-timer modama-crawler --config /stagingconf/full.toml crawl --path adhoc/libertem/libertem-test-data --select em/dm4`. *Option A, refuse:* the command ends with status 2 and `--select and --ignore cannot be used with --path: a subtree crawl uses the deployment's formats`; you drop `--select`, and the EMPAD scan is extracted too. The price: you cannot try a format that the deployment does not enable on one folder first. *Option B, allow (today's design):* the crawl runs without the EMPAD format, so the scan becomes two records of single files: `scan.xml` with another description, and `scan_x256_y256.raw` with a record of its own and a new identifier; both are harvested. The next nightly crawl makes them one dataset again and deletes the raw file's record in the crawler, but the search keeps it until a purge exists. Each such try leaves one more stray entry in the search. I lean to A.
- **What if a subtree crawl runs with another configuration than the nightly crawl?** (also finding M4 in `review.md`) Say `full.toml` later excludes NFS snapshots (`.snapshot/`), and you forget `--config`: `docker compose run --rm crawl-timer modama-crawler crawl --path adhoc/libertem/libertem-test-data`. The defaults exclude nothing, so `adhoc/libertem/libertem-test-data/.snapshot/hourly.0/dm/a.dm4` becomes a record. *Option A, refuse:* status 2 and `this crawl's configuration differs from that of the last crawl of the whole tree: pass the same --config`. That needs a fingerprint of the configuration stored with every run, next to the rule set (one more column next to `scope`). *Option B, warn:* the crawl runs and prints a warning line; the snapshot's records reach the search and stay there after the next nightly crawl deletes them, as in the question above. *Option C, nothing:* as B without the warning (today's design; the README's commands always pass `--config`). I lean to A: the mistake is easy to make with `docker compose run`, a refusal is fixed by typing the command again, and a stray record in the search has no way out yet.
- **Should reverting an experiment undo it by itself?** (finding H3 in `review.md`; this waits for the walk-through of the extractor's identity, and is not decided in this change) You change the DM reader, run `docker compose run --rm crawl-timer modama-crawler --config /stagingconf/full.toml crawl --path adhoc/libertem/libertem-test-data`, don't like the result, revert the code and rebuild, and forget to run `crawl --path` there again. *Option A, keep the version label (today):* every nightly crawl reuses the experimental description of `a.dm4`, because its extractor is still `em/dm4` version `"2"`; the search shows it until someone runs `crawl --path` there again or the file changes. *Option B, a hash of the extractor's code as its identity:* the next nightly crawl sees that the code differs from the one that wrote the description, and extracts `a.dm4` again: the old description is back by itself. The other side of B: while the changed reader is deployed, a nightly crawl extracts every DM file of the tree again, as after a version bump (about 50 minutes on 8 processes on staging, run 3). The design's D3 has the sequence of events step by step.

## Capabilities

### New Capabilities

### Modified Capabilities
- `crawl`: the index after a crawl is defined for a subtree crawl as well, plus new requirements for the subtree crawl: what it changes, that it recognises and extracts from scratch, which paths it accepts (a canonical path below the data root, under the full crawls' data root, entered by a full crawl), that it fails when its path cannot be listed, and the lock and SIGTERM.
- `crawl-runs`: a run records its subtree, and `runs` shows it.
- `harvest-trigger`: a subtree crawl starts the harvest, and the timer's catch-up counts full crawls only.
- `chain-trace`: the freshness time T counts full crawls only.
- `extraction` (added by the open change `em-formats-and-extraction`, which is archived first): take-over and reuse are stated for a crawl of the whole tree, and a subtree crawl is the exception.

## Impact

- Crawler: `cli.py` (the option, path checks, the run's scope, `--root`'s help), `walk.py` (start the walk at a directory below the root, with anchors relative to the root; the start directory fails like the root when it cannot be listed; the checks on the directories above it), `store.py` (store restricted to a subtree; the `scope` column, as migration 0002 of the change `schema-migrations` or in `ensure_tables` if this change ships first, so the database need not be recreated, design D5; `last_finished` for full crawls only), tests (a new `test_subtree.py` for the subtree crawl's scenarios, `test_locks.py`, `test_runs.py`, `test_trigger.py`, `test_walk.py`).
- `python/search-chain`: T from full crawls only; `scope` read as part of the `crawl_runs` interface.
- Docs: `README.md` (running the crawler, the format-wide procedure, undoing an experiment, the rollback step), `BACKLOG.md`, `design/requirements.md` (R41), the decision log, `/prototypes/search-stack/README.md` (the command as a one-off container of `crawl-timer`, which alone has the Airflow account in production), `docker-compose.staging.yml`'s header and the staging runbook (no more exclusions for a first crawl of a subtree).
- No new dependency.
