# Design

## Context

The motivation is in the proposal. This is what the code does today (crawler branch at 9c9b32b), and it is what shapes the approach:

- **The crawl root is the whole repository.** `walk()` visits its root as `/` (`walk.py:354`), so anchors, and with them identifiers and browse URLs, are relative to the root it is given (`records.py:27`, `:36`: "relative to the data root"). `store()` deletes every dataset, listing and record that is not in the result (`store.py:425`, `:438`, `:459`). So `crawl --root SUBTREE` renames the subtree's records and deletes all the others. Exclusions keep the names but delete the same records, and they enter the rule set (`selection.py:165`), so the next full crawl takes nothing over (`store.py:391`).
- **Reuse.** A full crawl takes over a directory whose listing, and the listings of everything below it, are unchanged under the same rule set (`walk.py:264`, `:302`). It reuses an extraction while extractor id, `extractor_version` and the dataset's stamp are the same and the failure, if any, was not an environment failure (`extraction.py:114`). Extractions are reused across a change of rule set as well (`cli.py:222`). The rule set covers format versions, MIME XML, selection, exclusions and distribution versions, but not extractor versions (`selection.py:138`). Distribution versions are static (`0.0.1.dev0`), and the search stack's image installs the crawler and `modama-formats-em` editable (`crawler.Dockerfile`). So a code change without a version bump leaves both the rule set and the extractor identity as they are, and nothing runs again.
- **Datestamps** move only when a record's metadata changes (`store.py:463`, `:470`).
- **Harvest.** The crawler starts `warehouse_harvest_and_index` with `harvest_urls` = its endpoint after every finished crawl (`cli.py:340`, `harvest.py:37`). The warehouse opens the harvest run with `from_date` = the `until_date` of the endpoint's last closed run (`metadata-warehouse/src/app/db_methods.py:176`), so the harvest is incremental. The DAG then indexes only the closed runs created since its start (`harvest_and_index.py:57`, `:110`), and `max_active_runs=1` (`:37`) queues a second DAG run behind a running one, which includes its wait for the indexing (`index_run`, `wait_for_completion=True`, `:138-145`). A record changed under the same identifier replaces its search document (e2e test, 2026-11-11, `BACKLOG.md`). Deletions do not reach the warehouse (`deletedRecord=no`). Staging finding F17 is fixed on the `crawler` branch (b58caac, merged in 05341ef): the broker waits 48 hours for an acknowledgement (`prototypes/search-stack/broker.conf`), so the default worker no longer stops taking tasks during a long harvest.
- **Runs.** `last_finished()` (`store.py:271`) drives the timer's catch-up (`cli.py:403`). `modama-chain` takes T from the newest finished crawl (`search-chain/src/modama_chain/chain.py:299`). Neither knows about subtrees.
- **Staging, run 3:** extraction ran 177,166 times in about 52 minutes on 8 processes, DM4 18,294 s and DM3 5,377 s summed over them. The harvest ran at about 77 records/s, and indexing at 26 to 62 records/s (F16).

## Goals / Non-Goals

**Goals:** one subtree is crawled from scratch, with the same identifiers as a full crawl, and the rest of the index stays untouched. The stored state stays consistent for the next full crawl. Requests 1 and 3 get one command, and request 2 gets a documented procedure.

**Non-Goals:** making the warehouse faster. For a format-wide change, the harvest and indexing of the changed records dominate: about 170,000 DM records at F16's rates take about 40 minutes to harvest and 45 minutes to two hours to index, against a 17-minute walk.

## Decisions

The review of 2026-11-12 (`review.md`) is folded in with its leans (@weber: "Go with your leans, and where there is no obvious answer, please provide clearer examples"). Each fix names its finding; what has no obvious answer is in the proposal's questions.

**D1. One option on `crawl`, not a new command: `crawl --path PATH`.** A subtree crawl is a crawl. It has the same lock, run record, SIGTERM handling, store lock, report, harvest trigger, `--config`, `--select` and `--ignore`, so all of that comes for free and stays the same. Whether `--select`, `--ignore` and a configuration other than the deployment's should be refused with `--path` is a question (proposal; review M4). *Alternatives:* (a) a command of its own (`recrawl PATH`): it would say "from scratch" in its name, but it would duplicate the option handling and the exit statuses; (b) `--root` with exclusions, which staging uses today: it deletes the rest of the index and resets the rule set (Context). *Name:* `--path` rather than `--subtree`, because the requests say "path". `--root` keeps its meaning, the data root, and its help text says so (proposal).

**D2. PATH is a canonical path, checked against what a full crawl enters.** PATH is relative to the data root; a leading `/` (the form of anchors and `dc:title`) and a trailing `/` are accepted. It is normalised (`adhoc/../other/` is `/other`), and a `..` that leaves the root is an error. Each of the following ends the crawl with status 2 and an error line naming the path and the reason, before a run is recorded (spec `crawl`, "A subtree crawl only covers what a full crawl enters"):
- *Not valid UTF-8.* Python passes such a name from the command line as a string with lone surrogates; the walk skips such names with a warning (R35), and an anchor holding one cannot become an identifier (`oai_identifier` raises `UnicodeEncodeError` at `records.py:43`, run in the review). The error names PATH with `!r` (review M6).
- *The data root itself:* `--path /`, `--path .`, an empty PATH, and a file at the top level, which stands for the root. The error says that the data root is crawled by `crawl` without `--path` (review M3). As a subtree crawl, the root would delete every stored listing, so the next full crawl would take nothing over (1 h 17 min on staging instead of a take-over).
- *Not found:* the error names the data root PATH is relative to, so that a PATH typed as the container's path is recognisable: `crawl --path /data/adhoc/libertem` gives `ERROR /data/adhoc/libertem: no such directory under the data root /data (--path is relative to it)` (review L5).
- *On the way down:* the crawl goes from the root down to PATH. For each directory on the way, and for PATH itself, it asks the file system: an `lstat`, which refuses symlinks, and a listing, which refuses a directory it cannot list (AGENTS.md: the file system is the truth). It then applies the exclusions, and the pre-order check of the formats active at that directory after per-path ignores (`formats_for`, `walk.py:186`), to that listing (review L5). The first directory that is a symlink, excluded or not listable, and the first directory above PATH that is collapsed (an environment, `.git`, a Zarr store), is named in the error. PATH itself may be collapsed: it then becomes one dataset, as in a full crawl (review M1).
- *Another data root:* when a crawl of the whole tree has finished on this index, the data root must be that crawl's (`crawl_runs.root`). `crawl --root /data/adhoc --path libertem` on an index crawled from `/data` would make anchors `/libertem/…`: records with other identifiers, harvested, and deleted again by the next full crawl in the crawler only. The error names both roots (review L3). This check reads the index, so it runs after the crawl lock is taken and before the run is recorded.

The checks prevent records that a full crawl would not make, which would be harvested and never purged. The pre-order check runs on the listings rather than on the stored datasets, so it also holds for a tree that was never crawled. *A file as PATH* stands for its directory, because recognition works per directory (agreed, Decisions by @weber).

**D3. From scratch inside the subtree.** The walk starts at PATH with rel = PATH, without the stored state (`previous=None`), and extraction runs without the stored extractions. So every directory under PATH is recognised and every extractor runs, with or without a version bump. This does not contradict "the same data gives the same result or a failure" (change `parallel-walk`, spec `crawl`). Only the cache is skipped, not the rules: the same code on the same files gives the same records, and no datestamp moves. Only changed code changes records, which is the point. *Alternative:* the normal take-over and reuse in the subtree, with a `--force` flag. Request 3 (new data, unchanged code) would then do less work, but request 1 needs the forced run, and a subtree is small enough that one behaviour beats a flag (agreed, Decisions by @weber).

*PATH cannot be listed when the walk reaches it* (review H2). The walk's start directory behaves like the root: today `visit()` raises only for `rel == "/"`, and records any other directory it cannot list as skipped, with no datasets (`walk.py:245-256`). Started at PATH, that would give an empty result, and D4 would delete every dataset and record under PATH. So the walk raises for its start directory too. D2's listing does not close the window: PATH can become unlistable seconds later (`ESTALE` after an NFS failover, `EACCES` after an ACL change). The crawl then fails as for an unreadable root: status 2, `cannot read /data/adhoc/…: …`, the run recorded as `failed` (`cli.py:296-319`), and the store is never reached. Directories below PATH that cannot be listed are skipped as in a full crawl.

*Reverting an experiment* (review H3, open). A forced extraction is stored under the extractor's identity of today, `(format id, extractor_version, stamp)` (`extraction.py:114-121`, `:135-140`), and every later crawl reuses it while the files are unchanged. That is the gap: the label does not identify the code. Whether the identity becomes a hash of the extractor's code, valid within one deployment, waits for the walk-through of the extractor's identity with @weber (Decisions, request 2); this change does not decide it. One sequence of events shows what such a hash would change. The file is `adhoc/libertem/libertem-test-data/dm/a.dm4`; its stamp S stays the same throughout (the file is not touched); the DM extractor's code is C0, and it is stored with C0's description.

| Step | Stored today, identity `(em/dm4, "2", S)` | Stored with a code hash, identity `(em/dm4, hash, S)` |
|---|---|---|
| 1. The DM extractor is changed to C1 without a version bump; the image is rebuilt; `crawl --path adhoc/libertem/libertem-test-data` | C1's description under `"2"`; the record gets a new datestamp and is harvested | C1's description under `h1`; the same record and datestamp |
| 2. The change is reverted to C0; the image is rebuilt; `crawl --path adhoc/libertem/libertem-test-data` again | C0's description under `"2"`; the record changes back, gets a new datestamp and is harvested | C0's description under `h0`; the same as today |
| Step 2 without the second `crawl --path`: the next full crawl runs C0 | reuses C1's description, because `"2"` matches: the experiment stays in the index and the search, with nothing to show it, until someone runs `crawl --path` there again | sees `h1` ≠ `h0` and extracts `a.dm4` again with C0: the experiment is undone by itself |
| A full crawl between step 1 and 2 that runs C1 | inside the subtree reuses C1; outside it, every DM file keeps C0's description under the same `"2"`: two codes under one identity | extracts every DM file of the tree again with C1, as after a version bump (DM4 and DM3 took 23,671 s of extraction summed over 8 processes in run 3), so the index holds C1's output everywhere, under `h1` |

So with a code hash, reuse never crosses a code change, and the forced run of D3 is no longer needed for correctness; it stays for the performance tests @weber wants (Decisions). Until the identity is settled, the README procedure (task 4.2) says that after reverting an experiment, `crawl --path` on the same path brings the old descriptions back. The scenario for the revert is written once the identity is decided.

**D4. The store, restricted to the subtree.** P is PATH normalised to a leading `/` and no trailing `/` (`/adhoc/libertem/libertem-test-data`), the form of `datasets.directory` and `directories.path` (`walk.py:214`). "Under P" means `directory = P OR starts_with(directory, P || '/')`: the `/` keeps the sibling `/adhoc/libertem/libertem-test-data-old` out, which a bare `starts_with(directory, P)` would match (review H1; `starts_with('/adhoc/a/bc', '/adhoc/a/b')` is true on PostgreSQL 17). `starts_with()`, not `LIKE`, because paths may contain `%` and `_`. A collapsed P is under P, since a collapsed dataset's `directory` is the directory itself (`formats/__init__.py:273`). In one transaction, as today:
- delete the datasets under P whose anchor is not in the result (members go by cascade), and upsert the result's datasets;
- delete the records of the deleted datasets, by the identifiers of their anchors, since records have no anchor column and long identifiers are hashed. Upsert the result's records under the store lock, with one datestamp, as today;
- delete the stored listings (`directories`) whose `path` is under P, by the same predicate, and store none for the subtree. The next full crawl then recognises the subtree again and reuses its extractions (spec scenario "The next full crawl takes over the extractions"), whatever rules either crawl ran under. *Alternative:* store fresh listings, so that the next full crawl takes the subtree over. That is wrong when the subtree crawl ran under other rules (a forgotten `--config`, a format bumped in the image): the full crawl would then take over datasets recognised under those other rules. The cost of deleting is one more recognition of the subtree;
- record no rule set on the run. `previous()` then still compares against the last full crawl.

Parents are set only for datasets that a format adopts as parts of a dataset in a directory above, and no format returns parts today (`formats/__init__.py:346-349`; review L5). So the datasets at the top of the subtree get no parent, as at the top of a full crawl ("Not now").

**D5. The run records its subtree.** A column `crawl_runs.scope TEXT` holds P in the form of the other path columns (`/adhoc/libertem/libertem-test-data`), and NULL for a full crawl; `runs` prints it after the root as a canonical path, without the leading `/` (review L5). `last_finished()` and `modama-chain`'s T use `scope IS NULL` only. The column is the first change of the schema, and the database is not recreated for it: that would cost staging a full crawl, harvest and indexing, about a night. Schema migrations are planned with Alembic in the open change `schema-migrations`, and `scope` becomes its migration 0002 whichever change ships first. If `schema-migrations` ships first, this change adds the column as that migration and leaves `ensure_tables` alone. If this change ships first, `ensure_tables` adds the column with `ALTER TABLE crawl_runs ADD COLUMN IF NOT EXISTS scope TEXT`, run only when `information_schema.columns` does not list the column: the statement takes an ACCESS EXCLUSIVE lock on `crawl_runs` even when the column exists, and `ensure_tables` runs at every `crawl`, `runs`, `timer` and `serve` (`cli.py:270`, `:402`, `:454`, `:484`; review L2). Its docstring ("There are no migrations: recreate the database after a change", `store.py:63`) then says that this column is added in place. `modama-chain` checks that the column exists, as it already does for the table (`crawler.py:102`), so that it also works against a crawler from before this change. *Alternative:* encode the subtree in `root` (root + path). Readers would then have to know the data root to tell the two kinds apart.

**D6. Lock, SIGTERM and harvest: no new mechanism.** The same crawl lock: a subtree crawl and a full crawl refuse each other with status 1. SIGTERM records the run as `failed` and exits with 143, and the store's single transaction guarantees that no record changed. After a finished subtree crawl the harvest starts as after any crawl. Only records changed under PATH have a datestamp after the last harvest window, so only they are harvested and indexed. *How soon* (review M5): within one incremental harvest and its indexing when no harvest DAG run is active. When one is, the new DAG run waits until the active one has harvested and waited for its indexing (`max_active_runs=1`), which after a full crawl that changed much takes hours (run 3: 5 h 14 min of harvest, then hours of indexing). Its window still starts at the end of the last closed run, so it includes the subtree's records. With F17 fixed, the queued run is taken when the active one ends. *Where it runs* (review M8, plausible, checked by task 4.2): in production only `crawl-timer` has the Airflow account, so a subtree crawl that should start the harvest runs as a one-off container of that service, from the image just built: `docker compose build crawler`, then `docker compose run --rm crawl-timer modama-crawler --config … crawl --path …`. It gets the service's environment, account, user and mounts without recreating the timer, and Compose passes signals to it. `docker compose up --build` would recreate the timer and stop a crawl it is running, and a process started with `docker compose exec` gets no SIGTERM when its container stops (its run then shows as stale; the data is safe).

**D7. Request 2 (all files of a kind): bump the version and crawl now.** No new command. Bump the format's `extractor_version` (DM3 and DM4 share one, `modama_formats_em/dm/__init__.py:19`), rebuild the image, and run `crawl` instead of waiting for the timer. The full crawl takes every unchanged directory over, extracts only that format's datasets again (`extraction.py:118`), and gives a new datestamp only to records whose content changed. So the harvest is incremental. A recognition change (format `version`, MIME XML) changes the rule set: every directory is recognised again, and extractions are still reused. This is the decision of 2026-10-16 ("after a format change, re-crawl; no selective invalidation") and the open change `em-formats-and-extraction`'s scenario "A new extractor version". The bump is also what carries the improvement to every other deployment. Cost on staging: the walk (17 minutes with warm caches) and the store (about 8 minutes in run 3) on top of the format's extraction, and then the warehouse (Non-Goals). The README gets the procedure. *Alternatives:* (a) `crawl --format ID[,ID…]`: a full crawl that does not reuse the given formats' extractions. It is small (one set passed to `extract`) and needs no bump while iterating, but the stored results then carry a version label that does not identify the code that produced them, so another deployment with that version would give different results. D3 has the same property for a subtree (D3, "Reverting an experiment"). (b) Re-extraction from the stored datasets without a walk: it saves about 25 minutes out of about three hours, at the price of a second store path and of extracting files that changed or disappeared since the last crawl.

## Risks / Trade-offs

- [A subtree crawl holds the lock at the timer's time] → the nightly crawl exits with status 1, and the timer waits until the next day (`cli.py`, `cmd_timer`). Subtree crawls are short, and `runs` shows the conflict. Acceptable until the demo, and a backlog item with a test (Decisions by @weber; task 6.1).
- [A large PATH (`adhoc`)] → everything under it is extracted again. The operator chose the path, and the report shows the counts.
- [Rules other than the deployment's: `--select`, `--ignore`, a forgotten or another `--config`] → the subtree is recognised under those rules until the next full crawl. D4 keeps the crawler's stored state consistent, but records that a full crawl would not make are harvested, and the warehouse keeps them after the next full crawl deletes them (review M4). Refuse or warn is a question (proposal). In the search stack's README, the commands always pass `--config`.
- [A reverted experiment stays in the index] → open with the extractor's identity (D3, review H3). Until then the README names the undo step.
- [The warehouse keeps records of datasets that disappeared under PATH] → as after a full crawl. The purge of stale entries is in the backlog.
- [Paths that are not valid UTF-8] → a PATH that is not is refused (D2); names below it are skipped by the walk as in a full crawl (R35).

## Migration Plan

No database recreation (D5). Deploy by rebuilding the crawler image (with `schema-migrations`, after its migration step). Rollback: the old crawler ignores the `scope` column. Its timer and `modama-chain` would then count earlier subtree runs as full crawls. For the timer that only delays a catch-up; for T it is a false claim: T would jump to a subtree crawl's start and state that every file older than that is in the search (review L4). So before a rollback, the operator deletes the subtree runs' rows (`DELETE FROM crawl_runs WHERE scope IS NOT NULL`); the README says so with the procedure (task 4.2).

## Not now

- Several paths in one crawl (`--path` repeated).
- A subtree crawl that takes over and reuses (`--force` off), for new data with unchanged code (D3).
- `crawl --format` or re-extraction without a walk (D7).
- The timer retrying later when a subtree crawl holds the lock.
- Subtree crawls below a format that adopts datasets of subdirectories (series, when it comes): keep or recompute the parent.
- A warning when a subtree crawl runs under rules other than the last full crawl's, unless the question in the proposal brings it now.
- Tombstones (`deletedRecord`) and the purge; the inotify watcher feeding subtree crawls (the decision log's "later, a watcher").
