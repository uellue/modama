# Design

## Context

The motivation is in the proposal. This is what the code does today (`crawler` at 0786930f, brought up to date on 2026-11-13; the first version described 9c9b32b), and it is what shapes the approach:

- **The crawl root is the whole repository.** `walk()` visits its root as `/` (`_walk`, `visit(root, "/")`), so anchors, and with them identifiers and browse URLs, are relative to the root it is given (`records.py`: "relative to the data root"). `store()` deletes every dataset, listing and record that is not in the result. So `crawl --root SUBTREE` renames the subtree's records and deletes all the others. Exclusions keep the names but delete the same records, and they enter the rule set (`selection.fingerprint`), so the next full crawl takes nothing over (`store.previous`).
- **Reuse.** A full crawl takes over a directory whose listing, and the listings of everything below it, are unchanged under the same rule set (`visit`). It reuses a successful extraction while the extractor (format id), the dataset's stamp and the extractor identity are the same; a failure is never reused (`extraction.extract`, change `extractor-identity`). The identity is a digest of the installation (`identity.py`): the Python version, every distribution's version, and the source of the format packages and of whatever is installed from a path. The search stack's image installs the crawler and the format packages editable from a copy, so any code change gives a new identity, and the next crawl extracts every dataset with an extractor again. Extractions are reused across a change of rule set as well (`crawl_tree`: `stored or Stored(conn)`).
- **Datestamps** move only when a record's metadata changes (`store()`, the records' upsert).
- **Harvest.** The crawler starts `warehouse_harvest_and_index` with `harvest_urls` = its endpoint after every finished crawl (`cli._trigger_harvest`, `harvest.py`). The warehouse opens the harvest run with `from_date` = the `until_date` of the endpoint's last closed run (`metadata-warehouse/src/app/db_methods.py`), so the harvest is incremental. The DAG then indexes only the closed runs created since its start (`harvest_and_index.py`), and `max_active_runs=1` queues a second DAG run behind a running one, which includes its wait for the indexing (`index_run`, `wait_for_completion=True`). A record changed under the same identifier replaces its search document (e2e test, 2026-11-11). Deletions do not reach the warehouse (`deletedRecord=no`). Staging finding F17 is fixed (b58caac): the broker waits 48 hours for an acknowledgement.
- **Runs.** `last_finished()` drives the timer's catch-up (`cmd_timer`). `modama-chain` takes T from the newest finished crawl (`search-chain/src/modama_chain/chain.py`, `freshness`). Neither knows about subtrees.
- **Schema.** The schema changes only by Alembic migrations (`migrations/versions/`; `0001_baseline`, `0002_extractor_identity`); `store.py` has no DDL, and every command but `migrate` checks the version (`schema.HEAD`).
- **One folder alone.** `walk(top=…)` (change `chain-browse`, for `modama-chain browse`) already makes the pre-order calls from the root down to a folder, as the crawl of the whole tree makes them; it does not descend.
- **Staging, run 3:** extraction ran 177,166 times in about 52 minutes on 8 processes, DM4 18,294 s and DM3 5,377 s summed over them. The harvest ran at about 77 records/s, and indexing at 26 to 62 records/s (F16).

## Goals / Non-Goals

**Goals:** one subtree is crawled from scratch, with the same identifiers as a full crawl, and the rest of the index stays untouched. The stored state stays consistent for the next full crawl. Requests 1 and 3 get one command.

**Non-Goals:** request 2 (served by the change `extractor-identity`, proposal); making the warehouse faster.

## Decisions

The review of 2026-11-12 (`review.md`) is folded in with its leans (@weber: "Go with your leans, and where there is no obvious answer, please provide clearer examples"). Each fix names its finding.

**D1. One option on `crawl`, not a new command: `crawl --path PATH`.** A subtree crawl is a crawl. It has the same lock, run record, SIGTERM handling, store lock, report, harvest trigger and `--config`, so all of that comes for free and stays the same. `--select` and `--ignore` are refused with `--path` (answer 169; review M4): a subtree crawl under another selection makes records that a full crawl would not make, for example `--select em/dm4` splits an EMPAD scan into two single-file records, one with a new identifier that the search keeps after the next full crawl deletes it. *Alternatives:* (a) a command of its own (`recrawl PATH`): it would say "from scratch" in its name, but it would duplicate the option handling and the exit statuses; (b) `--root` with exclusions, which staging uses today: it deletes the rest of the index and resets the rule set (Context). *Name:* `--path` rather than `--subtree`, because the requests say "path". `--root` keeps its meaning, the data root, and its help text says so (proposal).

**D2. PATH is a canonical path, checked against what a full crawl enters.** PATH is relative to the data root; a leading `/` (the form of anchors and `dc:title`) and a trailing `/` are accepted. It is normalised lexically (`adhoc/../other/` is `/other`), and a `..` that leaves the root is an error. Each of the following ends the crawl with status 2 and an error line `cannot crawl --path PATH: …` naming the reason, before a run is recorded (spec `crawl`, "A subtree crawl only covers what a full crawl enters" and the requirements after it):
- *Not valid UTF-8.* Python passes such a name from the command line as a string with lone surrogates; the walk skips such names with a warning (R35), and an anchor holding one cannot become an identifier (`oai_identifier` raises `UnicodeEncodeError`). The error names PATH with `!r` (review M6).
- *The data root itself:* `--path /`, `--path .`, an empty PATH, and a file at the top level, which stands for the root. The error says that the data root is crawled by `crawl` without `--path` (review M3). As a subtree crawl, the root would delete every stored listing, so the next full crawl would take nothing over (1 h 17 min on staging instead of a take-over).
- *Not found:* the error names the data root PATH is relative to, so that a PATH typed as the container's path is recognisable: `crawl --path /data/adhoc/libertem` gives `cannot crawl --path /data/adhoc/libertem: no such directory under the data root /data (--path is relative to it)` (review L5).
- *On the way down* (`walk.refusal()`): from the root down to PATH, for each directory below the root an `lstat`, which refuses a symlink and a file, and the exclusions; for each directory down to PATH, PATH included, a listing, which refuses a directory it cannot list (AGENTS.md: the file system is the truth); for each directory above PATH, the pre-order call of the formats active there after per-path ignores, which refuses a collapsed directory (review L5). The first such directory is named. PATH itself may be collapsed: it then becomes one dataset, as in a full crawl (review M1). The pre-order calls are those of `walk(top=…)`; they run on the listings rather than on the stored datasets, so the check also holds for a tree that was never crawled.
- *Another data root:* when a crawl of the whole tree has finished on this index, the data root must be that crawl's (`crawl_runs.root`). `crawl --root /data/adhoc --path libertem` on an index crawled from `/data` would make anchors `/libertem/…`: records with other identifiers, harvested, and deleted again by the next full crawl in the crawler only. The error names both roots (review L3).
- *Another configuration* (answers 170, 171): when the last finished crawl of the whole tree recorded its configuration (`crawl_runs.config`), the subtree crawl's must be the same: the selection, the per-path ignores and the exclusions, compared as values, not the file's name or bytes. The error names both configuration files (or "none") and the parts that differ. A forgotten `--config` without `MODAMA_CRAWLER_CONFIG` would otherwise crawl `.snapshot/` folders that the deployment excludes, and their records would stay in the search. The rule set's fingerprint is not compared: it also covers format versions and MIME definitions, which a developer changes on purpose before a subtree crawl. When the last full crawl has no recorded configuration (it ran before migration 0003), the configuration is not compared and a warning says so (proposal, Q1, lean A).

The last two read the index, so they run after the crawl lock is taken and before the run is recorded. The checks prevent records that a full crawl would not make, which would be harvested and never purged. *A file as PATH* stands for its directory, because recognition works per directory (agreed, Decisions by @weber); an info line says so.

**D3. From scratch inside the subtree.** The walk starts at PATH with rel = PATH, without the stored state (`previous=None`), and extraction runs without the stored extractions. So every directory under PATH is recognised and every extractor runs, whatever the identity. This does not contradict "the same data gives the same result or a failure" (change `parallel-walk`, spec `crawl`). Only the cache is skipped, not the rules: the same code on the same files gives the same records, and no datestamp moves. Only changed code changes records, which is the point. With the extractor identity, a rebuilt image re-extracts anyway; from scratch stays for the performance tests @weber wants (Decisions), and it also re-recognises, which the identity does not cover (its "Not now"). *Alternative:* the normal take-over and reuse in the subtree, with a `--force` flag. Request 3 (new data, unchanged code) would then do less work, but a subtree is small enough that one behaviour beats a flag (agreed, Decisions by @weber).

*PATH cannot be listed when the walk reaches it* (review H2). The walk's start directory behaves like the root: `visit()` raises for its first directory (the root, `top`, or the subtree's PATH), and records any other directory it cannot list as skipped, with no datasets. Without that, a PATH that cannot be listed gives an empty result, and D4 deletes every dataset and record under PATH. D2's listing does not close the window: PATH can become unlistable seconds later (`ESTALE` after an NFS failover, `EACCES` after an ACL change). The crawl then fails as for an unreadable root: status 2, `cannot read /data/adhoc/…: …`, the run recorded as `failed` (`cmd_crawl`), and the store is never reached. Directories below PATH that cannot be listed are skipped as in a full crawl.

*Reverting an experiment* (review H3): resolved by the change `extractor-identity`, its sequence S1. The file is `adhoc/libertem/libertem-test-data/dm/a.dm4`; its stamp S stays the same throughout; the installation's code is C0 with identity `h0`.

| Step | Stored for `a.dm4` |
|---|---|
| 1. The DM reader is changed to C1; the image is rebuilt (`h1`); `crawl --path adhoc/libertem/libertem-test-data` | C1's description under `h1`; if it differs from C0's, a new datestamp, harvested |
| 2. Reverted to C0, the image rebuilt (`h0` again); the nightly crawl, without another `crawl --path` | `h1` ≠ `h0`: extracted again with C0, C0's description is back, a new datestamp, harvested |

If the image with C1 stays deployed overnight, the nightly crawl extracts every dataset with an extractor again under `h1` (about 52 minutes on staging), as for any deployment.

**D4. The store, restricted to the subtree.** P is PATH normalised to a leading `/` and no trailing `/` (`/adhoc/libertem/libertem-test-data`), the form of `datasets.directory` and `directories.path`. "Under P" means `directory = P OR starts_with(directory, P || '/')`: the `/` keeps the sibling `/adhoc/libertem/libertem-test-data-old` out, which a bare `starts_with(directory, P)` would match (review H1; `starts_with('/adhoc/a/bc', '/adhoc/a/b')` is true on PostgreSQL 17). `starts_with()`, not `LIKE`, because paths may contain `%` and `_`. A collapsed P is under P, since a collapsed dataset's `directory` is the directory itself. In one transaction, as today:
- delete the datasets under P whose anchor is not in the result (members go by cascade), and upsert the result's datasets;
- delete the records of the deleted datasets, by the identifiers of their anchors (`records.oai_identifier`), since records have no anchor column and long identifiers are hashed. Upsert the result's records under the store lock, with one datestamp, as today;
- delete the stored listings (`directories`) whose `path` is under P, by the same predicate, and store none for the subtree. The next full crawl then recognises the subtree again and reuses its extractions (spec scenario "The next full crawl takes over the extractions"), whatever rules either crawl ran under. *Alternative:* store fresh listings, so that the next full crawl takes the subtree over. That is wrong when the subtree crawl ran under other rules (a format's recognition changed in the image): the full crawl would then take over datasets recognised under those other rules. The cost of deleting is one more recognition of the subtree;
- record no rule set on the run. `previous()` then still compares against the last full crawl.

Parents are set only for datasets that a format adopts as parts of a dataset in a directory above, and no format returns parts today (`formats/__init__.py`, `run_post`; review L5). So the datasets at the top of the subtree get no parent, as at the top of a full crawl ("Not now").

**D5. The run records its subtree and its configuration: migration `0003_crawl_runs_scope`.** `crawl_runs.scope TEXT` holds P in the form of the other path columns (`/adhoc/libertem/libertem-test-data`), and NULL for a full crawl; `runs` prints it after the root as a canonical path, without the leading `/` (review L5). `crawl_runs.config JSONB` holds the configuration of every crawl, full or subtree: `{"file": "/stagingconf/full.toml", "select": […], "ignore": […], "per_path_ignores": {…}, "exclude": […]}`, after `--select` and `--ignore` (D2, "Another configuration"). `last_finished()`, the last full crawl's root and configuration, and `modama-chain`'s T use `scope IS NULL` only. The migration adds both columns, nullable, with no default and no `IF NOT EXISTS` (README, "Adding a migration"). Its `downgrade()` first deletes the subtree runs (`DELETE FROM crawl_runs WHERE scope IS NOT NULL`), then drops the columns: without the delete, the older code's `last_finished()` and `modama-chain`'s T would count a subtree run as a full crawl, and T would claim that every file older than a subtree crawl's start is in the search (review L4; `schema-migrations` D6). `schema.HEAD` becomes `0003_crawl_runs_scope`. `modama-chain` checks that the column exists, as it already does for `identity` (`crawler._has_column`), so that it also works against a crawler from before this change. *Alternative:* encode the subtree in `root` (root + path). Readers would then have to know the data root to tell the two kinds apart.

**D6. Lock, SIGTERM and harvest: no new mechanism.** The same crawl lock: a subtree crawl and a full crawl refuse each other with status 1. SIGTERM records the run as `failed` and exits with 143, and the store's single transaction guarantees that no record changed. After a finished subtree crawl the harvest starts as after any crawl. Only records changed under PATH have a datestamp after the last harvest window, so only they are harvested and indexed. *How soon* (review M5): within one incremental harvest and its indexing when no harvest DAG run is active. When one is, the new DAG run waits until the active one has harvested and waited for its indexing (`max_active_runs=1`), which after a full crawl that changed much takes hours (run 3: 5 h 14 min of harvest, then hours of indexing). Its window still starts at the end of the last closed run, so it includes the subtree's records. *Where it runs* (review M8, plausible, checked by task 4.2): in production only `crawl-timer` has the Airflow account, so a subtree crawl that should start the harvest runs as a one-off container of that service, from the image just built: `docker compose build crawler`, then `docker compose run --rm crawl-timer modama-crawler crawl --path …`. It gets the service's environment (with `MODAMA_CRAWLER_CONFIG` on staging), account, user and mounts without recreating the timer, and Compose passes signals to it. `docker compose up --build` would recreate the timer and stop a crawl it is running, and a process started with `docker compose exec` gets no SIGTERM when its container stops (its run then shows as stale; the data is safe).

**D7 (2026-11-12: request 2, "bump the version and crawl now")** is dropped: the change `extractor-identity` serves request 2 (proposal, "Changed since 2026-11-12").

**D8. The configuration from `MODAMA_CRAWLER_CONFIG`** (answers 170, 171). `cli.main` reads it, after `.env`, as the default for the global `--config`; `--config` on the command line wins. An empty value means none. It is read for every command that takes a configuration (`crawl`, `records`, `timer`; proposal Q2, lean). The timer passes its `--config` on to its crawls, and the crawl processes inherit the environment, so either way they use the same file. On staging, `docker-compose.staging.yml` sets it for `crawler` and `crawl-timer`, and the timer's command no longer carries `--config`. The test deployment sets none (it crawls with the defaults).

## Risks / Trade-offs

- [A subtree crawl holds the lock at the timer's time] → the nightly crawl exits with status 1, and the timer waits until the next day (`cmd_timer`). Subtree crawls are short, and `runs` shows the conflict. Acceptable until the demo, and a backlog item with a test (Decisions by @weber; task 6.1).
- [A large PATH (`adhoc`)] → everything under it is extracted again. The operator chose the path, and the report shows the counts.
- [Recognition rules other than the deployment's: a format changed in the image] → the subtree is recognised under those rules until the next full crawl, which recognises it again (D4). Records that differ are harvested; those of datasets that a full crawl would not make stay in the warehouse until the purge. That is the purpose of a subtree crawl after a format change, and the same as after a deployment.
- [The warehouse keeps records of datasets that disappeared under PATH] → as after a full crawl. The purge of stale entries is in the backlog.
- [Paths that are not valid UTF-8] → a PATH that is not is refused (D2); names below it are skipped by the walk as in a full crawl (R35).
- [A subtree crawl with experimental code makes the next nightly crawl extract everything again while that image stays deployed] → as for any deployment (change `extractor-identity`, S1 step 1a); `modama-crawler runs` prints the note of what the next crawl extracts again.

## Migration Plan

Deploy by rebuilding the crawler image; `modama-crawler migrate` (the service `crawler-migrate`) applies `0003_crawl_runs_scope`. Rollback: the migration's downgrade, run with the newer code before going back (README, "Upgrade"), deletes the subtree runs and drops `scope` and `config`; the older code then reads `crawl_runs` correctly.

## Not now

- Several paths in one crawl (`--path` repeated).
- A subtree crawl that takes over and reuses (`--force` off), for new data with unchanged code (D3).
- `crawl --format`, or re-extraction without a walk.
- The timer retrying later when a subtree crawl holds the lock.
- Subtree crawls below a format that adopts datasets of subdirectories (series, when it comes): keep or recompute the parent.
- A report line comparing a subtree crawl's new results with the stored ones per format (the change `extractor-identity`'s D6 named "forced" as a reason); the records changed count serves until someone asks.
- Tombstones (`deletedRecord`) and the purge; the inotify watcher feeding subtree crawls (the decision log's "later, a watcher").
