# Proposal: an office document's text in its record (`office-text`)

## In short

A Word document or a PowerPoint deck says what it is about in its own text: its title, headings, slide titles, bullet points. Before this change its record showed only what the property parts say (title, author, dates, application, page or slide count) and, as the second `dc:description`, those parts as `name: value` lines. With this change the second description of a `.docx`, `.docm` or `.pptx` is **the document's text, rendered as Markdown** (headings, lists, bold and italic, tables; per slide its title, its text and its speaker notes), led by the author's subject, keywords, description and category, up to 4,096 characters, and treated like the text of a Markdown file (change `text-as-written`): a line that may hold a credential is left out. The summary line stays first and unchanged. Embedded pictures, videos and other embedded files are never read: the converter gets a copy of the package in memory that holds only its XML parts (design D2).

Example, the public fixture `testWORD_custom_props.docx` (Apache Tika), by the code of this change:

- before: summary `My Title, EJ04325S, 2011-07-29T16:52:00Z, Microsoft Office Word, Pages 1`, then the lines `app.AppVersion: 14.0000`, `app.Application: Microsoft Office Word`, `app.Company: EDF-DIT`, … (about 40);
- after: the same summary, then `core.subject: My subject` / `core.keywords: My Keyword` / `core.description: My Comments` / (blank) / `Document content`.

A deck written by python-pptx in the tests: `# Drift correction` / `Cross-correlation per frame` / `Sub-pixel by upsampling` / `### Notes:` / `mention the 2019 data` / (blank) / `# Results`; so a search for "drift correction" finds the deck and an answer can say what it is about.

## Why

- @weber, 2026-11-14, on the AI Mode test of page item 367 a (a `.pptx` record had slide count, size and date but no slide titles, so the answer could not tell what the deck is about): "What about treating indexing complex office documents generally as attempting to convert the text part of it, up to a size limit, to Markdown, and then feeding it into the same path how actual Markdown is treated at the moment? That should also preserve title, headlines, lists, and some basic formatting such as bold."
- Decision 369 (decision log, 2026-11-14; TEMPLATE.md, "Extracting metadata"): "without editorializing" is for scientific data and measurements; office documents' text may be rendered.
- His refinements, same morning: "doesn't have to be Markdown per se, I just found that an obvious option." "Size limit: Let's not set a hard limit, but flag when it goes beyond what we had discussed before. The documents are complex and we don't control the reader and converter well. We just need to make sure we don't look at images or even videos that are embedded. That's a requirement for the converter I guess, or we first extract a proxy document with large chunks dropped out? So let's first work on it working well, then make it efficient." "docx and pptx sound obvious. PDF we have a lot as well, right? Then by order what we have in the file system."

I read the `.pptx` of 367 a as an example of a rule, "an office document's record carries its text, rendered, within the record's limit, without reading embedded media", not as the whole ask (standing rule on named cases). I read "Markdown" as the rendering's form, kept because the record's text path already shows Markdown files as written. Counts (October listing, a quarter of the tree; `common-office` proposal): `.pdf` 862, `.docx` 151, `.pptx` 149, `.xlsx` 26, `.odt` 20, `.odp` 8. This change: `.docx` and `.pptx`, and `.docm`, which the same reader handles (L8); the others are next steps in that order (Out of scope, BACKLOG).

Serves R30 ("not finding something although the file tree and file contents held enough information to match the query"), R15 (extract from content), decisions 234 (the second description) and 369, and the requirement "The file's text as the second description" of change `text-as-written`.

## Assumptions and leans

Accepted by @weber on 2026-11-14 (page items 374 and 375): Q1, the dependencies, "sounds reasonable to add"; Q2 to Q5 "sounds reasonable, let's see how it will feel in practice!". An independent review of the proposal then asked for fixes before the build (M1, M2, S1 to S8); they are folded in below and marked "(review …)". Deviations from the accepted leans are marked **Deviation**.

- **L1 The converter** (Q1, design D1): `.docx` and `.docm` by **mammoth** (to HTML) and **markdownify** (HTML to Markdown), the libraries Microsoft's MarkItDown uses for Word, without MarkItDown itself; `.pptx` by **python-pptx** on the proxy (L2) and a short walk of ours over its slides. New dependencies: mammoth 1.13.0 (BSD-2-Clause; brings cobble), markdownify 1.2.3 (MIT; brings beautifulsoup4, soupsieve, six), python-pptx 1.0.2 (MIT; brings XlsxWriter; lxml and Pillow are there already); python-docx 1.2.0 for the tests. Not MarkItDown 0.1.9 (magika and onnxruntime at import, Python below 3.15), not pandoc 3.14 (GPL-2.0 binary, a process per document), not docx2python 3.7.2 (no Markdown).
- **L2 Never read embedded media** (D2; review M2, S8): the extractor copies the package's XML parts into a ZIP in memory and writes every other part empty. A part is XML when its content type, looked up as OPC does (its Override first, then its extension's Default, both case-insensitive), is `application/xml`, `text/xml` or ends in `+xml`, and is not of the top-level types `image/`, `audio/`, `video/` or `model/` (Office writes SVG pictures as `image/svg+xml`); a part with no known type is not read. Measured: a `.docx` and a `.pptx` with a 20 MB picture each read less than 1 MiB; a `.docx` with a 3 MB SVG picture less than 256 KiB.
- **L3 What the rendering keeps** (Q2, D3): Word: the title (style Title as `#`), headings (`#`), paragraphs, lists, bold and italic, tables as pipe tables (first row as header), links, footnotes and endnotes (their number links and back links as plain text, review note); names as written, no `\_` or `\*` (review S5); pictures left out without a line; comments not shown; tracked changes as accepted (deleted text never shown); headers and footers not shown; hidden text (`w:vanish`) shown, as mammoth does (review note: left as it is). PowerPoint: per slide, in order, `# <title>` (a slide without a title: a line `---`), each text shape's paragraphs as lines with bold and italic runs, tables as pipe tables, group shapes walked, then the speaker notes after `### Notes:`; pictures, media, charts, SmartArt and comments left out; hidden slides like the others.
- **L4 Into the record** (Q5, D4; review M1): the rendering, led by the core properties `subject`, `keywords`, `description` and `category` where not empty as `core.<name>: <value>` lines (review S6: with a text the property lines leave the record, and these are the author's own words), goes through the text area's rule for what is shown (`written.shown`, as for a plain text file): a line that may hold a credential is left out (`… (a line left out: may be a credential)`, counted in `mapped_metadata["credentials_left_out"]`), and a text over 4,096 characters is shown as its first and last lines, about 2,000 characters each, with a line `… N bytes left out …` between them. The result is `values["text"]`, which the record shows as its second description in place of the tag lines (records requirement of `text-as-written`). The summary line and `original_metadata` stay as they are.
- **L5 No hard size limit, a flag** (Q4, D5): no limit of ours on the parts read or rendered. Every rendered document gets `mapped_metadata` `bytes read` (bytes read of the file by the extraction so far, as the read limit counts them), `xml bytes` (the XML parts' size uncompressed, from the ZIP's directory) and `large document text` (`true` when the bytes read are past 1 MiB, the per-file read limit's stop of decision 329). **Deviation from Q4** (review S2, coordinator 2026-11-14): no dataset warning and no marker in `modama-chain review` tonight; the crawler's core (`extraction.py`, `review.py`) is left untouched for the staging crawl's safety, and the flag is these numbers only, visible in `browse` and `records --verbose`. The warning channel (a tuple of extractor markers beside `SLOW_EXTRACTION`, `_slow` generalised, stale warnings removed) is a next step in BACKLOG.
- **L6 A soft deadline** (review S4): a rendering that takes more than 30 s (an interval timer in the worker's main thread raising `TimeoutError`) is given up, the metadata kept, so that the extraction does not fail at its limit of 60 s.
- **L7 The tag lines leave the record** (Q3, D4): where a record has a text, the property parts' `name: value` lines are no longer in it; title, author and dates stay in the summary line, subject, keywords, description and category at the text's head (L4); company, template and custom properties only in the values.
- **L8 Which formats**: `common/docx`, `common/docm`, `common/pptx`. Not `.xlsx`, `.odt`, `.odp`, `.pdf` or the legacy formats (Out of scope).
- **L9 A rendering that fails** (D6; review S1): the metadata is kept, the record keeps its tag lines, `mapped_metadata["text not rendered"]` holds the reason, and the extraction does not fail. An XML part that declares a DTD stops the rendering before a converter sees it: each kept part is parsed by defusedxml with DTDs forbidden up to its first start tag, so a `<!DOCTYPE` is found in any encoding and after a comment of any length.
- **L10 Extractor identity**: nothing to do. The identity is a digest of the installation (change `extractor-identity`); the new libraries enter it.
- **L11 Tests** (D7): public fixtures (Apache Tika's: `testComment.docx` and `testPPT_embeddedMP3.pptx` added, the area's others re-recorded) and documents written at test time by python-docx and python-pptx; one test per scenario; tracked changes by a reproducer (Tika's `testWORD_custom_props.docx` with one insertion and one deletion added to its XML), since no public fixture was found by name.

## What Changes

- `python/modama-formats-common/src/modama_formats_common/office/rendered.py` (new): the proxy, the DTD check, the deadline, the Word and the PowerPoint rendering, the numbers of L5; `ooxml.extract` takes a renderer, `Docx`, `Docm` and `Pptx` pass theirs; `office/tests/test_text.py` (new), two Tika fixtures, three expected results re-recorded and two new, two tests of `test_office.py` changed (a presentation's `mapped_metadata` holds more than its slide count; only the XML parts are read).
- `python/modama-formats-common/pyproject.toml`: mammoth, markdownify, python-pptx pinned; python-docx in `test`.
- READMEs of `modama-formats-common` and of the crawler, `BACKLOG.md`, a decision-log row.

Behaviour towards the user: the record of every `.docx`, `.docm` and `.pptx` carries the document's text, rendered as Markdown (headings, lists, emphasis, tables; slide titles, text and speaker notes) and led by its subject, keywords, description and category, as its second `dc:description`, up to 4,096 characters and else as head and tail with a visible marker, a line that may hold a credential left out, in place of the property parts' `name: value` lines; the summary line stays first and unchanged, so Matchmaker's cited entry, the search API's hit, the reranker and the chat model's context are unchanged (they use the first description only, `tags-in-the-record` D4). The text reaches DataCite, the warehouse, the keyword search and the embedding text (its first 512 tokens). These records' values gain `bytes read`, `xml bytes` and `large document text`. A crawl reads these documents' XML parts, not only their property parts, and still never their pictures or other embedded files. Every record of these formats changes once, so the next harvest and indexing are a full run for them. `modama-chain review` is unchanged.

## Out of scope

## Capabilities

### New Capabilities
None.

### Modified Capabilities
- `formats/office`: the rendered text of Word documents and presentations; "Office Open XML metadata from the package's property parts" no longer says that no other part is read (from the unarchived change `common-office`).

## Impact

- Code, tests and documents as above; three dependencies with four transitive ones new to the image (cobble, beautifulsoup4 with soupsieve, six, XlsxWriter).
- Order of archiving: `common-office` and `text-as-written` before this change.
- Size and cost: in the October listing 300 `.docx`, `.docm` and `.pptx` files, about 1,200 in the whole tree. Extraction of the fixtures took 0.01 to 0.1 s each, a 100-slide deck written by python-pptx read 296,667 bytes of its 216,616; each record's embedding text grows to up to 512 tokens, about 0.4 s more per record on one CPU (`tags-in-the-record` D5): together about 10 CPU minutes for the tree.
