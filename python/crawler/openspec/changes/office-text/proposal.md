# Proposal: an office document's text in its record (`office-text`)

## In short

A Word document or a PowerPoint deck says what it is about in its own text: its title, headings, slide titles, bullet points. Today its record shows only what the property parts say (title, author, dates, application, page or slide count) and, as the second `dc:description`, those parts as `name: value` lines. With this change the second description of a `.docx`, `.docm` or `.pptx` is **the document's text, rendered as Markdown** (headings, lists, bold and italic, tables; per slide its title, its text and its speaker notes), up to 4,096 characters, and treated like the text of a Markdown file (change `text-as-written`). The summary line stays first and unchanged. Embedded pictures, videos and other embedded files are never read: the converter gets a copy of the package in memory that holds only its XML parts (design D2).

Example, a deck `group-meeting.pptx` of 12 slides (made up):

- today: summary `Group meeting; A. Author; 2025-03-04T10:00:00Z; Microsoft Office PowerPoint; Slides 12`, then the lines `app.Application: Microsoft Office PowerPoint`, `app.Company: …`, `core.creator: A. Author`, …;
- with this change: the same summary, then `# Drift correction` / `Cross-correlation per frame` / `Sub-pixel by upsampling` / `### Notes:` / `mention the 2019 data` / `# Results` / …, so that a search for "drift correction" finds the deck and the answer can say what it is about.

## Why

- @weber, 2026-11-14, on the AI Mode test of page item 367 a (a `.pptx` record had slide count, size and date but no slide titles, so the answer could not tell what the deck is about): "What about treating indexing complex office documents generally as attempting to convert the text part of it, up to a size limit, to Markdown, and then feeding it into the same path how actual Markdown is treated at the moment? That should also preserve title, headlines, lists, and some basic formatting such as bold."
- Decision 369 (decision log, 2026-11-14; TEMPLATE.md, "Extracting metadata"): "without editorializing" is for scientific data and measurements; office documents' text may be rendered.
- His refinements, same morning: "doesn't have to be Markdown per se, I just found that an obvious option." "Size limit: Let's not set a hard limit, but flag when it goes beyond what we had discussed before. The documents are complex and we don't control the reader and converter well. We just need to make sure we don't look at images or even videos that are embedded. That's a requirement for the converter I guess, or we first extract a proxy document with large chunks dropped out? So let's first work on it working well, then make it efficient." "docx and pptx sound obvious. PDF we have a lot as well, right? Then by order what we have in the file system."

I read the `.pptx` of 367 a as an example of a rule, "an office document's record carries its text, rendered, within the record's limit, without reading embedded media", not as the whole ask (standing rule on named cases). I read "Markdown" as the rendering's form, kept because the record's text path already shows Markdown files as written, not as a requirement of its own. Counts (October listing, a quarter of the tree; `common-office` proposal): `.pdf` 862, `.docx` 151, `.pptx` 149, `.xlsx` 26, `.odt` 20, `.odp` 8. This change: `.docx` and `.pptx`, and `.docm`, which the same reader handles (L8); the others are later steps in that order (Out of scope).

Serves R30 ("not finding something although the file tree and file contents held enough information to match the query"), R15 (extract from content), decisions 234 (the second description) and 369, and the requirement "The file's text as the second description" of change `text-as-written`.

## Assumptions and leans (for @weber before the build; the reasons are in design.md)

- **L1 The converter** (design D1): `.docx` and `.docm` by **mammoth** (to HTML) and **markdownify** (HTML to Markdown), the libraries Microsoft's MarkItDown uses for Word, without MarkItDown itself; `.pptx` by **python-pptx** on the proxy (L2) and a short walk of ours over its slides, in MarkItDown's shape. New dependencies, each @weber's yes first: mammoth 1.13.0 (BSD-2-Clause; brings cobble), markdownify 1.2.3 (MIT; brings beautifulsoup4, soupsieve, six), python-pptx 1.0.2 (MIT; brings lxml, XlsxWriter, typing-extensions; Pillow is there already). Not MarkItDown 0.1.9: its package imports magika at import, which needs onnxruntime (wheels of 16 and 26 MiB), and it caps Python below 3.15. Not pandoc 3.14: GPL-2.0 binary of 34 MiB packed, a process per document. Not docx2python 3.7.2: no Markdown, we would write the renderer.
- **L2 Never read embedded media** (D2): the extractor copies the package's XML parts (by the content types `[Content_Types].xml` gives: a type ending in `xml`) into a ZIP in memory and writes every other part empty (pictures, video, audio, embedded workbooks and PDFs, fonts, macros, thumbnails); the converter only sees that copy. Measured on a self-made `.docx` and `.pptx` with a 20 MB picture: 135,764 and 134,862 bytes read for the copy and the conversion, against 40,686,911 (MarkItDown on the original `.docx`: mammoth reads the picture to embed it, and MarkItDown reads the file twice) and 20,346,359 (python-pptx opening the original `.pptx`).
- **L3 What the rendering keeps** (D3): Word: the title (style Title as `#`), headings, paragraphs, lists, bold and italic, tables as pipe tables, links, footnotes and endnotes; pictures left out without a line; comments not shown; tracked changes as accepted (insertions shown, deleted text never), measured; headers and footers not shown (mammoth does not read them). PowerPoint: per slide, in order, `# <title>`, then each text shape's paragraphs as lines, tables as pipe tables, group shapes walked, then the speaker notes as `### Notes:` and their text; pictures, media, charts and SmartArt left out; comments not read; hidden slides like the others.
- **L4 Into the record** (D4): the rendering in `values["text"]`, which the record shows as its second description in place of the tag lines (records requirement of `text-as-written`); at most 4,096 characters (`written.TEXT`, `extraction.MAX_STRING`); a longer rendering as head and tail by `written.shown_text`, about 2,000 characters each with a line `… 12,345 characters left out …`, the rule `text-as-written` uses for a rendering of ours. The summary line and `original_metadata` stay as they are; the property parts' lines leave the record but stay in the values (L7).
- **L5 No hard size limit, a flag** (D5): no limit of ours on the parts read or rendered (the worker's existing 60 s and 4 GiB stop a pathological file, as for every extractor). A package whose XML parts take more than **1 MiB** read from the file is flagged at its dataset with a warning of its own, `common/pptx read 1,234,567 bytes of XML to render its text; large document text`, a fixed marker that `modama-chain review` lists, as `slow extraction`. 1 MiB is the per-file read limit's stop of decision 329, "what we had discussed before" as I read it: the point where recognition would refuse a read; its 64 KiB flag would flag nearly every document (python-docx's empty template alone reads 135 kB). A slow conversion is flagged by `slow extraction` (10 s) already.
- **L6 The flag's channel** (D5): an extractor may put `values["warnings"]`, a list of strings each ending in a fixed marker; the crawler warns them at the dataset at every crawl, from the stored extraction too, as it does the slow-extraction warning. A small change of the core (`extraction.py`, the extraction spec), no migration.
- **L7 The tag lines leave the record** (D4): where a record has a text, the property parts' `name: value` lines are no longer in it (title, author and dates stay in the summary line; company, template, custom properties only in the values, `browse` and `records --verbose`). This follows from `text-as-written`'s rule "only the text" (its L2, 512 tokens of the embedding).
- **L8 Which formats**: `common/docx`, `common/docm`, `common/pptx`. `.docm` comes free (same reader, a public fixture); its macros (`vbaProject.bin`) are not XML and never read. Not `.xlsx`, `.odt`, `.odp`, `.pdf` or the legacy formats now (Out of scope).
- **L9 A rendering that fails** (D6): the metadata is kept, the record keeps its tag lines, and `mapped_metadata["text not rendered"]` holds the converter's message, as `sheets not read` does for a workbook; the extraction does not fail. An XML part with a `<!DOCTYPE` is not copied into the proxy and the text is not rendered, `text not rendered` naming the part: OOXML never needs a DTD, and the converters do not parse with defusedxml (D2).
- **L10 Extractor identity**: nothing to do. The identity is a digest of the installation (change `extractor-identity`), so the new libraries and their versions enter it, and a new version re-extracts every dataset, as for every dependency.
- **L11 Tests** (D7): public fixtures (Apache Tika's, as the area has) and documents written at test time by python-docx and python-pptx (A1); one test per scenario; a `.docx` and a `.pptx` with a 20 MB picture, written at test time, whose extraction reads less than 1 MiB (`bytes_read`); comments (Tika's `testComment.docx`, `testPPT_comment.pptx`); tracked changes: no public fixture found by name at Tika's pinned commit, so a reproducer written at test time (Tika's `testWORD_custom_props.docx` with one insertion and one deletion added to its XML).

## What Changes

- `python/modama-formats-common/src/modama_formats_common/office/`: a module `rendered.py` (the proxy, the Word and the PowerPoint rendering, the flag); `ooxml.extract` gives `values["text"]` for the three formats; `Docx`, `Docm`, `Pptx` call it; tests, fixtures, re-recorded expected results.
- `python/modama-formats-common/pyproject.toml`: mammoth, markdownify, python-pptx, pinned (L1).
- `python/crawler/src/modama_crawler/extraction.py`: an extractor's `values["warnings"]` warned at its dataset (L6); `python/search-chain/src/modama_chain/review.py`: the marker `large document text`.
- READMEs of `modama-formats-common` (the office rows: the text) and of the crawler (the record's descriptions), `formats/TEMPLATE.md` (an extractor's warnings), `BACKLOG.md` (the next formats), a decision-log row once @weber agrees.

Behaviour towards the user: the record of every `.docx`, `.docm` and `.pptx` carries the document's text, rendered as Markdown (headings, lists, emphasis, tables; slide titles, text and speaker notes), as its second `dc:description`, up to 4,096 characters and else as head and tail with a visible marker, in place of the property parts' `name: value` lines; the summary line stays first and unchanged, so Matchmaker's cited entry, the search API's hit, the reranker and the chat model's context are unchanged (they use the first description only, `tags-in-the-record` D4). The text reaches DataCite, the warehouse, the keyword search and the embedding text (its first 512 tokens). A document whose XML parts take more than 1 MiB is listed by `modama-chain review` as `large document text`. A crawl reads these documents' XML parts, not only their property parts, and still never their pictures or other embedded files. Every record of these formats changes once, so the next harvest and indexing are a full run for them.

## Out of scope

- Next, in the order of the listing: PDF (pypdf, already a dependency, has `extract_text`; no headings), `.xlsx` (openpyxl reads the shared strings already; a table per sheet's first rows), `.odt` and `.odp` (content.xml with defusedxml, or a library to be searched), then the legacy `.doc`, `.ppt`, `.xls`; `.pptm`, templates, `.rtf`, Outlook `.msg` (open since `common-office`).
- An outline first for a long document (all headings, then the text): after @weber has seen real records (D4).
- Pictures' alternative texts, charts' and SmartArt's texts, headers and footers, comments, deleted text of tracked changes.
- Measuring every extraction's bytes read, as its seconds are (a stored field, a migration): a next step if the flag of L5 is wanted for every format.

## Impact

- Code and tests as above; three dependencies with five transitive ones (L1), lxml the largest (a 5 MiB wheel); the crawler's image grows by them.
- Order of archiving: `common-office`, `text-as-written` and `slow-extractions` before this change.
- Size and cost: in the October listing 300 `.docx`, `.docm` and `.pptx` files, about 1,200 in the whole tree. Copy and conversion took 0.03 to 0.3 s per document on the self-made ones (warm imports; MarkItDown's code paths, D1); each such record's embedding text grows to up to 512 tokens, about 0.4 s more per record on one CPU (`tags-in-the-record` D5): together about 15 CPU minutes for the tree.
