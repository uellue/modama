# Design: an office document's text in its record (`office-text`)

Facts looked up on 2026-11-14 (PyPI's JSON API, the code host's repository API), measurements in a throwaway venv (Python 3.14, the versions below) on two self-made documents written by python-docx and python-pptx, each with one 20 MB noise PNG, and on the office area's Tika fixtures. Bytes read are `/proc/self/io` `rchar`, as `modama_crawler.testing.bytes_read` counts them, imports warmed up first.

Choice (L1): mammoth + markdownify for Word, python-pptx on the proxy for PowerPoint. They are the libraries MarkItDown itself uses for these two formats; taking them directly avoids magika and onnxruntime, which MarkItDown's package imports at import time although we would never call them (every extraction worker would load them; not measured), and MarkItDown's cap below Python 3.15. What we write ourselves: the proxy (D2) and the walk over a presentation's slides, about 50 lines in the shape of MarkItDown's `PptxConverter` (slide title as `#`, text frames, tables, notes), without its HTML comment per slide and its picture handling. mammoth's own Markdown output is deprecated by its author ("Generating HTML and using a separate library to convert the HTML to Markdown is recommended"), hence markdownify. pandoc is left out for its licence in the image, its size and a process per document; docx2python for its output (nested lists, no Markdown), which would leave the renderer to us.

Alternative kept open: our own walk over the WordprocessingML and PresentationML with defusedxml (no dependency, the area's way for the property parts), about 150 lines; against the standing rule while established libraries exist.

## D2 The proxy: only the XML parts

An OOXML package is a ZIP whose `[Content_Types].xml` gives each part's content type (by extension, `Default`, or by part name, `Override`). The extractor opens the file as the area does (`common.opened`, 64 KiB buffer, readahead off), reads `[Content_Types].xml` with defusedxml, and writes a ZIP in memory (stored, no recompression) with every XML part as it is, and every other part present but empty. A part's type is looked up as OPC does: its Override first, then its extension's Default, both case-insensitive. It is XML when the type is `application/xml`, `text/xml` or ends in `+xml`, and not of the top-level types `image/`, `audio/`, `video/`, `model/`: Office writes an SVG picture as `image/svg+xml` (review M2). A part whose type is unknown is not read (fail-safe). Media, embedded packages and PDFs (`word/embeddings/`, `ppt/embeddings/`), OLE objects, macros (`vbaProject.bin`), fonts, VML drawings and thumbnails are thus never read, by the rule on types, not by folder names. Empty parts keep the converters working: mammoth and python-pptx open them without error (both measured on the 20 MB documents; the rendered text was the same as from the original but for the pictures).

Safety: the converters parse the XML with their own parsers, mammoth with `xml.dom.minidom` (expat 2.9.0 here, which limits entity expansion), python-pptx with lxml and `resolve_entities=False`. Since OOXML never needs a DTD, each kept part is parsed by defusedxml (`iterparse`, DTDs forbidden) up to its first start tag, after which no DOCTYPE can come; a DTD stops the rendering (L9) before a converter sees it, in any encoding and after a comment of any length (review S1, which replaced a look at the first 1,024 bytes). mammoth gets `external_file_access=False` (its default in 1.13.0, set explicitly). A part that expands to gigabytes (a ZIP bomb in an XML part) is stopped by the worker's 4 GiB address space; a slow one by the soft deadline of 30 s (D6); no size limit of ours (L5).

As built, the measures of the tests: a `.docx` and a `.pptx` with a 20 MB picture each read less than 1 MiB, the same text as with a 20-pixel picture; a `.docx` with a 3 MB SVG picture (`image/svg+xml`) less than 256 KiB; Tika's `testPPT_embeddedMP3.pptx` has its MP3 and its poster picture empty in the proxy. The bytes read count the 64 KiB buffer's refills: a part read out of the file's order costs up to a buffer, so a small package can read more than its size (Tika's MP3 deck: 246,931 bytes of 84,434; a 100-slide deck by python-pptx: 296,667 of 216,616).

## D3 What the rendering keeps

Measured with MarkItDown's code paths on the self-made documents and the fixtures:

- Word (self-made): `Lamella preparation` (style Title: mammoth's default style map has no entry for it, so a plain line; L3 adds `p[style-name='Title'] => h1:fresh`), `# Milling`, `Thinning at **30 kV**, then *5 kV* cleaning.`, `* first step` / `* second step`, `1. one`, a pipe table; the picture as `![](data:image/png;base64...)`, to be left out; a comment's text (`A reviewer's private remark`) not shown.
- Tracked changes (a paragraph with `<w:ins>INSERTED</w:ins>` and `<w:del>DELETED</w:del>`): `Kept INSERTED`; the deleted text never appears.
- `testWORD_macros.docm` (Tika): `The **quick** *brown* fox.`; `testWORD_custom_props.docx`: `Document content`.
- PowerPoint (self-made): `# Drift correction`, `Cross-correlation per frame`, `Sub-pixel by upsampling`, `### Notes:`, `Speaker note: mention the 2019 data`, `# Results`, and the picture as `![noise.png](Picture2.jpg)`, to be left out. `testPPT_comment.pptx` (Tika): `# title`, `subtitle`; its comment not shown.
- `testWORD_truncated.docx`: `BadZipFile`, as the metadata's extraction already fails today.

Speaker notes are in (L3): they are part of the file as every reader of the deck sees it in PowerPoint, and they often say what a slide only shows. Comments and deleted text are out: they are remarks about the document, often by other people, not its text. Hidden text (`w:vanish`) is rendered by mammoth like any other text; left as it is (review note).

As built (review S5): markdownify with `heading_style="ATX"` (`#`, not underlined), `escape_underscores=False` and `escape_asterisks=False` (`TEM_grid_03` and `*.dm4` as written; the record is read as text, not rendered as Markdown), `table_infer_header=True` (a Word table has no header row of its own); mammoth with `convert_image=lambda image: []` (no `img` at all, so no data URI and no line) and the style map `p[style-name='Title'] => h1:fresh`. A link within the document (a footnote's number `[1]` and its back link `↑`) is shown as its text, the back link not at all. A slide without a title starts with a line `---`, the separator of slides in pandoc's Markdown, so that its text does not run on from the slide before; MarkItDown's `<!-- Slide number: N -->` is not taken. python-pptx's `has_notes_slide` is asked first: `notes_slide` would create one.

## D4 Into the record, and the cut

The rendering goes into `values["text"]` and is the record's second description by the records requirement of `text-as-written`; nothing in `records.py` changes. It goes through `written.shown` as the UTF-8 bytes of the rendering, the rule for a text file (review M1): the proposal had `written.shown_text`, the rule for a rendering of ours, which has no credential check, while a document can hold `password: hunter2` as any note can. So a line that may hold a credential is left out (counted in `mapped_metadata["credentials_left_out"]`, as the text area does), and a rendering over 4,096 characters is shown as head and tail with `… N bytes left out …` between (bytes of the UTF-8 rendering, the text rule's unit). For a deck its last slides are often "Thank you" or "Questions", and an outline first (all headings, then text) may serve better: a next step once real records are seen. `values["text"]` is the shown text, not the whole rendering: one stored string holds at most `MAX_STRING` characters, as for every format.

With a text the property parts' `name: value` lines leave the record (L7): `text-as-written` decided "only the text" (its L2) so that the same content does not fill the embedding's 512 tokens twice. For office documents the two are not the same content. The summary line keeps title, author, dates, application, pages or slides; the core properties `subject`, `keywords`, `description` and `category` are the author's own words about the document, so they lead the text as `core.<name>: <value>` lines where they are not empty (review S6), the form the tag lines have; company, template and custom properties go out of the record.

## D5 The flag and its channel

"Flag when it goes beyond what we had discussed before": the limits discussed are the per-file read limit of recognition (decision 329: flag past 64 KiB, stop at 1 MiB), the 10 s of `slow extraction` (352), `text-as-written`'s reads (1 MiB head, 16 KiB tail, 80 KiB of a large structured file) and the area's 16 MiB per XML part (`MAX_PART`). The bytes read for the proxy are the measure: they are what the converters will parse, and they are counted as the read limit counts (bytes read from the file, `Budgeted.read_so_far`). 64 KiB would flag almost every document (python-docx's template with one paragraph reads about 28 to 75 kB); 1 MiB is the read limit's stop, the point where recognition refuses, so "beyond" it is the read I take for "beyond what we had discussed". Alternatives: 64 KiB (flags nearly all), 16 MiB (`MAX_PART`, flags only extremes).

The channel, as built (deviation from Q4, review S2): `mapped_metadata` gets `bytes read` (the file's bytes read by the extraction once the proxy is made, `Budgeted.read_so_far`), `xml bytes` (the kept parts' size uncompressed, the sum of their `ZipInfo.file_size`, known before reading them) and `large document text` (`bytes read` past 1 MiB), for every rendered document; visible in `browse` and `records --verbose`, not listed by `modama-chain review`. The crawler's core stays untouched for tonight's staging crawl. The proposal's channel, an extractor's `values["warnings"]` warned at the dataset as `_slow` warns, is the next step, in the review's design: a tuple of extractor markers in the core beside `SLOW_EXTRACTION`, `_slow` generalised to set them anew from the stored extraction, a warning no longer given removed (BACKLOG). Alternative later: every extraction's bytes read measured in the worker like its seconds (a stored field, a migration).

## D6 Failures and the deadline

The rendering runs after the property parts are read; an exception of the converter (or the DTD stop of D2) keeps the metadata, gives no `text`, so the record keeps the tag lines, and puts the message into `mapped_metadata["text not rendered"]`, as `sheets not read` does for a workbook. The extraction does not fail: a failure is retried by every crawl (decision 185), a document the converter cannot render would be converted again every night. A package that is not a ZIP fails as today.

The deadline (review S4): the extraction's limit of 60 s fails the whole extraction, the metadata too, and is retried every night. The rendering (proxy and converter) runs under an interval timer of 30 s (`signal.setitimer`, `SIGALRM`), whose handler raises `TimeoutError` into it; the timer and the previous handler are restored after. Signals arrive only in the main thread: the extraction worker runs `extract` there (nothing else in the worker uses `SIGALRM`; it ignores `SIGINT` only); in another thread the rendering has no deadline of its own. A `TimeoutError` raised inside a library's cleanup could leave it in a bad state; the worker is replaced after 100 tasks anyway.
