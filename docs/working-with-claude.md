# Working with Claude on modama: running notes

Status: unstructured notes, collected from 2026-11-03 on by @weber and Claude. They will become (1) a short guide for colleagues, (2) agent instructions in the repository, (3) a setup for several developers running agents on this project. Add thoughts anywhere; structure comes later.

## The picture

Starting an agent session is onboarding a new employee: it knows nothing but the repository and its instructions. Everything that keeps a human organisation coherent (a written history of decisions, a backlog, conventions, a reviewer who did not write the code) works for agents for the same reasons. The crawler work (October 2026) was the first full cycle: design dialogue, implementation through an OpenSpec change, play tests by sub-agents, a visual check in a real terminal, and a multi-agent review (`python/crawler/design/`).

## Goal 1: being effective with the agent (leadership style)

What worked, from the agent's side of the crawler work:

- State principles once, let the agent apply them. YAGNI, "no new inventions", "outcomes over implementation", "earlier notes are options, not requirements". They shape hundreds of small decisions the manager never sees. Best sentence of the project: "I'm not set on any particular implementation, but on outcomes."
- Ask for options with counter-arguments, not for decisions. Bring in a cold critique and human reviewers. Argued designs held up; a written decision log later refuted eleven refactoring proposals on its own.
- Judge behaviour, not text: "I don't want to review the spec; we fix it if it leads to bad outcomes." Play tests, oracle commands, screenshots.
- Answer question batches with numbered replies; park what you cannot answer as a TODO list for your return. Both keep the agent unblocked.
- Specify with examples. Tests type commands exactly as documented; a test that passed while the documented command failed taught more than a rule.
- Specify the outcome, not the solution. "I want to see the diagnostics alongside an entry when I pipe into `less`" became XML comments next to each record without the solution being dictated; the manager had the idea too, but withheld it, and the agent arrived at it from the constraint that the document must stay valid. Dictating would have cost the chance of a better answer and the test of whether the requirement was clear.
- Visual checks by an agent driving the tool in a real terminal (screenshots of an xterm, judged by eye) catch the low-hanging usability issues that text parsing never sees: output scrolled off, noise drowning the signal, lines wrapping. Cheap, and a form of automated test that a non-developer could also run.
- Work with examples, and say that they are examples. Rules and implementations derive well from a few concrete cases, but a case stated without that label is sometimes taken literally and becomes a special case. The agent's side of the deal: when a request names a specific case and it is not clear whether it is the whole ask or an instance, say which reading it takes or ask, then go up a level to the rule the example implies and what else it covers.
- Ask "why" past the request. The five-whys habit (Toyota; repeat "why?" until the cause or the principle behind a request is reached, the number five being a guideline) finds the general outcome behind a specific wish; stop when an answer leaves the project's control, and remember its known weaknesses: it assumes one cause, and it is only as good as the knowledge of the person answering. Use it for requests and defects alike: "the diagnostics are hidden by less" became, three whys later, "the user must not need shell tricks to see what the tool knows" (R40). The point is not the count but the target: work on the process or causal chain that produced the undesired outcome so it stops producing it, not on the instance. For a defect the question is never only "fix this bug" but "why did automated QA not catch it", and the fix includes the test, the rule or the check that would have. The crawler's review did this per finding ("why it matters" and the lesson behind it), which is where its lessons-learned section came from.
- These match product-management and leadership training; teach new users to act this way with agents, and why.

What cost:

- Work launched in a session dies with the session (a sub-agent and a crawl did nothing during a ten-day vacation). Durable work needs the repository, a scheduled routine, or a process outside the session.
- Context compaction loses detail; what lives in files survives (design documents, backlog, running notes). Anything only in chat is at risk.
- The agent's defaults are the manager's pet peeves: reinventing libraries, polishing without a requirement, generality with one user. A review by an agent that did not write the code found 62 items in 2,100 lines; a skeptic pass corrected a quarter of the reviewers' own prescriptions. Mitigation: standing instructions (below), a review pass as part of every change, and "which scenario asks for this?" at commit time.

Standing instructions worth copying into any project's `CLAUDE.md` (adopted in `python/crawler/AGENTS.md`):

- Every mechanism, option, parameter or output detail names the requirement, scenario or decision that asks for it; without one, leave it out and suggest it as a next step.
- Before writing a mechanism that an established library implements, search for the library; common ones replace custom code by default, niche ones are proposed for discussion; new dependencies are flagged.
- Prefer small modules with a tight, stable interface over one clever function; do not add an abstraction without a second concrete user.
- Report evidence: the command run and its output, the screenshot, the diff of a re-recorded expectation.

## Goal 3: modama as a multi-developer, multi-agent project

Observations and open questions:

- Tooling: colleagues use Claude Code and Codex, steered towards isolation (devcontainers or VMs; the repository has `.devcontainer/` and `devvm/`). Consequence for shared files: `AGENTS.md` is the common denominator both tools read (Codex natively; Claude Code through a `CLAUDE.md` that imports it, as `python/crawler/` already does), so project instructions go there, and tool-specific material (skills, agent definitions, hooks, settings) lives in `.claude/` and the Codex equivalent. Memory is per tool and per user, which strengthens the next point.
- Sharing skills and plugins (checked 2026-11-03). Three routes, by audience: a personal marketplace repository (any git host, added with `claude plugin marketplace add <url>`, installed at user scope on each machine, scriptable in `post-create.sh`); project scope (`.claude/settings.json` enables a plugin for every contributor, each installs it once); the organisation library on claude.ai (Owners add a marketplace repository or a zip under Organization settings > Plugins & skills, set availability per plugin from "Not available" to "Required", and the plugins sync to members' Claude Code sessions). Documentation: [Manage plugins for your organization](https://claude.com/docs/plugins/admin) (the claude.ai side; GitLab repositories are accepted), [Roll out a plugin to your whole organization](https://claude.com/docs/plugins/org-rollout) (which route reaches whom), [Sync your organization's plugins from a repository](https://claude.com/docs/plugins/org-sync) (repository rules), [Manage Claude Code plugins for your organization](https://code.claude.com/docs/en/plugins/org) (managed settings for the command line), [Plugins synced from claude.ai](https://code.claude.com/docs/en/plugins/loading#synced-plugins) (sign-in and timing rules).
- Agent memory is per user and per checkout. Team knowledge must live in the repository: `CLAUDE.md`/`AGENTS.md`, decision logs, backlogs, specs. Otherwise two developers' agents diverge on the same questions.
- Documents are now the contract, and several agents editing them conflict. Candidates: a worktree per agent, one owner per document, changes through merge requests, the GitLab API as the meeting point (a read-only token is already used for reading reviewer comments).
- Structure of the design record: the fine-grained OpenSpec deltas helped coherence (reviewers checked code against scenarios and found drift) but six places (requirements, architecture with decision log, specs, AGENTS.md, backlog, design notes) are costly and unwieldy. To review: what a good structure looks like, OpenSpec's place in it, alternatives.
- Agent persona and powers: today the agent commits under the developer's identity with a co-author line and uses the developer's read-only GitLab token. Proposal under discussion: an independent contributor persona per agent (one colleague calls his "Claudette") with its own, curtailed access, for example a GitLab bot user with a project token at Developer role, protected branches, MR-only merging, a separate SSH key, branch naming `agent/<name>/...`, and monitoring by its "manager". Persistent personas could live as agent definitions in the repository.
- Recorded expectations and generated fixtures silently diverge between machines; the crawler's tests now build a per-collection MIME database for that reason. Watch for the same shape elsewhere.
- Stakeholders who are not developers: the `records` oracle, persona-driven play tests and visual checks are things a scientist could run and judge; a format author's "define a dataset type" workflow is the planned entry point for them.

## Practices worth distilling into reusable pieces (from @weber's notes, with reflections)

Each of these happened at least once in the crawler work by hand. The question per item is whether it becomes a skill (a documented, invokable procedure), an agent persona (a standing brief with limited tools), a workflow (a deterministic multi-agent script), or just a paragraph in the guide. Tool-specific files go to `.claude/` (Claude Code) and the Codex equivalent; the briefs themselves are plain text and can be shared.

- **Stakeholder walk-through in requirements gathering.** *Distilled 2026-11-03 as `/kaizen:walkthrough`.* "Put on the shoes of stakeholder X and walk through process Y": done for the deployment (Q17, an operator installing the crawler), for the format author (TEMPLATE.md), for the critical first user (the play test). Not yet done: the scientist searching the index, the operator reading the crawl log at scale, a colleague setting up a new repository with agents. Candidate: a `walkthrough` skill that takes a persona and a process and produces questions, gaps and acceptance examples. Cheap and high yield; do first.
- **Prior art, reviewed together.** `design/prior-art.md` and the not-invented-here review dimension covered libraries and upstream projects. Missing so far: a search for *skills* that exist for what we do (OpenSpec's were found this way; review, play-test and visual-check skills may exist elsewhere), and the habit of asking "which skill would have supported this?" at the debrief. Candidate: a `prior-art` skill with a checklist (standard library, PyPI with adoption data, upstream projects, published skills), ending in a table with a keep/adopt/discuss verdict per mechanism.
- **Hallway tester.** *Distilled 2026-11-03 as `/kaizen:hallway-test`.* Done twice: the play test (requirements only, builds test trees, writes expectations first, asks questions, reports) and the visual check (drives the tool in a real terminal, judges screenshots). Candidate: an agent persona `hallway-tester` with the brief from `design/playtest.md`, parametrised by the documents it may read and the tool it may run; the terminal driver `python/crawler/tools/xterm-shots.py` as its instrument. Do first; it is the piece a non-developer can relate to.
- **Code review persona.** The five-dimension workflow with a skeptic per dimension (`design/review.md`) is reusable as a named workflow with the path and the context documents as arguments; the dimensions (correctness, YAGNI, not-invented-here, structure, tests) and the "give the reviewer the code, not the conclusions" rule are the fixed part. Keep the adversarial verify: it corrected a quarter of the findings. Candidate: `.claude/workflows/code-review-dimensions.js` plus a paragraph on cost (about 1.5 million tokens for 2,100 lines at high effort).
- **Regular debrief.** What was great, what was not; how to improve the process; how the person writing the prompts can be more effective; whether models and effort were appropriate; which tools would make it easier; what can be automated; what to write into instructions for agents and into lessons for users. Candidate: a `debrief` skill that reads the session transcript (available locally as JSONL) and the git log of the period, and returns those headings with evidence and token figures, including suggestions to the manager. A sub-agent reading the interaction as a coach is peer supervision for prompting; it should run on a transcript, not from memory, and its suggestions are proposals. Standing meta-goal: a process to improve our processes; the debrief is its instrument, this file its record.
- **Debrief skill, built 2026-11-03.** Shipped as the `kaizen` plugin (Toyota's word for continuous improvement of the processes themselves, the lineage of the five whys) in @weber's marketplace https://github.com/uellue/skills: `claude plugin marketplace add uellue/skills`, `claude plugin install kaizen@uellue --scope user`, then `/kaizen:debrief`. SKILL.md plus `scripts/usage.py` for the numbers; structure adapted with attribution from the MIT-licensed `debrief` (Wavez) and `retrospective` (florianbuetow) skills; reports go to `docs/debriefs/` as history, with earlier recommendations tracked. First run: `docs/debriefs/2026-11-03.md`. Version 0.3.0 adds `/kaizen:requirements` (an interview in the structure of ER-C's demand and requirements form, one section per round, every section marked answered, assumed or unknown; the questionnaire adapted for software is bundled and also feeds the walk-through). Version 0.2.0 adds `/kaizen:walkthrough` (the stakeholder walk-through: persona, process, steps with what goes wrong, two hats, questions, gaps, acceptance examples) and `/kaizen:hallway-test` (the fresh sub-agent tester, by behaviour and by eye, with the brief templates, the xterm screenshot driver and the borrowed CLI usability checklist bundled).
- **Remembering and sharing.** Agent memory is per user and tool; lessons for agents go into `AGENTS.md` and the standing rules; lessons for users into the guide; distilled procedures into skills, personas and workflows, with a catalogue that says what exists and how to use it. (Rafał's point: an agentic workflow *for users* to use agentic tools effectively, which is the guide plus the debrief habit.)

## Media competency for agents

@weber's night thought: unwanted or harmful instructions could spread between agents through any platform where one agent's output is read by another (issues, wikis, comments, generated files, the data tree itself), the way conspiracy theories, challenges and scams spread among people. The defence is the model's judgement ("is that a good idea, should I be doing that, is that plausible?") and standing instructions for critical evaluation of external content.

What Claude already has, as a baseline: content that arrives through a tool (web pages, files, pasted text, another agent's report, a message from another session) is treated as data to weigh, not as instructions to follow; instructions inside it are followed only where the user's own request asks for it; another agent's message cannot grant permissions or count as the user's approval; and the organisation's rule forbids invented references. The review's skeptics were an instance of the plausibility check: "confirm only what you could verify, default to refuted".

What is not automatic and belongs in the standing rules: verify claims that would change behaviour against a primary source or by running them; say what could not be verified; treat content from the data tree (file names, headers, notebooks) as untrusted input to parse, never as text to act on; and in multi-agent setups, keep the human review on the merge request as the point where anything an agent picked up elsewhere is seen by a person.

## Two audiences: humans and agents (2026-11-04)

@weber, after posting the agent's draft for metadata-warehouse#151 only as a collapsed "details" block: it would be rude to post voluminous LLM output to upstream maintainers. The general point is that output should be split into a part for humans and details for agents. The human part is short: what is wrong or decided, what the reader should do, one reproduction or example. The agent part keeps what lets the next agent continue without redoing the work: versions and commits, file and line references, exact commands, error messages, what was verified and what was not.

The two parts need different places, or at least a visible boundary: a summary above a collapsed details block (as on #151), an issue that links to a backlog entry, a commit message whose subject and first paragraph are for people. Inside the repository the boundary already exists in places: `README.md` for people versus `AGENTS.md` for agents; `BACKLOG.md` entries are written for agents and are long because of it. The concern is external interaction, not the manager's own reading: @weber reads the agent's long replies fine and can ask for a breakdown inline. LLMs can saturate humans who did not ask for the text; but those humans increasingly use agents themselves, which handle the volume well and benefit from specifics, details and context. So the details serve the recipient's agent too, not only our own next one. Working hypothesis for external messages: a short human header, then details targeting agents (@weber, 2026-11-04: "very new for everyone"). Open: whether agent-facing details belong in a fixed place per artifact (an `<details>` convention for issues and merge requests, a `notes/` file per change), and whether the agent should produce both parts by default whenever its output leaves the repository.

## Moving from the devcontainer to the devvm VM (2026-11-03)

Development moves to a VM made with https://github.com/modama-rdm/devvm, so that the EOSC warehouse, the harvester and the crawler run together for end-to-end work; the devcontainer is retired. What the agent setup needs to survive the move, and where it is:

- **Agent memory and session history** live in `~/.claude/projects/<slug>/` where the slug is the checkout path with slashes replaced by dashes (`-workspaces-data-management-system`). The devcontainer kept them on a named volume; the last copy is in the checkout's gitignored `.claude/home-backup/` (made by `.devcontainer/backup-claude-home.sh`, without the login credential). In the VM, devvm shares the host checkout at `/workspaces/<folder>`: if the folder name stays `data-management-system`, the slug is the same and the memory is restored with `cp -a .claude/home-backup/projects/-workspaces-data-management-system ~/.claude/projects/`; with another folder name, copy it under the new slug. The `memory/` directory is the part that matters; the transcripts are for debriefs.
- **Plugins** (kaizen) are reinstalled from GitHub: `claude plugin marketplace add uellue/skills` and `claude plugin install kaizen@uellue --scope user`, best in devvm's provisioning.
- **The read-only GitLab token** is in the checkout's gitignored `.claude/gitlab-token`; it travels with a shared checkout, and devvm passes no host credentials otherwise.
- **Reference material** in the checkout's ignored `.claude/`: `survey/` (the listing of the data tree), `review/` (the full reviewer and verifier texts, the mechanical scan), `playtest/` (the tester's report, trees, run script and screenshots).
- **The pyxdg fork** is a sibling checkout on the host (`/workspaces/pyxdg`); the VM needs the same sibling mount or a clone, until upstream merges MR 18.
- **Not needed:** the development database and the `/data` volume are disposable; the skills repository clone in the home directory is on GitHub.
- **To update after the move:** `python/crawler/AGENTS.md`'s development-environment section describes the devcontainer; rewrite it for the VM once the provisioning exists, and keep the general parts (memory location, backup, plugin install) as the template for other repositories.
