# Embedding throughput: one small encoder on CPU and GPU

Research note, 2026-11-13, for the warehouse's embedding (`BAAI/bge-small-en-v1.5` through fastembed and ONNX Runtime) and the coming benchmark on a Grace-Hopper GH200. Written by an agent at @weber's request ("research online what people did to get maximum performance and efficiency out of these kinds of models / tasks, both CPU and GPU"; "How large is the model? I'm wondering if parallel tasks on the GPU will share the same model memory? Resp. would there be a reason to have multiple copies of the model?"; and on cache and memory layout: "66 MB is close to the total L3 cache we have here, so one copy per core exhausts it"). Not yet reviewed by a person. No code was changed, nothing was installed or measured; numbers marked *estimate* are arithmetic from the cited figures, not measurements.

## For people

- **How large:** 33.4 M parameters. That is 67 MB in fp16 and 133 MB in fp32. Without the embedding table, which is only looked up and never multiplied, the 12 layers are 21.3 M parameters: 43 MB in fp16, 85 MB in fp32. On a GPU in fp16, one copy is well under 1 GB including activations. Each extra *process* also costs its own CUDA context, which one forum report puts at about 500 MB (not an official figure; to be measured). The H100 has 96 GB of memory on a GH200, so memory sets no practical limit on the number of copies.
- **Do parallel tasks on the GPU share the weights?** Within one process, yes. Several threads can call `Run()` on one ONNX Runtime session at the same time ("It's safe to invoke Run() on the same session object in multiple threads", an ONNX Runtime maintainer). A PyTorch model can likewise run on several CUDA streams. Separate processes do not share weights: each loads its own copy and creates its own CUDA context. MPS shares the GPU's scheduling between processes, not their memory. Each MIG slice has its own memory, so each slice needs its own copy.
- **A reason for several copies?** Not memory, but overlap: while one copy waits for the CPU (tokenising, Python, copies), another keeps the GPU busy. NVIDIA's Triton guide: "Typically, having two instances of a model will improve performance". The established way for embedding encoders is one server per GPU holding one model, with token-budget dynamic batching and several CPU threads tokenising. Text Embeddings Inference (TEI) and Infinity work this way, as does Triton's default of one instance per GPU, plus a second to overlap.
- **L3 and NUMA:** one weight copy per core does exhaust L3, but this hardly costs throughput as long as a sub-batch holds enough tokens. A matrix multiplication reuses each weight across every token of the sub-batch, so 32 short texts already do about 120 FLOP per byte moved (*estimate*), well above what Grace's memory needs to keep the cores busy (about 14 FLOP/B, *estimate*). What scales with the number of runs rather than with tokens is the per-run conversion of 53 fp16 weight tensors to fp32 that our profile shows. That conversion grows in weight with short texts and small sub-batches. On the GH200, keep the CPU benchmark's memory on the CPU's NUMA node: NVIDIA warns that pages can otherwise land in the GPU's memory.

Changes most likely to pay off, ranked:
- **1** GPU: one fp16 model copy per GPU, length-sorted batches sized by a token budget (TEI's default is 16,384 tokens per batch), and 2 to 4 feeders tokenising in parallel. fp16 alone gave 2.9× over fp32 on GPU in Sentence Transformers' benchmark ([sbert efficiency](https://sbert.net/docs/sentence_transformer/usage/efficiency.html); [TEI README](https://github.com/huggingface/text-embeddings-inference); [Triton optimization](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/optimization.html)).
- **2** GPU: tokenising becomes the bottleneck once the model is fast. Our profile implies about 3.7 ms of tokenizer CPU per long text (*estimate*), so feeding thousands of texts per second takes many cores. Measure it first ([TEI](https://github.com/huggingface/text-embeddings-inference) has `--tokenization-workers`, by default one per core).
- **3** Grace CPU: ONNX Runtime's bf16 fast-math GEMM (`mlas.enable_gemm_fastmath_arm64_bfloat16`). The vendor reports up to 65 % on Graviton3 for BERT-class models. It changes the numbers slightly, so check that the embeddings agree ([AWS blog](https://aws.amazon.com/blogs/machine-learning/accelerate-nlp-inference-with-onnx-runtime-on-aws-graviton-processors)).
- **4** CPU: int8 quantization. It gave 3.08× on short texts in one benchmark, and Intel's int8 bge-small lost 0.58 % retrieval NDCG@10. It changes every vector, so it needs a decision to re-embed everything ([sbert v3.4.1 docs](https://github.com/huggingface/sentence-transformers/blob/v3.4.1/docs/sentence_transformer/usage/efficiency.rst); [Intel/HF blog](https://huggingface.co/blog/intel-fast-embedding)).
- **5** GPU: padding-free attention (FlashAttention on variable-length, packed inputs). With fp16, Sentence Transformers measured a median 3.87× over fp32 (against 2.92× for fp16 alone). Since we already sort by length, the extra gain over our own path will be smaller than in their mixed-length data. In ONNX Runtime this "packing mode" exists for CUDA only ([sbert](https://sbert.net/docs/sentence_transformer/usage/efficiency.html); [ORT `convert_to_packing_mode.py`](https://github.com/microsoft/onnxruntime/blob/v1.24.4/onnxruntime/python/tools/transformers/convert_to_packing_mode.py)).
- **6** CPU: a model file of our own, with the fp16→fp32 conversions folded in and the GELU fused, worth up to about 12 % by our profile (11 % GELU, 1 % Cast). ONNX Runtime 1.24.4 registers the GELU fusion for CPU, so first find out why it did not apply ([ORT graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)).
- **7** CPU placement on the GH200: memory bound to the CPU's node, automatic NUMA balancing off as NVIDIA recommends, and a test of one process with many threads sharing one session (one weight copy) against one process per core ([Grace tuning guide](https://docs.nvidia.com/grace-perf-tuning-guide/os-settings.html); [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)).

No credible source compares CPU and GPU energy per embedding. The GH200 reports module, GPU and Grace power, so the benchmark can measure joules per text itself (last section).

Our own measurements are in `python/crawler/openspec/changes/cpu-budget/design.md` ("The budget against today, measured" and "Profile of one batch on long texts (249, 2026-11-13)") and in `docs/research/cpu-oversubscription.md`.

### 1. The model's size

From [`config.json`](https://huggingface.co/BAAI/bge-small-en-v1.5/blob/main/config.json): `hidden_act` gelu, hidden 384, 12 layers, 12 heads, intermediate 1536, 512 positions, vocabulary 30,522, `torch_dtype` float32. Counted from these (*estimate*, and the counts agree with the 33.4 M that the [Intel/HF blog](https://huggingface.co/blog/intel-fast-embedding) cites from the Hub):

| Part | Parameters | fp32 | fp16 |
|---|---|---|---|
| word, position and type embeddings, LayerNorm | 11.92 M | 47.7 MB | 23.8 MB |
| 12 encoder layers (Q, K, V, O, two FFN matrices, two LayerNorms; 1.774 M each) | 21.29 M | 85.2 MB | 42.6 MB |
| pooler (if exported) | 0.15 M | 0.6 MB | 0.3 MB |
| **total** | **33.4 M** | **133 MB** | **67 MB** |

The 66 MB file `model_optimized.onnx` of `qdrant/bge-small-en-v1.5-onnx-q` is consistent with fp16 storage. Its [model card](https://huggingface.co/Qdrant/bge-small-en-v1.5-onnx-Q) says only "Quantized ONNX port of BAAI/bge-small-en-v1.5" and names no tool or level. Our profile (design.md, 249) shows that it computes in fp32 and "casts 53 float16 tensors" on every run. Its GELU appears as Mul, Add and Tanh, that is, the tanh approximation, although the original model's `hidden_act` is the erf `gelu`. So the export probably went through an optimizer that approximates GELU. That is an inference; the card does not say.

Work per token (*estimate*): about 2 × 21.3 M = 42.6 MFLOP in the matrix multiplications, plus about 0.8 MFLOP per layer for attention at 512 tokens. That makes about 52 MFLOP per token, or about 27 GFLOP for a 512-token text. Our VM measured about 530 ms of CPU per such text (design.md, H1). That is about 50 GFLOP/s per core, roughly half of what one Zen 2 core can do in fp32 (2 × 256-bit FMA per cycle, an assumption about the EPYC 7F72, not measured).

### 2. GPU: one copy or several (question 1)

**Within one process the weights are shared.**
- ONNX Runtime: "It's safe to invoke Run() on the same session object in multiple threads. No need for any external synchronization." (Pranav Sharma, maintainer, [onnxruntime#114](https://github.com/microsoft/onnxruntime/issues/114), 2018; the same thread has a 2024 report of concurrency bugs with the TensorRT provider, said to be fixed). The CUDA provider's option `use_ep_level_unified_stream` "Uses the same CUDA stream for all threads of the CUDA EP" and is off by default. It is "implicitly enabled by `has_user_compute_stream`, `enable_cuda_graph` or when using an external allocator" ([CUDA EP docs](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)). From this wording I infer that by default, concurrent `Run()` calls from different threads get their own streams; the page does not say so outright. With CUDA graphs, "`Run()` MAY NOT be invoked on the same `InferenceSession` object from multiple threads". I/O binding: "should be utilized to avoid overhead resulting from copies on inputs and outputs" (same page). For us the inputs are small: a batch of 32 × 512 int64 token ids is 131 kB (*estimate*).
- Sessions in one process can also share weights explicitly. The `PrePackedWeightsContainer` "holds pre-packed weights of shared initializers to be shared across sessions using these initializers and thereby provide memory savings" ([C# API docs](https://onnxruntime.ai/docs/api/csharp/api/Microsoft.ML.OnnxRuntime.PrePackedWeightsContainer.html); the C++ API has `Ort::PrepackedWeightsContainer`). I did not find it in the Python API.
- PyTorch: "operations from different streams can execute concurrently in any relative order" ([CUDA semantics](https://docs.pytorch.org/docs/2.15/notes/cuda.html)), so one module run on several streams uses one copy of the weights. CUDA tensors can be shared between processes, with caveats: "either the `spawn` or `forkserver` start method are required to use CUDA in subprocesses", and "the sending process is required to keep the original tensor as long as the receiving process retains a copy" ([multiprocessing notes](https://docs.pytorch.org/docs/2.15/notes/multiprocessing.html)).

**Across processes they are not.**
- Each process has its own CUDA context. Its size is not documented officially. A PyTorch forum user reports "a large (~500MB) cuda context created per process on GPU" ([forum thread](https://discuss.pytorch.org/t/cuda-context-size-per-process/79976); a user report, not documentation). CUDA's lazy loading "reduces memory overhead, both on GPU memory and host memory" ([CUDA 12.2 guide, Lazy Loading](https://docs.nvidia.com/cuda/archive/12.2.1/cuda-c-programming-guide/lazy-loading.html)). A search summary says it has been on by default since CUDA 12.3; I did not open that page.
- MPS: "MPS is useful when each application process does not generate enough work to saturate the GPU", and "MPS allows the leftover GPU capacity to be occupied with CUDA kernels running from other processes". Without MPS, "each client context allocates independent context storage and scheduling resources" ([When to Use MPS](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html)). MPS shares scheduling and context resources. It does not share model weights; each client allocates its own.
- MIG: the H100 SXM offers "Up to 7 MIGS @ 10GB each" ([H100 page](https://www.nvidia.com/en-us/data-center/h100/); the MIG guide's pages with the details were not fetched). Each slice has its own memory, so each needs its own copy. MIG is for isolating several applications, not for one job's throughput.

**How the servers do it.**
- Triton: "By default, a single execution instance of the model is created for each GPU" ([model configuration](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/model_configuration.html)). "Typically, having two instances of a model will improve performance because it allows overlap of memory transfer operations (for example, CPU to/from GPU) with inference compute", and "Smaller models may benefit from more than two instances" ([optimization](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/optimization.html)). Dynamic batcher: "By default the dynamic batcher will create batches as large as possible up to the maximum batch size", and "Preferred batch sizes should not be used for most models" ([batcher](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/batcher.html)). Neither page says outright whether an instance holds its own copy of the weights.
- TEI (v1.9.4, [README](https://github.com/huggingface/text-embeddings-inference)): "Token based dynamic batching" and "Optimized transformers code for inference using Flash Attention, Candle and cuBLASLt". `--max-batch-tokens` (default 16,384): "This represents the total amount of potential tokens within a batch", "one critical control to allow maximum usage of the available hardware". `--tokenization-workers`: "Default to the number of CPU cores on the machine". Its BERT path calls `flash_attn_varlen` with `cu_seqlens`, that is, packed sequences without padding ([`flash_bert.rs`](https://github.com/huggingface/text-embeddings-inference/blob/main/backends/candle/src/models/flash_bert.rs)). **On the GH200:** the Hopper image is listed for x86_64 only. For aarch64 there is only a CPU image (`cpu-arm64-1.9`), so TEI on the GH200's GPU needs a build from source; I did not check whether that works.
- Infinity: "All visible CUDA GPUs are used by default, with a complete model replica on each GPU"; its native v3 server "is written in Rust and uses LibTorch" ([README](https://github.com/michaelfeil/infinity)).
- vLLM: pooling models are supported "primarily for convenience", and this "is not guaranteed to provide any performance improvements over using Hugging Face Transformers or Sentence Transformers directly" ([pooling models](https://docs.vllm.ai/en/latest/models/pooling_models.html)). Not the tool for this job.

**Conclusion:** one model per GPU in one serving process, batches as large as the token budget allows, and enough CPU threads to tokenise. A second instance, or a second feeder process, serves to overlap the CPU's work, not to add memory. More processes than that pay one CUDA context each and, without MPS, time-slice the GPU.

### 3. GPU optimisations for small encoders (question 2)

- **fp16/bf16.** Sentence Transformers' current benchmark (RTX 3090; models from all-MiniLM-L6-v2 to bge-m3; median speedup over PyTorch fp32): fp16 2.92×, bf16 3.84×, and fp16 with FlashAttention-2 and input unpadding 3.87×, "without reducing average task quality" ([efficiency docs](https://sbert.net/docs/sentence_transformer/usage/efficiency.html); [source rst](https://github.com/huggingface/sentence-transformers/blob/main/docs/sentence_transformer/usage/efficiency.rst)). The older v3.4.1 page, for short texts on GPU: "1.46x for ONNX, and ONNX-O4 reaches 1.83x whereas fp16 and bf16 reach 1.54x and 1.53x respectively. So, for shorter texts we recommend ONNX on GPU" ([v3.4.1 rst](https://github.com/huggingface/sentence-transformers/blob/v3.4.1/docs/sentence_transformer/usage/efficiency.rst); O4 = "ONNX with float16 precision and O4 optimization"). In ONNX Runtime, the transformer optimizer's `--float16` converts a model to "use float16 to boost performance using mixed precision on GPUs with Tensor Cores" ([transformer optimization](https://onnxruntime.ai/docs/performance/transformers-optimization.html)). TF32 is on by default in the CUDA provider (`use_tf32`, default 1, [CUDA EP](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)), so even an fp32 model uses the Tensor Cores for its GEMMs.
- **Padding removal.** Sentence Transformers: unpadding "automatically skips padding for text-only inputs by concatenating them into a single sequence". Flattening "improves throughput and reduces VRAM use in this benchmark, with the largest gains on the mixed dataset, where input lengths range from 10 to 500 tokens" (bge-base, [source rst](https://github.com/huggingface/sentence-transformers/blob/main/docs/sentence_transformer/usage/efficiency.rst)). TEI does the same (above). TensorRT's BERT demo: "By concatenating each input id into a single long input id ... we can eliminate the wasted computation in the input paddings" ([demo/BERT README, release/10.13](https://github.com/NVIDIA/TensorRT/blob/release/10.13/demo/BERT/README.md)). ONNX Runtime has `convert_to_packing_mode.py`, which inserts `RemovePadding`, `PackedAttention` and `RestorePadding` ([v1.24.4](https://github.com/microsoft/onnxruntime/blob/v1.24.4/onnxruntime/python/tools/transformers/convert_to_packing_mode.py)). `PackedAttention` exists under `contrib_ops/cuda/bert/` but not under `contrib_ops/cpu/bert/` (checked by URL at v1.24.4), so it is GPU only. Sorting by length, which we already do (H1), removes most padding by itself. Sentence Transformers sorts too (`length_sorted_idx = np.argsort([-self._text_length(sen) ...])` in `encode`, [v3.4.1 source](https://github.com/huggingface/sentence-transformers/blob/v3.4.1/sentence_transformers/SentenceTransformer.py)).
- **Fused kernels.** The CUDA provider sets environment switches for its attention kernels (`ORT_DISABLE_FLASH_ATTENTION`, `ORT_DISABLE_MEMORY_EFFICIENT_ATTENTION`, `ORT_DISABLE_FUSED_ATTENTION`, … in [`attention_common.h`](https://github.com/microsoft/onnxruntime/blob/v1.24.4/onnxruntime/contrib_ops/cpu/bert/attention_common.h)). Which kernel runs depends on the model graph having a fused `Attention` node (section 4). TensorRT through Triton: "The TensorRT optimization provided 2x throughput improvement while cutting latency in half" (DenseNet, [Triton optimization](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/optimization.html)); no figure for BERT encoders there. CUDA graphs "remove CPU overhead associated with launching CUDA kernels" but need fixed shapes bound through I/O binding ([CUDA EP](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)), which conflicts with variable lengths unless lengths are bucketed.
- **Batch sizes people use.** TEI: by tokens, default 16,384. Sentence Transformers v3.4.1 tested MiniLM-L6 at batch 16 to 256, bge-base at 16 to 128, and used "each backend's best tested batch size". Intel: peak throughput at batch 128 with 256-token texts ([Intel/HF blog](https://huggingface.co/blog/intel-fast-embedding)).
- **The tokenizer as a bottleneck.** In our profile, the Rust tokenizer was 0.65 % of the samples at FILL 500: 0.65 % × 141.8 s ÷ 250 texts ≈ 3.7 ms per long text, about 270 texts/s per core (*estimate*). Our FILL 500 texts may be much longer than the 512 tokens kept. Whether fastembed's tokenizer encodes the whole text before truncating I have not checked; if it does, cutting the text in characters first would be a cheap lever. On a GPU that does thousands of texts per second, tokenising then needs tens of cores, which is why TEI defaults to one tokenizer worker per core. "The Framework Tax" (EMNLP 2023) found that at small batch sizes the framework's overhead, not FLOPs, sets the latency, for BERT-base on GPU ([arXiv 2302.06117](https://arxiv.org/abs/2302.06117)).

**Scale (*estimate*).** H100 SXM, vendor figures: FP16 Tensor Core "1,979 teraFLOPS" with sparsity (footnote "* With sparsity"; dense is half), FP32 "67 teraFLOPS", memory bandwidth "3.35TB/s" ([H100 page](https://www.nvidia.com/en-us/data-center/h100/); the GH200's H100 has different memory and may differ in clock and power). At 20 to 30 % of the dense fp16 peak, 27 GFLOP per 512-token text gives about 7,000 to 11,000 long texts/s. Our VM manages about 2 per core. The only measured number for this model on GPU I found: fastembed's GPU example embeds 500 copies of one 43-character sentence in "43.4 ms ± 2.06 ms" on the GPU against "4.33 s ± 591 ms" on the CPU, on unnamed Colab hardware ([FastEmbed GPU](https://qdrant.github.io/fastembed/examples/FastEmbed_GPU/)). It is a smoke test, not a benchmark.

### 4. CPU optimisations (question 3)

**Graph optimisation.** ONNX Runtime fuses at load time ("ONNX Runtime automatically applies most optimizations while loading transformer models", [transformer optimization](https://onnxruntime.ai/docs/performance/transformers-optimization.html)). GELU fusion, LayerNorm fusion, BERT embedding layer fusion, attention fusion, skip-LayerNorm fusion and bias-GELU fusion are listed for "CPU, CUDA, ROCm" ([graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)). In the v1.24.4 source, `FastGeluFusion` (the tanh form our model has) is registered for CPU too ([`graph_transformer_utils.cc:391`](https://github.com/microsoft/onnxruntime/blob/v1.24.4/onnxruntime/core/optimizer/graph_transformer_utils.cc#L391)), and `contrib_ops/cpu/bert/fast_gelu.cc` exists. Yet our profile shows the GELU unfused (Mul, Add, Tanh: 11 %) and 53 Casts per run. A hypothesis to check by opening the graph: the Casts sit between initializers and the arithmetic and break the patterns, or constant folding does not fold them. If so, a model file stored in fp32 (or with the Casts folded), run once through `optimizer.py --model_type bert` offline, would remove both. That is worth up to about 12 % by the profile, with identical numbers if only the storage changes. That last point is to be verified by comparing embeddings.

**int8.** ONNX Runtime: "it is recommended to use dynamic quantization for RNNs and transformer-based models". Arm has "no such issue" with saturation, and "Quantization is not a loss-less transformation" ([quantization](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)). Sentence Transformers v3.4.1 (i7 CPU, short texts): "ONNX with int8 quantization is even stronger with a 3.08x speedup", and "For longer texts, ONNX and OpenVINO can even perform slightly worse than PyTorch". Its decision chart asks "Is a 0.4% accuracy loss acceptable?" before recommending `openvino-qint8` ([v3.4.1 rst](https://github.com/huggingface/sentence-transformers/blob/v3.4.1/docs/sentence_transformer/usage/efficiency.rst)). Intel's static int8 `bge-small-en-v1.5` on a Xeon 8480+: "up to 4x improvement compared to the baseline" (bf16) in throughput at 256 tokens. On MTEB, reranking MAP fell from 0.5836 to 0.5826 and retrieval NDCG@10 from 0.5168 to 0.5138 ([Intel/HF blog](https://huggingface.co/blog/intel-fast-embedding); vendor-authored). Mixing int8 and fp32 vectors in one index is not an option, so int8 means re-embedding everything, a decision for @weber.

**OpenVINO** targets Intel CPUs (Sentence Transformers' chart: "Do you have an Intel CPU?" → `openvino`, else `onnx`), so it is not a candidate for Grace.

**aarch64 / Grace.**
- Grace: "72 Arm Neoverse V2 Cores with 4x 128b SVE2 per core" ([Grace tuning guide](https://docs.nvidia.com/grace-perf-tuning-guide/index.html)). AWS's Graviton table lists Neoverse V2 as Armv9.0-a with "sve2, sve-int8, sve-bf16, sve-bitperm, sve-crypto" on top of V1's "sve, rng, bf16, int8", and "4x Neon/SVE 128bit vectors" ([aws-graviton-getting-started README](https://github.com/aws/aws-graviton-getting-started/blob/main/README.md)). Arm's own pages I fetched do not list the extensions, so check `lscpu` flags (`bf16`, `i8mm`, `sve2`) on the machine.
- ONNX Runtime's CPU kernels on aarch64 are MLAS. At v1.24.4 MLAS detects I8MM and BF16 at run time ([`mlas/lib/platform.cpp`](https://github.com/microsoft/onnxruntime/blob/v1.24.4/onnxruntime/core/mlas/lib/platform.cpp), `HWCAP2_SVEI8MM`, `HWCAP2_BF16`). It replaces its SGEMM with Arm's KleidiAI kernels only `if (...HasArm_SME())` (lines 611 to 620). The build option `onnxruntime_USE_KLEIDIAI` defaults to OFF ([CMakeLists.txt:93](https://github.com/microsoft/onnxruntime/blob/v1.24.4/cmake/CMakeLists.txt#L93)). Neoverse V2 is Armv9.0 and is not listed with SME, so KleidiAI does not apply on Grace (an inference). The ACL execution provider is separate and not in the standard wheel.
- bf16: "Starting version v1.17.0, ONNX Runtime supports Bfloat16 accelerated SGEMM kernels", enabled with `sess_options.add_session_config_entry("mlas.enable_gemm_fastmath_arm64_bfloat16", "1")`; "MMLA QGEMM kernels are enabled by default" for int8 ([AWS Graviton ONNX guide](https://aws.github.io/graviton/machinelearning/onnx.html)). AWS reports up to 65 % for fp32 inference and up to 30 % for int8 on BERT, RoBERTa and GPT-2, on a c7g.4xl (Graviton3 = Neoverse V1) with ORT 1.17.1 ([AWS blog](https://aws.amazon.com/blogs/machine-learning/accelerate-nlp-inference-with-onnx-runtime-on-aws-graviton-processors), vendor claim, no accuracy statement). fastembed exposes only `enable_cpu_mem_arena` as an extra session option (cpu-oversubscription.md), so this setting needs our own session or a patch.
- PyTorch on aarch64 uses "Compute Library for the Arm® Architecture (ACL) GEMM kernels via the oneDNN backend". "The standard fp32 models use bfloat16 kernels via oneDNN FPmath mode without model quantization", up to 2× ([PyTorch blog](https://pytorch.org/blog/optimized-pytorch-w-graviton/), vendor claim), switched on with `DNNL_DEFAULT_FPMATH_MODE=BF16`. "The fast math mode is not enabled by default" because GEMM then runs in lower precision ([PyTorch Graviton tuning recipe](https://docs.pytorch.org/tutorials/_sources/recipes/inference_tuning_on_aws_graviton.rst.txt)).

**Threads, processes, one weight copy.** On the VM, processes of one thread won over threads in one process (design.md, H2: 8 × 1 10.7 records/s against 1 × 8 8.0 and 4 × 2 9.4). What was not tried is the third layout: one process, one session, N caller threads each running `Run()` with `intra_op_num_threads=1`. That gives one weight copy and no intra-op synchronisation, and `Run()` is thread-safe (section 2). Whether ONNX Runtime's Python binding releases the GIL during `run` I did not verify in the source; the benchmark would show it. In C, the `PrePackedWeightsContainer` shares packed weights between sessions.

**Cache, memory and NUMA (@weber's addition).**
- *Grace's hierarchy* ([Grace tuning guide](https://docs.nvidia.com/grace-perf-tuning-guide/index.html)): L1 "64KB i-cache + 64KB d-cache per core", L2 "1MB per core", L3 "114MB" per Grace CPU, a distributed cache on a mesh ("The CPU cores and SCF cache partitions are distributed throughout the mesh"). LPDDR5X "provides up to 500 GB/s of bandwidth"; its table also gives "Up to 384 GB/s for 480GB", without saying which product that row means. Secondary sources give 480 GB and 512 GB/s for the GH200; I could not open NVIDIA's datasheet, so measure the bandwidth. NVLink-C2C: "Up to 900 GB/s" and "provides memory coherency". The Grace Hopper memory "is set up as two NUMA nodes connected through the high-bandwidth NVLink-C2C". So on the GH200 the CPU side is one NUMA node and the GPU's HBM is another.
- *Placement advice from NVIDIA* ([OS settings](https://docs.nvidia.com/grace-perf-tuning-guide/os-settings.html)): "we recommend that you **do not** use Automatic NUMA Scheduling and Balancing (AutoNUMA)"; "Use NUMA-aware memory allocation (for example using numactl, libnuma, or mbind)". Applications "might have their memory pages allocated from GPU HBM, even if they are not using the GPU". The guide also recommends `init_on_alloc=0`, 64K pages and 2 MB mTHP. For a CPU-only benchmark: `numactl --cpunodebind=<cpu node> --membind=<cpu node>`.
- *ONNX Runtime and NUMA* ([threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)): "Test showed that setting affinities to a single NUMA node has nearly 20 percent performance improvement". Affinities are set with `session.intra_op_thread_affinities`, for example `'3,4;5,6;...'`. There is a global thread pool option for several sessions in one process. This matters on two-socket x86 servers (the dev server), less on the GH200's single CPU node.
- *Why one copy per core need not hurt (*estimate*).* NVIDIA's GEMM guide compares a GEMM's arithmetic intensity (FLOPs per byte moved) with the machine's ops:byte ratio. "matrix-vector products (general matrix-vector product or GEMV), where either `M=1` or `N=1`, are always memory limited" ([GEMM background](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)). Our FFN GEMM has M = tokens in the sub-batch, K = 384 and N = 1,536. With 32 sorted short texts of about 34 tokens (M ≈ 1,088) in fp32, that is 2·M·N·K ÷ (4·(MK + KN + MN)) ≈ 120 FLOP/B. With 32 long texts (M = 16,384), it is about 230 FLOP/B. Grace's balance is about 72 cores × 32 FLOP/cycle × 3 GHz (assumed clock) ≈ 6.9 TFLOP/s fp32, against about 500 GB/s, that is, about 14 FLOP/B. So each layer's weights are read from memory about once per run and then reused from L1/L2 for all tokens: compute-bound. The 72 private copies cost capacity (72 × 133 MB ≈ 9.6 GB), not much bandwidth. Bandwidth matters where work does not scale with tokens. One case is single texts (M ≈ 34: about 8 FLOP/B, memory-bound). The other is the per-run Casts of the fp16 weights (about 67 MB read and 133 MB written per run, *estimate*). With short texts and many processes these add up: at, say, 0.3 s per run of 32 short texts, 72 processes move about 50 GB/s for the Casts alone (*estimate*). That is a reason to measure the fp32 file (section 4, graph optimisation) on Grace.

### 6. Energy (question 5)

I found no credible study that compares CPU and GPU energy per embedding. The closest, all on other setups:
- Alizadeh and Castor, "Green AI" (CAIN 2024, [arXiv 2402.13640](https://arxiv.org/html/2402.13640v1)): BERT-base on an RTX 3070 laptop GPU, measured with nvidia-smi and RAPL, idle baseline subtracted. In their Table 1, the PyTorch model exported to ONNX used 4,750 J total at batch 1 and 1,767 J at batch 64, against 9,892 J and 2,881 J for PyTorch. They ran no CPU-only BERT.
- Ferreira, Paleyes and Lawrence (CAIN'26, [arXiv 2601.08991](https://arxiv.org/abs/2601.08991)): "parameter and floating-point operation counts can be unreliable proxies for energy consumption".
- A non-peer-reviewed tutorial page claims GPU cost ratios for sentence-transformers, without its setup; not used.

The GH200 can measure energy itself ([power and thermals](https://docs.nvidia.com/grace-perf-tuning-guide/power-thermals.html)). `nvidia-smi -q -d POWER` reports module and GPU power. The hwmon `power1_average` (µW, 50 ms window by default; needs `acpi_power_meter`) reports "Module Power" (the whole module including DRAM, GPU and HBM), "Grace Power Socket 0", "CPU Power Socket 0" and "SysIO Power Socket 0". Regulator loss is about 15 % of the TDP and is included.

### 7. What this means for the benchmark on Grace

Run the same texts everywhere, as three sets taken from real records: short (about 20 to 60 tokens), long (512 after truncation) and the real length mix of staging. Report each cell's records/s, tokens/s, CPU seconds per text, J per text (module power, and Grace CPU power for the CPU cells), peak RSS or GPU memory per process, and the agreement of its embeddings with production's: cosine to the production vector, and identical top-10 on a fixed query set. Record `lscpu` (flags `bf16`, `i8mm`, `sve2`), `numactl -H`, `cat /proc/sys/kernel/numa_balancing`, driver, CUDA and package versions. Take a smoke test of one cell end to end first.

**CPU (72 cores), ONNX Runtime CPU:** production's fastembed 0.8.0 / ORT 1.24.4 as the baseline, and ORT 1.31.1 (the current PyPI release, with aarch64 wheels, checked 2026-11-13).

| Axis | Values |
|---|---|
| layout | 72 processes × 1 thread; 36 × 2; 18 × 4; 1 process × 72 intra-op threads; **1 process, one session, 72 caller threads with intra-op 1** (one weight copy) |
| memory placement | as the system does it; `numactl --cpunodebind=0 --membind=0` (CPU node) |
| sub-batch (sorted) | 16, 32, 64, 128; and token budgets of 2k, 4k, 8k tokens |
| model file | as in production (fp16 stored, 53 Casts per run); fp32 file; fp32 file through the ORT transformer optimizer (FastGelu fused) |
| math | fp32; bf16 fast-math on; int8 dynamic (quality measured separately, decision for @weber) |

Not every combination: first the layout × placement on the production model with sub-batch 32, then the model files and the math on the best layout, then the sub-batch sizes.

**GPU (H100), ONNX Runtime CUDA provider** (`onnxruntime-gpu` 1.31.1 aarch64 wheel, fastembed-gpu, or our own session). Optionally two references for what padding-free kernels give: TEI (a build from source on aarch64) and Sentence Transformers with fp16 and FlashAttention-2. Whether flash-attn wheels exist for aarch64 is not checked.

| Axis | Values |
|---|---|
| precision | fp32 (TF32 on, the default); fp16 model (`optimizer.py --float16 --use_gpu`) |
| batch, sorted | token budgets of 4k, 8k, 16k, 32k, 64k tokens (for 512-token texts: 8 to 128 texts; for short texts several hundred to thousands) |
| feeders | 1, 2, 4 processes, each with its own session (each a CUDA context); and 1 process with 2 to 4 threads on one session; for > 1 process, MPS on and off |
| tokenizer | measured alone first (texts/s per core on the three sets); `RAYON_NUM_THREADS` for the feeders |
| padding | sorted only; ORT packing mode (`convert_to_packing_mode.py`) on the fp16 model |

Measure in addition GPU utilisation (`nvidia-smi dmon` or DCGM, SM activity), GPU memory per process (context plus weights plus arena), and the CPU cores the feeders use. Those cores count against the GPU path's efficiency: J per text from module power covers CPU and GPU together. The comparison CPU against GPU is then: best records/s and J per text of each, on the same three sets, at the same embedding agreement.
