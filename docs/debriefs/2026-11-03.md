# Debrief 2026-11-03: the crawler from design to reviewed implementation

Coverage: one session, 2026-10-14 to 2026-11-03, compacted once around 2026-10-27; the first two weeks seen through the summary and the files. Earlier debriefs: none.

## In five lines

- One session carried the crawler from "what is a dataset" to a reviewed, tested implementation with a full crawl of the real tree.
- What made it work: principles stated once and trusted; behaviour judged by trying it rather than by reviewing text; decisions given as numbered answers to the agent's question lists; requests that specify the desired outcome or user experience without taking a position on the solution; every review finding checked by a second agent trying to refute it.
- What cost: background work that died with the session, the agent's own defaults caught only by the review, instruments scaled before a smoke test.
- For you: say when a case is an example of a general rule; before leaving, decide what must outlive the session and where it runs; ask "what changes for the user" when a change is designed, not after; disagree with at least one recommendation per review.
- Seven small proposals below; the one medium item is the structure session for the design record.

## Numbers

20 days, 127 user turns, 1,326 assistant turns, 611 tool calls (Bash 355, Write 71, WebFetch 60, Edit 59, Read 31, Agent 12), 3.3 million output tokens in the main loop (Fable 2.7, Opus 0.57), 23 sub-agent transcripts, one compaction. The review workflow alone: 1.48 million tokens including input.

## What went well

- **State principles once and trust them.** YAGNI, "no new inventions", "outcomes over implementation", stated in the first days, shaped three weeks of decisions through the agent's memory without being repeated.
- **Judge behaviour by trying it, not by reviewing text.** "I don't want to review the spec; we fix it if it leads to bad outcomes" → a tester agent ran 20 experiments in an afternoon and found the json5 bug that the spec review would not have.
- **Specify the outcome, not the solution.** "I want to see diagnostics alongside an entry in `less`", with the XML-comment idea deliberately kept back → the agent arrived at it from the constraint that the document stays valid, and the requirement (R40) was written as an outcome.
- **Answer question lists with numbered decisions.** One message answering eleven TODO items after the vacation → a full day of fixes, each with scenario and test, with no further round trip.
- **Verify every finding adversarially.** A second agent per review dimension tried to refute each finding against the code: 25 of 62 corrected in cause, severity or action, none refuted outright, so observations were reliable and prescriptions were not.
- **Check human-facing output in a real terminal.** A Sonnet agent drove an xterm and judged screenshots: it found the summary scrolled off and 557 routine comments drowning the signal, which no text-parsing test had seen.

## What cost

- 🔴 **Background work died with the session.** Play tester and crawl launched 2026-10-16 before ten days away; both stopped an hour later, ran 2026-10-27.
  Cause: no "before logging off" step asking what must outlive the session and where it runs.
- 🟡 **Edits after a formatter.** 2026-11-03: a string-replacement fix silently missed because ruff had reformatted the file; an assert caught it.
  Cause: editing text not re-read. Keep the assert habit; re-read after formatters.
- 🟡 **Two lint configurations.** `ruff` from the package passed, the pre-commit hook from the root failed; you hit it at commit time.
  Cause: "clean" reported from a different command than the commit runs. Fixed: run the hook's command.
- 🟡 **Instruments scaled before a smoke test.** The `pytester` plugin tests took four rounds; the xterm driver, smoke-tested first, took one.
  Cause: writing all scenarios before one had run.
- 🟡 **The agent's defaults are your pet peeves.** 62 findings in 2,100 lines: a reinvented matcher, generality with one user, polish without a requirement.
  Cause: nothing in the loop asked "which scenario asks for this". Fixed in part: standing rules in `AGENTS.md`; a review per change remains.
- 🟢 **Six places to keep coherent.** The stale-docs findings came from the spread; structure session planned.
- 🟢 **Notes started late.** The lessons file began on day 20; two weeks survived only through the summary and the design documents.

## Coaching for @weber

Keep doing: state principles once; ask for options with counter-arguments instead of decisions; refuse to review long generated text and judge the behaviour instead; answer question lists with numbered replies; specify the outcome and keep your own solution idea back; bring in a cold critique and colleagues as reviewers.

1. **Label examples.** Several one-case requests meant a rule; you noticed. Cheapest habit here, and the agent now asks when in doubt.
2. **Plan what outlives a session.** Ten days away with two background jobs and a tester that wanted to ask you questions. Ask before logging off, and expect the agent to say "that will not survive".
3. **Ask the behaviour question early.** "Any decisions that impact behaviour towards the user?" settled five changes in one message after the review; at design time it is a standing question per change.
4. **Challenge one recommendation per review.** All eleven D leans accepted in a line; defensible, but disagreement is where you add the most.
5. **Decide the structure before the next change.** The OpenSpec trial bought reviewers something to check against and cost six documents; you named it yourself.

## Models and effort

Proportionate. High effort on Fable for design, critique and review is what bought the verifiers' corrections and twelve defects; Opus for the implementation stretch was adequate; Sonnet for the visual tester was the right size, and the play tester could have been Sonnet too. The mechanical scan found no defect and costs nothing: hints only. Waste was in wall-clock (subprocess tests, harness rounds), not tokens.
